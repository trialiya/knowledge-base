## 3. Локальный запуск для разработки

### 3.1. База данных

```bash
cd docker
cp example.env .env
# Отредактируйте .env — укажите AI_API_KEY, AI_EMBED_API_KEY, PROJECT_PATH_MOUNT
docker compose up -d postgres
```

PostgreSQL будет доступен на `localhost:5432`.

### 3.2. Бэкенд

```bash
./gradlew :backend:bootRun
```

Бэкенд запустится на `http://localhost:8080`.

### 3.3. Фронтенд (dev-режим с hot reload)

```bash
./gradlew :frontend:yarnServe
```

Vite-сервер поднимется на `http://localhost:3000` и будет проксировать `/api` на `localhost:8080` (настроено в `vite.config.js`, секция `server.proxy`).

### 3.4. Полная сборка

```bash
./gradlew build
```

Выполняет: `yarnInstall` → `yarnBuild` → `copyFrontend` (в `frontend/build/static`) → `bootJar`, который упаковывает эту статику в JAR.

## 5. Форматирование кода (Spotless)

### Бэкенд (Google Java Format)

```bash
./gradlew spotlessApply    # Форматировать
./gradlew spotlessCheck    # Проверить
```

Настройки в `backend/build.gradle`:
- `googleJavaFormat('1.28.0').aosp()` — AOSP-стиль
- `importOrder()` — сортировка импортов
- `removeUnusedImports()` — удаление неиспользуемых импортов
- `endWithNewline()` — завершающий перевод строки

### Фронтенд (Prettier)

```bash
./gradlew :frontend:spotlessApply
```

Настройки в `frontend/build.gradle`:
- `semi: true` — точки с запятой
- `singleQuote: true` — одинарные кавычки
- `trailingComma: 'all'` — запятые везде
- `printWidth: 120` — ширина строки

> ⚠️ **Требуется Node.js локально.** Spotless для фронтенда запускает Prettier через Node.js. В отличие от фронтенд-сборки (где Node скачивается Gradle-плагином автоматически), Spotless использует системный Node.js. Если `spotlessCheck` падает с ошибкой «node: command not found» — установите Node.js 22+ в систему.

## 6. Null-safety (JSpecify + NullAway)

Бэкенд аннотирован [JSpecify](https://jspecify.dev/) и проверяется [NullAway](https://github.com/uber/NullAway) (через плагин `net.ltgt.errorprone`) прямо в `:backend:compileJava` — нарушение падает сборку так же, как обычная ошибка компиляции.

**Как это устроено:**
- Каждый пакет в `backend/src/main/java` помечен `@NullMarked` через свой `package-info.java` — все типы в нём по умолчанию не-null, кроме явно помеченных `@Nullable` (поле, параметр, возврат метода).
- NullAway настроен в `backend/build.gradle` с `OnlyNullMarked=true` (проверяет только `@NullMarked`-код, но включая вызовы в него из непомеченного кода) и `JSpecifyMode=true` (понимает `org.jspecify.annotations.Nullable`, а не только собственные аннотации).
- `compileTestJava` из-под NullAway выведен целиком (`options.errorprone.enabled = false`) — тесты намеренно передают `null` для проверки граничных случаев, и гонять по ним null-checker чистый шум.

**Как чинить нарушение:**
- Если значение действительно может быть `null` — добавить `@Nullable` (поле/параметр/возврат) и обработать `null` у вызывающей стороны.
- Если NullAway не видит инвариант, который в коде очевиден (например, id сущности, только что сохранённой через `repo.save()`, всегда не-null) — обернуть в `Objects.requireNonNull(...)` с комментарием, откуда взялась гарантия, а не подавлять проверку.
- Для сущностей Spring Data JDBC / DTO, наполняемых фреймворком через `@NoArgsConstructor` + сеттеры или Jackson (полей не видно в конструкторе, который анализирует NullAway) — `@SuppressWarnings("NullAway.Init")` на классе, как в `DocumentEmbeddingEntity` и соседних `@Data @NoArgsConstructor` сущностях.
- Создавая новый пакет в `backend/src/main/java` — добавить в него свой `package-info.java` с `@NullMarked` (скопировать из соседнего пакета), иначе NullAway тихо пропустит весь пакет.

```bash
./gradlew :backend:compileJava   # запускает NullAway; нарушение — обычная ошибка компилятора
```

## 7. Статический анализ (PMD + SpotBugs)

Помимо NullAway бэкенд проверяют [PMD](https://pmd.github.io/) (по исходникам) и
[SpotBugs](https://spotbugs.github.io/) (по байт-коду). Обе падают на любом нарушении.

**С `check` они намеренно сняты** — `./gradlew build` их не запускает. Ни один из инструментов не
инкрементален: правка одного `.java` заставляет перепроверить все исходники (~14 с), и платить это
на каждой локальной сборке невыгодно. Вместо этого их зовут по имени: `./run/test.sh lint`, гейт
`pre-pr` и отдельный шаг в `backend-pr.yml`.

**Где настройка:**

| Что | Где |
|---|---|
| Набор правил PMD | `config/pmd/ruleset.xml` |
| Фильтр исключений SpotBugs | `config/spotbugs/exclude.xml` |
| Версии инструментов и подключение | `backend/build.gradle` (блоки `pmd` / `spotbugs`) |

Оба файла — с комментариями: каждое исключённое правило объясняет, почему оно не подходит именно
этому коду. Правил взято не «всё подряд», а то, ради чего стоит ронять сборку: стиль и именование
остаются за Spotless, а null-safety — за NullAway (поэтому в SpotBugs отключены `NP_*`-детекторы,
которые не понимают JSpecify).

**Только main-исходники.** `pmdTest` и `spotbugsTest` выключены — тот же срез, что у NullAway
(`compileTestJava`): тесты намеренно передают `null`, дублируют фикстуры и полагаются на
жизненный цикл JUnit.

**Как чинить нарушение:**
- Сначала — по существу: правило чаще право, чем нет (так, `CloseResource` нашёл незакрытые
  нативные хендлы tree-sitter в `TreeSitterOutlineParser`).
- Если в конкретном месте правило неприменимо — точечное подавление рядом с кодом:
  `@SuppressWarnings("PMD.ИмяПравила")` на методе плюс комментарий, почему; для SpotBugs —
  адресный `<Match>` с `<Class>`/`<Method>` в `config/spotbugs/exclude.xml`.
- Правило целиком выключают только если оно не подходит всему проекту, и всегда с комментарием
  в ruleset/фильтре.

```bash
./run/test.sh lint                             # обе проверки
./gradlew :backend:pmdMain :backend:spotbugsMain
```

Отчёты — в `backend/build/reports/pmd/main.html` и `backend/build/reports/spotbugs/main.html`;
в CI (`backend-pr.yml`) они выкладываются артефактом `backend-static-analysis-reports`.

## 9. База данных и миграции

Используется **Flyway**. Миграции лежат в `backend/src/main/resources/db/migration/`.

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    validate-on-migrate: false
```

## 10. Docker-сборка

Dockerfile использует **трёхстадийную сборку**:

1. **Stage 1 (build):** `eclipse-temurin:25-jdk-alpine` + Node.js/Yarn → `./gradlew :backend:bootJar`
2. **Stage 2 (extract):** `eclipse-temurin:25-jre-alpine` → распаковка слоистого JAR (`java -Djarmode=tools -jar app.jar extract --layers`)
3. **Stage 3 (runtime):** `eclipse-temurin:25-jre-jammy` + git + curl → копирование слоёв из extract → запуск через `start.sh`

Entrypoint — `start.sh`:
```sh
#!/bin/sh
exec java $JAVA_OPTS -jar app.jar
```

Сборка образа:
```bash
docker build -t kb-backend -f docker/Dockerfile .
```

Запуск полного стека:
```bash
cd docker
cp example.env .env
docker compose up -d
```

## 12. Virtual Threads

В проекте включены виртуальные потоки Java 25:
```yaml
spring:
  threads:
    virtual:
      enabled: true
```

Это означает, что все HTTP-запросы обрабатываются на виртуальных потоках — не нужно настраивать пулы потоков.

## 13. Tree-sitter (опционально)

Tree-sitter используется для структурного анализа кода в `OutlineService`. Это нативная библиотека, которая подключается через JNI.

**Поддерживаемые языки:** Java, JavaScript, TypeScript, Python.

**Важно:** Tree-sitter — опциональная зависимость. Если нативная библиотека недоступна (например, несовместимая платформа), `OutlineService` автоматически переключается на regex-парсер. Функциональность структурного анализа кода сохраняется, но с меньшей точностью.

**Зависимости в `build.gradle`:**
- `tree-sitter` (core)
- `tree-sitter-java`
- `tree-sitter-javascript`
- `tree-sitter-typescript`
- `tree-sitter-python`

## 15. Dependency Locking

Проект использует Gradle dependency locking. Lock-файлы (`gradle.lockfile`) зафиксированы в репозитории.

Для обновления lock-файлов после изменения зависимостей:
```bash
./gradlew resolveAndLockAll --write-locks
```

> **Важно:** задача `resolveAndLockAll` несовместима с Gradle Configuration Cache и требует флага `--write-locks`. Без него выполнение прервётся с ошибкой.
