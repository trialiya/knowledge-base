## Обзор чат-системы

Документ описывает архитектуру и ключевые компоненты чат-системы Knowledge Base. Чат — это AI-ассистент, который отвечает на вопросы пользователя, используя инструменты (tools) для доступа к базе знаний, Git-репозиторию и вложениям.

- [Конфигурация](конфигурация.md) — `ChatConfig`, параметры AI, `ChatModelProperties`, `ChatModeProperties`, `SecurityConfig`, `SubAgentConfig`
- [Фронтенд — обзор архитектуры](фронтенд-обзор-архитектуры.md) — как чат устроен на клиенте
- [Сжатие контекста чата](../features/сжатие-контекста-чата.md) — разбор суммаризации и `/compact` рядом: чем отличаются, чего стоят, когда применяются

### 1. Архитектура чата

```
Пользователь (Frontend)
    │  HTTP (REST + SSE events)
    ▼
ChatController  (/api/chats)
    │
    ├── ChatRunService — запуск фоновой генерации (virtual threads)
    │       ├── ChatClient (Spring AI)
    │       │     ├── ChatModel (OpenAI-совместимый)
    │       │     ├── Advisor-цепочка (см. §6.3):
    │       │     │     ToolCallingAdvisor → MessageChatMemoryAdvisor
    │       │     │     → InterjectionAdvisor → TokenUsageAdvisor
    │       │     │     → MessageLoggingAdvisor
    │       │     ├── ChatMemory (ChatHistoryMemory) → ChatHistoryService → PostgreSQL (chat_message)
    │       │     ├── ToolCallbacks (функции + MCP) → RecordingToolCallback → ToolInvocationCollector
    │       │     └── System Prompt (classpath:prompt/sys.md, плейсхолдер {mode_instructions})
    │       └── ChatEventService → ConversationHub (in-memory pub/sub + replay)
    │
    ├── ChatEventService — SSE-канал: стриминг + кросс-вкладочная синхронизация
    │       └── ConversationHub — лог событий + fan-out на подписчиков (SseEmitter)
    │
    ├── ChatModeService — фрагменты инструкций «режимов» ассистента
    ├── ChatRuntimeMonitor — мониторинг утечек (логирование размеров реестров)
    ├── ChatRuntimeShutdown — остановка прогонов и SSE-подписок при shutdown
    ├── ChatTopicRepository → PostgreSQL (chat_topic)
    ├── ChatHistoryService → chat_message · ToolCallService → tool_call_index (детали вызовов)
    ├── ChatSearchService → поиск по чатам и сообщениям
    ├── SummarizeService (фоновая суммаризация)
    └── CompactService (сжатие контекста по команде /compact)

GitController  (/api/git)
    └── GitService — fuzzy-поиск и чтение tracked-файлов репозитория

SettingsController  (/api/settings)
    ├── GET /api/settings/ai-config — снапшот AI-конфигурации для панели настроек
    └── GET /api/settings/tools — каталог инструментов модели (ToolCatalogService)

SecurityConfig — HTTP Basic Auth (stateless, in-memory user)
```

**Ключевые особенности:**
- **Фоновые прогоны (background runs)** — генерация ответа не привязана к HTTP-запросу: `POST /runs` запускает задачу и сразу возвращает `runId`, ответ приходит через SSE event channel. Ответ переживает перезагрузку страницы и виден всем вкладкам
- **SSE event channel** — единый поток событий (`GET /events`) для стриминга ответа и кросс-вкладочной синхронизации. При подключении реплеятся пропущенные события (по `seq`), затем идут живые
- **Остановка генерации** — явный сигнал `POST /runs/{runId}/stop` вместо разрыва соединения
- **Посегментное сохранение** — tool-цикл ведёт `ToolCallingAdvisor`, а `MessageChatMemoryAdvisor` работает **внутри** цикла и сохраняет каждый сегмент (текст ассистента + `tool_calls`, ответы инструментов) отдельным сообщением. Отдельного «сохранения tool calls в конце прогона» больше нет
- **Протокольные tool-данные в сообщении** — вызовы и ответы инструментов лежат в `chat_message.tool_data` (JSON), а UI-метаданные — в `chat_message.meta`. Индекс `tool_call_index` отображает `callId` → строки сообщений, что даёт точечный `GET /tool-calls` для модалки деталей
- **Режимы ассистента** — «Аналитик», «Разработчик», «Тестировщик»: подстановка фрагмента инструкций в системный промпт (см. §7)
- **Инструменты (tools)** — AI может вызывать функции для поиска документов, чтения файлов, истории коммитов, правки файлов рабочего дерева, а также `searchCodebase` (sub-agent для многошагового поиска)
- **Компактные результаты** — `CompactToolResultConverter` сжимает результаты в `resultGist` для отображения в UI
- **Частичное сохранение при остановке/ошибке** — при `RUN_STOPPED`/`RUN_ERROR` накопленный хвост сегмента сохраняется с маркером `[stopped]`/`[error]`
- **Починка оборванных пар** — `repairDanglingToolCalls` достраивает `assistant.tool_calls` без TOOL-ответа, иначе модель отвергла бы такой диалог; достроенный ответ пишется в `tool_call_index` наравне с обычным, иначе оборванный вызов навсегда остался бы для модалки деталей «ещё работающим»
- **Суммаризация** — длинные диалоги автоматически сжимаются, чтобы не превысить контекстное окно
- **Сжатие по команде (`/compact`)** — пользователь может сжать весь контекст чата сразу, не дожидаясь порогов: окно уходит модели теми же сообщениями, что и в обычном прогоне, с полными аргументами и результатами вызовов инструментов (см. §12)
- **Выбор модели, режима и проекта** — переключаются для каждого чата по отдельности; проект (репозиторий) определяет, в каких файлах работают инструменты модели
- **Поиск** — по всем чатам пользователя (`GET /search`) и внутри одного чата (`GET /messages/search`, find-бар Ctrl+F)
- **Внешние инструменты через MCP** — к чат-модели можно подключить внешние MCP-серверы (`kb.mcp.enabled` + `spring.ai.mcp.client.*`) — конкретный сервер не встроен и настраивается оператором
- **Библиотека фраз** — готовые подсказки над полем ввода в пустом чате, управляются из БД через [PhraseController](api-reference.md)
- **Вставка файлов и документов (`/file`, `/doc`)** — fuzzy-поиск прямо в композере чата, вставка как чипы с превью содержимого
- **HTTP Basic Auth** — stateless-аутентификация с единственным in-memory пользователем из конфига (`kb.security.*`)

| `ChatHistoryService` | Персистентное хранение сообщений и чтение истории |

Служебные сообщения-«крошки» вызовов инструментов (флаг `meta.toolCalls`) при выдаче обрезаются до преамбулы — JSON пользователю не показывается. Удаление чата останавливает идущую генерацию и рассылает событие `CHAT_DELETED`, чтобы открытые на нём вкладки закрыли его.

#### Фоновые прогоны (Background Runs)

Генерация ответа не привязана к HTTP-запросу:

1. **`POST /runs`** — принимает сообщение, **сохраняет его синхронно** (см. §3), запускает генерацию в фоновом потоке (virtual thread) и сразу возвращает `{ "runId": "...", "messageId": 123 }`. Если генерация уже идёт — `409 Conflict`
2. **`GET /events`** — постоянное SSE-соединение. При подключении реплеит пропущенные события (по `fromSeq`), затем шлёт живые
3. **`POST /runs/{runId}/stop`** — явная остановка: `dispose()` → `CANCEL` → частичное сохранение + событие `RUN_STOPPED`
4. **`GET /runs/active`** — для восстановления состояния после перезагрузки страницы

**Преимущества:**
- Ответ продолжает генерироваться после перезагрузки страницы
- Все вкладки видят один и тот же ответ (кросс-вкладочная синхронизация)
- Остановка — явный сигнал, а не разрыв соединения
- `clientMsgId` защищает от задвоения оптимистичного пузыря
- Вопрос пользователя не теряется, даже если прогон упадёт до подписки на стрим

### 3. ChatRunService — фоновые прогоны

`ChatRunService` — центральный сервис, запускающий генерацию как фоновую задачу:

- **`start(conversationId, user, userMessage, contextItems, options, clientMsgId)`** — атомарная заявка на чат (`ConversationSlots.take`), затем синхронно `repairDanglingToolCalls` + `saveUserMessage`, затем запуск в `chatRunExecutor` (virtual threads + `DelegatingSecurityContextExecutorService`). Возвращает `StartedRun(runId, userMessageId)`
  - **`userMessage = null` — повтор упавшего прогона** (`POST /runs` с `retry`): нового сообщения не появляется, ходом остаётся последний неотвеченный вопрос (`unansweredUserMessage`). Если модель успела выдать хоть что-то — текст или вызов инструмента — повтор запрещён (`422`), см. §3.2
- **`stop(conversationId, runId)`** — `dispose()` реактивного стрима
- **`stopAll()` / `awaitQuiescence(timeout)`** — гашение всех прогонов при остановке приложения (см. §5)
- **`activeRun(conversationId)`** — делегирует в `ConversationSlots`, а та — в `ChatEventService`

**Поток выполнения (`run()`):**
1. Публикует `USER_MESSAGE` (эхо для других вкладок, с `id` сохранённого сообщения) и `RUN_STARTED`. На повторе сообщение не новое, но событие всё равно публикуется: вкладки сверяют пузырь по `id` и срезают всё, что стоит после него, — так пузырь с ошибкой упавшего прогона исчезает везде сразу
2. Создаёт `ChatClient` prompt: `mode_instructions` в системный промпт, `toolContext` (явная передача пользователя — операторы Reactor исполняются на других потоках, куда thread-local `SecurityContext` не доезжает), advisor-параметры `CONVERSATION_ID` и `RUN_ID_PARAM`. Своего `.user(...)` в промпте **нет** — вопрос уже в истории, его подставит advisor памяти
3. Подписывается на реактивный стрим: `onNext` → `STREAM`, `onComplete` → `markRunResult` + `TOOL_CALLS` + `RUN_DONE` + суммаризация
4. `doFinally`: `CANCEL` → частичное сохранение + `RUN_STOPPED`, `ON_ERROR` → частичное сохранение + `RUN_ERROR`
5. `cleanup()`: пишет учётную строку по токенам прогона и отдаёт чат — `ConversationSlots.release`, то есть закрытие хаба и снятие заявки в одном месте и в одном порядке (сначала хаб). Обратный порядок отдал бы чат следующей операции, а её событие ушло бы в хаб, который этот `cleanup` как раз закрывает

**Границы сегментов и буфер.** Завершённые сегменты сохраняет advisor-цепочка по ходу прогона, поэтому в буфере держится только хвост текущего сегмента — иначе `persistPartial` задублировал бы уже сохранённое. Буфер сбрасывается на `finishReason=TOOL_CALLS` и по колбэку `ToolInvocationCollector` (вызов инструмента — надёжная граница: агрегированный tool-чанк `ToolCallingAdvisor` отфильтровывает из потока).

**Порядок в `persistPartial`:** сначала `repairDanglingToolCalls`, только потом запись частичного текста — иначе записанный первым `partial` навсегда спрятал бы оборванную пару (`repairDanglingToolCalls` смотрит только на последнюю строку), и модель отвечала бы `400` на каждый следующий запрос этого чата.

**Гонка «стоп до подписки»:** `cancel()` ставит флаг ДО чтения `disposable`, а `run()` ставит `disposable` ДО чтения флага — так остановка не проваливается в окно между постановкой задачи в пул и подпиской на стрим.

#### 3.1. Контекст, приложенный к сообщению

Файл, приложенный в композере, попадает не только в список вложений чата, но и **в само
сообщение** — ссылкой в `chat_message.meta.contextItems` (см. `ContextItem` в
[модели данных](модели-данных/чат.md)). Раньше вложение существовало отдельно от диалога, и
модель узнавала о нём, только если сама догадывалась спросить список вложений.

Ключевые решения:

- **Ссылка, а не копия.** В историю уходит id, а не содержимое: файл может быть на мегабайт, и
  в промпте он остался бы навсегда. `ContextItemService.render` собирает опись приложенного при
  **каждом** чтении истории (`ChatHistoryService.promptMessages`) и дописывает её к тексту
  вопроса блоком `<attached-context>`. Содержимое модель читает инструментом
  `getAttachmentContent` тогда, когда оно понадобилось.
- **Переименовали — увидит новое имя, удалили — не увидит ничего.** Следствие того же резолва
  при чтении: удалённое вложение просто выпадает из блока, а не остаётся вечным обещанием файла,
  которого больше нет.
- **Записанный текст не меняется.** Блок живёт только в `UserChatMessage`, отданном модели;
  `chatMessage().getContent()` по-прежнему отдаёт то, что написал пользователь, — на этом держатся
  и дедупликация в `append`, и показ сообщения в ленте.
- **Опись получает только вопрос,** и решает это одно место — сборка ряда в
  `ChatHistoryService.promptRow`, до того как ряд разойдётся на промпт и на весы сжатия. Блок
  говорит о том, что приложил **пользователь**, и на ответе модели был бы неправдой; проверка типа
  ниже по течению, во второй раз, развела бы стороны молча.
- **Клиенту верят только на ссылку.** `ContextItemService.resolve` проверяет, что вложение
  принадлежит этому чату (иначе чужой id стал бы способом прочитать чужой файл), и берёт подпись с
  самого объекта, а не из запроса.
- **Момент привязки — не проблема.** Мы сами пишем USER-ряд в `start()` (см. этап предсохранения),
  поэтому элементы уходят в `meta` той же вставкой: ни знания id заранее, ни второго запроса.

Сжатие истории про это знает: `summarizer.md` требует сохранять имя и id вложения дословно —
блок `<attached-context>` исчезает вместе со сжатым сообщением, и потерянный id означает файл,
до которого больше не добраться.

> **Читаешь сообщения мимо `promptMessages` — бери текст из `promptRows`, а не из `content`.**
> Опись живёт в `meta`, а не в `content`, поэтому любой другой читатель истории теряет упоминание
> вложения молча. Окно истории целиком читается через `ChatHistoryService.promptRows` (так устроен
> вход суммаризатора и его бюджет в `SummarizeWindow`); точечному читателю одного сообщения — как
> `MessageLookupFunction.getOriginalMessages` — остаётся `render`. Третий читатель появится —
> сводите его к одному из этих двух путей.

**Чат заводит то, что в нём сделали первым.** Отдельного «создать чат» нет ни в API, ни в UI:
`conversationId` придумывает фронт, а строка в `chat_topic` появляется от первого обращения —
`ChatTopicService.ensureExists`. Долгое время таким обращением было только сообщение, и создание
жило внутри `ChatController.checkChat`. Теперь первым может оказаться вложение — файл прикладывают
к ещё не начатому разговору, — и `AttachmentService.uploadForChat` заводит чат той же транзакцией,
что и файл: отвергнутый файл пустого чата не оставляет. Обратная сторона — id для загрузки берётся
из запроса, поэтому фронт не должен слать туда свой черновичный `new`: панель вложений в черновике
выключена именно за этим.

Отменённый чип (крестик над полем ввода) **удаляет вложение**. Иначе файл, приложенный по ошибке,
оставался бы в чате незамеченным: чип — единственный его след на экране до отправки. Симметрично,
удаление файла из панели вложений снимает чип, чтобы отправка не упала на ссылку в никуда.

#### 3.2. Повтор упавшего прогона

Повторить ход можно **ровно в одном состоянии**: вопрос сохранён, а модель не выдала ничего — ни текста, ни вызова инструмента. Тогда в истории дописывать нечего, и повтор просто запускает прогон поверх неё заново, без второго `USER`-ряда.

Как только ответ начался, повтор запрещён. Переиграть такой ход молча можно было бы только двумя способами, и оба хуже прямого продолжения диалога: задвоить вопрос вторым `USER`-рядом либо стереть сделанное моделью, включая побочные эффекты уже выполненных инструментов. Поэтому дальше пользователь пишет сам — «продолжай».

Решает это `ChatHistoryService.unansweredUserMessage`: последний ряд чата, если это `USER`. Проверка идёт **после** `repairDanglingToolCalls` — достроенный TOOL-ответ как раз и означает, что ответ уже начался, и он же закрывает окно повтора. В обратном порядке последним рядом ещё был бы вопрос, и прогон стартовал бы поверх незакрытой пары.

На фронте то же решение принимается заранее, в момент ошибки, — там ещё известно, доехал ли вопрос до бэка (`constants/retryMode.js`):

| Режим | Когда | Что делает «Повторить» |
|---|---|---|
| `resend` | Сбой самого `POST /runs` | Отправляет текст вопроса заново — на бэке его нет |
| `continue` | `RUN_ERROR`, и прогон не выдал ни текста, ни вызова инструмента | `POST /runs` с `retry` — прогон поверх той же истории |
| нет режима | `RUN_ERROR` после начатого ответа | Кнопки нет вовсе |

Бэк остаётся единственным арбитром: если состояние успело измениться (другая вкладка, гонка с событием), `retry` получает `422`, кнопка с пузыря снимается и показывается пояснение.

#### 3.3. Сообщение во время прогона

Пользователю не нужно ждать конца ответа: `POST /runs/{runId}/messages` принимает сообщение в
очередь чата (`chat_pending_message`, единственный писатель — `PendingMessageService`) и отвечает
`202`. Отдельная таблица, а не ряд `chat_message` с флагом: пока идут инструменты, хвост истории —
это незакрытая пара `assistant.tool_calls` → `tool`, и `USER`-ряд внутри неё сделал бы диалог
протокольно невалидным.

**Три места доставки.** Ряд появляется в истории там, где это безопасно:

| Где | Кто | Что за ряд |
|---|---|---|
| Между итерациями tool-цикла | `InterjectionAdvisor` | `meta.interjection` — вопрос внутри идущего хода |
| В конце прогона | `ChatRunService.deliverQueued` | Обычный вопрос — следующий ход чата |
| На приёме, если генерации уже нет | `ChatRunService.deliverIfNobodyGenerates` | То же самое, но без ответа: прогон кончился между проверкой и коммитом строки |
| На старте приложения | `PendingMessageRecovery` | То же самое, только позже: процесс упал вместе с прогоном |

Конкурирующие точки (advisor и терминальная обработка могут прибежать почти одновременно)
разводятся claim-through-delete на уровне строки: доставляет тот, чей `DELETE` её застал.

**Обычным вопросом — только в незанятом чате.** Три доставки из четырёх идут изнутри прогона или
после него, а две оставшиеся — приём и восстановление на старте — работают рядом с чужой генерацией
и потому сперва убеждаются, что её нет: приём смотрит на реестр прогонов чата (а не на тот прогон,
к которому сообщение вставало в очередь — за то же окно другая вкладка успевает начать следующий),
восстановление берёт ту же заявку на чат, что и прогон со сжатием. Иначе `USER`-ряд лёг бы в
середину чужого хода — ровно то, ради чего заведена отдельная таблица. Зависнуть строка при этом не
может: прогон покидает реестр **до** собственной доставки, поэтому «увидел живым и не дождался
доставки» — состояние недостижимое.

**Почему advisor стоит именно там.** Его порядок — строго между advisor-ом памяти
(`DEFAULT_ORDER + 100`) и самыми внутренними (`LOWEST_PRECEDENCE`): к этому моменту `MessageChatMemoryAdvisor.before()`
уже записал TOOL-ответы итерации, то есть хвост истории — `tool`, а не оборванный
`assistant.tool_calls`. Доставленные ряды advisor дописывает и в инструкции **текущей** итерации:
окно памяти собрано раньше их записи, и иначе модель увидела бы их только следующей итерацией,
которой может не быть.

**Модель знает, что это перебивка.** Ряд с `meta.interjection` читается из истории обёрнутым в
`<user-interjection>` (собирается на чтении, в БД не попадает — как маркер смены проекта и
git-команда). Инструкция summarizer'у здесь **обратная** остальным маркерам: свернуть как обычную
реплику, тег не сохранять — к моменту сжатия прогон давно кончился, и «пока ты работал» уже ничего
не значит.

**Такой ряд не открывает ход.** Всё, что ищет «последний вопрос», обязано смотреть сквозь него —
`ChatHistoryService.opensATurn` и его фронтовый двойник `trimActiveRunTail`. Иначе хвост прогона
обрезался бы посередине: сегменты выше перебивки остались бы без модели и без плашек вызовов
навсегда, а окно сжатия открывалось бы на ответе к вопросу, который сжатие только что унесло в
сводку. Единственное исключение — `unansweredUserMessage`: для «Повторить» такой ряд настоящий
вопрос, и это то, что спасает сообщение при упавшем прогоне.

**Настройки едут из очереди.** `model`/`mode`/`project` запоминаются на приёме как есть и
резолвятся только когда по очереди пойдёт прогон (`RunOptionsResolver`): сообщение писали при этих
настройках. Переключение селектора после отправки на него не влияет, а если оно означает смену
проекта — follow-up прогон поставит маркер смены на этом вопросе, как на любом другом.

**Отвечает не всякий прогон.** Follow-up стартует **только** из терминальной обработки успешно
завершённого прогона. Остановленный и упавший доставляют сообщение, но нового не запускают:
остановку нажимают, чтобы генерация прекратилась, а ошибка повторилась бы. Две доставки со стороны —
приём и восстановление на старте — не отвечают вовсе: чем кончился прогон, им уже не видно (в
реестре его нет), а отвечать всем подряд значило бы запускать генерацию после «Стоп». Сообщение при
этом становится последним вопросом истории — тем самым состоянием, где чат предлагает «Повторить».

### 4. ChatEventService и ConversationHub — SSE event channel

**ChatEventService** — in-memory pub/sub поверх `ConversationHub`:

- **`subscribe(conversationId, fromSeq)`** — создаёт/находит хаб, подписывает `SseEmitter` с replay пропущенных событий. Таймаут эмиттера — `kb.chat.timeout.sse` (по умолчанию 30 минут)
- **`publish(conversationId, type, runId, clientMsgId, payload)`** — публикует событие всем подписчикам уже существующего хаба; хаба нет — событие пропадает. Заводят хаб ровно двое: подписка вкладки и `startRun`. Хаб, заведённый публикацией, закрыть было бы некому (закрывают его уход последнего подписчика и `endRun`), а событие прогона застаёт хаб закрытым ровно тогда, когда опоздало — прогона уже нет
- **`startRun`/`endRun`** — управление жизненным циклом прогона в хабе
- **`sendHeartbeats()`** — периодические keep-alive, чтобы прокси не рвали простаивающее соединение
- **`closeIfIdle()` / `closeAll()`** — выгрузка простаивающего хаба и гашение всех при shutdown

**ConversationHub** — канал одного чата:

- **Лог событий** (`eventLog`) — хранит события только активного прогона, очищается при старте и завершении; длина ограничена (2000 событий): у прогона их столько же, сколько токенов в ответе, а конца у прогона может и не наступить
- **Подписчики** (`subscribers`) — `SseEmitter` всех открытых вкладок
- **Replay** — при подключении с `fromSeq` реплеятся все события с `seq > fromSeq`. Если что-то из них уже вытеснено из лога, вкладке первым уходит `REPLAY_GAP`: показанный ею ответ заведомо с дырой, и она перечитывает историю, когда прогон закончится
- **Курсор из чужой нумерации** — `seq` сквозной внутри хаба, но хаб живёт меньше вкладки: простаивающий выгружается из реестра, и перезапуск приложения он тем более не переживает, а новый начинает счёт заново. Курсор больше всего, что этот хаб публиковал, поэтому не принимается вовсе (иначе он отрезал бы весь реплей, и вкладка, переподключившаяся посреди сжатия, увидела бы только готовый результат — ни `COMPACT_STARTED`, ни таймера). Лог реплеится целиком, а вместе с ним уходит `REPLAY_GAP`: часть реплея вкладка могла применить и вживую. Курсор чинит сам `REPLAY_GAP`: его `seq` — то значение, с которого продолжится реплей, и вкладка ставит курсор ровно туда (не «не ниже», а именно туда). Иначе чужой курсор пережил бы весь прогон, и каждый обрыв связи приносил бы полный реплей поверх уже собранного пузыря, задваивая ответ
- **Потокобезопасность** — `ReentrantLock` (не `synchronized`, чтобы избежать pinning на виртуальных потоках)
- **Закрытие** — `closed` флаг предотвращает гонку «выгрузка ↔ новая подписка»

**ChatEvent** — запись одного события:

| Поле | Тип | Описание |
|---|---|---|
| `seq` | long | Монотонный номер (точка дозагрузки) |
| `type` | ChatEventType | Тип события |
| `runId` | String | К какому прогону относится |
| `clientMsgId` | String | ID клиента-инициатора (защита от задвоения) |
| `payload` | Object | Полезная нагрузка |

**ChatEventType:**

| Тип | Payload | Когда |
|---|---|---|
| `MESSAGE_QUEUED` | `QueuedMessagePayload` | Сообщение принято в очередь идущего прогона (см. §3.3) — ряда истории у него ещё нет |
| `USER_MESSAGE` | `UserMessagePayload` | Эхо сообщения для других вкладок (`id`, `text`, `createdAt`). `interjection: true` — доставлено внутрь прогона, а не открывает новый ход |
| `RUN_STARTED` | `{ model }` | Начало генерации. Модель едет с событием, чтобы подпись под ответом появлялась сразу и во всех вкладках, а не только после перезагрузки |
| `STREAM` | `StreamMessage` | Чанк текста |
| `TOOL_CALL` | `ToolCallMessage` | Обновление вызова инструмента |
| `TOOL_CALLS` | `ToolCallsMessage` | Итоговый список вызовов сегмента |
| `RUN_USAGE` | `RunTokenUsage` | Токены прогона к этому моменту — состояние, а не добавка: каждое следующее событие заменяет предыдущее целиком. Эндпоинт без поддержки `stream_options.include_usage` не присылает его ни разу, и это отличается от нуля (см. §6.4) |
| `RUN_DONE` | — | Успешное завершение |
| `RUN_STOPPED` | — | Остановлена пользователем |
| `RUN_ERROR` | `{ message }` | Прервана ошибкой |
| `REPLAY_GAP` | — | Реплей неполон: часть событий прогона вытеснена из лога хаба. Только той вкладке, которой выброшенное предназначалось, и перед самим реплеем |
| `CHAT_DELETED` | — | Чат удалён (в т.ч. из другой вкладки) — вкладки закрывают его |
| `GIT_COMMAND` | `GitCommandPayload` | Пользователь выполнил git-команду из этого чата. Репозиторий сдвинулся для всех вкладок сразу, поэтому та, что команду не запускала, обязана показать и новый ряд истории, и новое состояние ветки |

### 5. ChatRuntimeMonitor и ChatRuntimeShutdown

**ChatRuntimeMonitor** — временный мониторинг утечек: периодически логирует размеры in-memory реестров (`eventHubs`, `activeRuns`, `claimedChats`). Интервал: `kb.chat.monitor-interval-ms` (по умолчанию 60000). Значение ≤ 0 отключает мониторинг.

**ChatRuntimeShutdown** — гашение рантайма при остановке приложения (слушает `ContextClosedEvent`, то есть срабатывает ДО graceful shutdown Tomcat):

1. `ChatRunService.stopAll()` — все активные прогоны отменяются как обычный стоп: `dispose()` → `CANCEL` → частичное сохранение с маркером `[stopped]` → событие `RUN_STOPPED` уходит ещё живым подписчикам
2. `awaitQuiescence(kb.chat.shutdown-grace-ms)` — ожидание, пока терминальная обработка допишет в БД: оборванный ответ и доставку очереди (по умолчанию 5000 мс; пул соединений закроется сразу после shutdown). Ждём **безусловно**, даже когда останавливать было некого: прогон, покинувший реестр за миг до остановки, в `stopAll()` не попал, а дописывает до сих пор
3. `ChatEventService.closeAll()` — все `SseEmitter` завершаются, реестр хабов очищается

Зачем: подписка вкладки на `GET /events` — долгоживущий async-запрос. Пока эмиттер не завершён, Tomcat считает запрос активным, а в Spring Boot 4 graceful shutdown включён по умолчанию — одна открытая вкладка задерживала остановку на все 30 с (`spring.lifecycle.timeout-per-shutdown-phase`), после чего соединение всё равно обрывалось (`Graceful shutdown aborted with one or more requests still active`). Вкладки видят обрыв потока и переподключаются с backoff уже к поднявшемуся инстансу, дозагружая пропущенное по `fromSeq`.

### 6. ChatClient и ChatConfig

`ChatConfig` — центральная конфигурация чата. Создаёт бины:

#### 6.1 ChatMemory

Реализация своя — `ChatHistoryMemory` (`@Service` в `service/chat/memory`), тонкая обёртка над `ChatHistoryService`:

```java
get(id)   -> history.promptMessages(id)   // окно, которое подставит advisor памяти
add(id, m)-> history.append(id, m)        // только дозапись, без чтения истории
clear(id) -> history.delete(id)
```

Оконной памяти Spring AI (`MessageWindowChatMemory` поверх `ChatMemoryRepository`) здесь нет, и заводить её обратно не стоит по двум причинам.

- **Окна на записи не существует.** Сколько истории уедет в модель, решает `SummarizeService`: помеченные `summarized` сообщения выпадают из `promptRows`, а пороги живут в `kb.chat.summarize.*`. Оконная память резала бы список ещё и на записи, по собственному счётчику сообщений, — числу, которое к этому решению отношения не имеет. В панели «Настройки → Модели» его поэтому и не показывали: лимит контекста читался бы из него неправильно.
- **`add` ничего не читает.** Advisor памяти зовёт его дважды за итерацию tool-цикла, и оконной памяти на каждый такой вызов нужна вся история целиком — склеить её с новыми сообщениями и отдать хранилищу обратно. Для append-only хранилища это чистая трата: позицию нового ряда `append` узнаёт одним запросом за максимумом. Итого на итерацию остаётся одно чтение окна — то, что действительно уходит в промпт.

#### 6.2 chatRunExecutor

```java
@Bean(destroyMethod = "shutdown")
public ExecutorService chatRunExecutor() {
    return new DelegatingSecurityContextExecutorService(
            Executors.newVirtualThreadPerTaskExecutor());
}
```

Виртуальные потоки + перенос `SecurityContext` на worker-поток.

#### 6.3 ChatClient и advisor-цепочка

- **ChatModel** — OpenAI-совместимая модель
- **System Prompt** — `classpath:prompt/sys.md` с плейсхолдером `{mode_instructions}`
- **Advisor-цепочка** (снаружи внутрь, по возрастанию `getOrder()`):

| Advisor | Порядок | Роль |
|---|---|---|
| `ToolCallingAdvisor` | `DEFAULT_ORDER` | Ведёт tool-цикл. Внутренняя история **отключена** (`disableInternalConversationHistory`): в каждой итерации промпт несёт только `[system, последний tool-ответ]`, остальной контекст перечитывается из `ChatMemory`. Это и есть режим Spring AI, при котором каждый сегмент сохраняется отдельным сообщением |
| `MessageChatMemoryAdvisor` | `+100` | **Внутри** цикла: `before()` подставляет историю и дописывает новое user/tool-сообщение в хранилище, `after()` сохраняет ассистентское сообщение каждой итерации — включая промежуточные сегменты с `tool_calls`. Требует `ChatMemory`, умеющей round-trip tool-сообщений (`ChatHistoryMemory`: `chat_message.tool_data`) |
| `TokenUsageAdvisor` | `LOWEST_PRECEDENCE` | Внутри цикла: замеряет каждое обращение к модели и шлёт `RUN_USAGE`. Внутри — обязательно: чанк с usage итерации цикл из downstream-потока отфильтровывает, снаружи виден был бы в лучшем случае замер последней итерации (см. §6.4) |
| `MessageLoggingAdvisor` | `LOWEST_PRECEDENCE` | Внутри цикла, самый внутренний: DEBUG-логирование фактического списка сообщений, уходящего в модель. Выключен по умолчанию |

**ToolCallbacks** — все функции оборачиваются в `RecordingToolCallback`:

| Функция | Условие подключения |
|---|---|
| `TopicFunction` | всегда — авто-именование чата, id/имя пользователя, дата-время |
| `MessageLookupFunction` | всегда — поиск исходных сообщений |
| `DocumentFunction` | всегда — работа с документами базы знаний |
| `GitFunction` | всегда — чтение Git-репозитория |
| `AttachmentFunction` | всегда — работа с вложениями |
| `SearchAgentFunction` | `kb.search.subagent.enabled=true` |
| `GitEditFunction` | проект принимает запись: `kb.projects[].edit-enabled` **и** рабочее дерево доступно на запись |
| MCP-инструменты | `kb.mcp.enabled=true` (внешние серверы из `spring.ai.mcp.client.*`) |

Оба условных бина отсутствуют целиком, когда выключены, — модель не видит инструментов, которые могли бы только упасть. У `gitEditFunction` вторая проверка нужна для read-only монтирования: при `edit-enabled=true` и недоступном на запись дереве бин возвращает `null` и пишет предупреждение в лог.

#### 6.4 Токены прогона (TokenUsageAdvisor / RunScope)

Ответ с инструментами — это несколько обращений к модели подряд, и наверх из них собирается не
одно число, а три.

**Почему advisor, а не подписчик стрима.** Usage итерации несёт агрегированный чанк с
`finishReason=TOOL_CALLS`, а `ToolCallingAdvisor` отфильтровывает его из downstream-потока —
`ChatRunService.onNext` увидел бы в лучшем случае замер последней итерации. `TokenUsageAdvisor`
стоит внутри цикла и видит сырой поток каждого обращения.
Границы обращений достаются даром: `adviseStream` цикл вызывает заново на каждой итерации,
поэтому замер итерации — обычная локальная переменная метода.

**Замеры одного обращения сворачиваются по-полевым максимумом** (см. `TokenUsage`), потому что
провайдеры отдают usage по-разному: OpenAI шлёт его единственным финальным чанком, Anthropic —
нарастающим итогом в каждом, часть прокси разносит `prompt` и `completion` по разным чанкам.
Максимум верен во всех трёх случаях; «первый непустой» терял бы `completion`, «последний
непустой» — `prompt`.

**Из обращений итог собирается тремя разными правилами** (см. `RunTokenUsage`), и это главное
место всей фичи. Сумма по обращениям — это total input, но как ответ на вопрос «сколько заняли
токены» бесполезная: `prompt` каждого следующего обращения включает предыдущее целиком, поэтому
сумма растёт квадратично от числа вызовов инструментов, а повторная часть вдобавок тарифицируется
по ставке кэша. Поэтому сумма ушла в расширенную статистику, а наверх вынесены три числа, каждое
из которых считает своё:

| Число | Правило | Что означает |
|---|---|---|
| `contextTokens` | `prompt` последнего обращения + его `completion` | Сколько занято контекста после ответа. Именно последнего: `prompt` каждого следующего обращения включает предыдущее целиком, так что последний и есть весь разговор, посчитанный один раз |
| `basePromptTokens` | `prompt` первого обращения | С чего прогон начал. У первого прогона чата это системная часть контекста: системный промпт со схемами инструментов плюс сам вопрос, то есть всё занятое ещё до разговора. Отдельным числом, потому что из остальных полей его не достать — выход последнего обращения в них не отделён от суммы по прогону |
| `toolTokens` | `prompt` последнего − `prompt` первого | Насколько прогон нарастил контекст. Разность съедает общую часть, оставляя ровно дописанное вызовами инструментов и ответами на них; у прогона без инструментов — ноль |
| `outputTokens` | Сумма `completion` по обращениям | Сколько модель сгенерировала. Здесь именно сумма: выход каждого обращения свой и в чужой `prompt` входит только один раз |
| `promptTokens` · `cacheReadTokens` · `cacheWriteTokens` · `modelCalls` | Суммы | Расширенная статистика: total input, cache read/write и число обращений — без них разрыв между занятым контекстом и суммарным входом необъясним. В интерфейсе они так и названы, провайдерскими терминами: «оплачено» звучало бы как счёт, которого приложение не выставляет |

На роль первого и последнего годится только замер с непустым `prompt`: провайдер вправе прислать
по ходу обращения чанк с одним лишь выходом, и такой замер, назначенный последним, обрушил бы
`contextTokens` до размера ответа, а назначенный первым — раздул бы `toolTokens` до всего
контекста. В суммы он при этом входит — выход в нём настоящий.

**Итог живёт в области прогона** (`RunScope`) — заводит её `ChatRunService.start`, снимает с
учёта терминальная обработка (`onTerminal`, строго до доставки очереди сообщений; размер реестра
печатает `ChatRuntimeMonitor`, в простое он обязан быть нулём).
Считаются только заведённые владельцем прогоны: область по чужому `runId` закрыть было бы
некому, поэтому advisor ничего не создаёт, а только ищет — не нашёл значит прогона нет.

**`stream_options.include_usage` обязателен.** Без него OpenAI-совместимый эндпоинт в стриме usage
не присылает вовсе, поэтому `ChatRunService` ставит опции запроса всегда, а не только под явно
выбранную модель. Шлюз, который поля не понимает, выключают точечно —
`kb.chat.models[].stream-usage: false`; его модели тогда просто остаются без цифры.

**Чего в цифре нет.** Обращения суб-агента (`searchCodebase`) и сжатия контекста идут мимо этой
advisor-цепочки — они строят свой `ChatClient` / работают с `OpenAiChatModel` напрямую, — поэтому
в итог прогона не попадают. Цифра под ответом — это токены **модели чата**, так она и подписана.

Суб-агент при этом считает себя сам, и **тем же правилом**: `SearchAgentService` копит обращения в
`RunTokenUsage.Tally` (общий на оба места — иначе одна и та же работа в двух местах интерфейса
называлась бы разными числами) и кладёт итог вместе с id своей модели в мету вызова
(`SearchAgentResult.getResultMeta`), откуда их показывают детали вызова. Складывать их с итогом
прогона нельзя: у суб-агента своя модель (`kb.search.subagent.model-id`) и свой тариф, а сумма по двум
разным тарифам — число, из которого уже ничего не вычислить.

Модели эти числа не показывают: `model` и `usage` в `SearchAgentResult` помечены `@JsonIgnore` —
как и `durationMs` до них. Увидев в результате инструмента цену собственного поиска, ассистент
начнёт про неё рассуждать в ответе, а вопрос был не про неё.

**Итог оседает в истории.** По завершении прогона `ChatHistoryService.markRunResult` кладёт его в
мету **последнего** ASSISTANT-ряда прогона (`ChatMessageMeta.usage`, колонка `chat_message.meta` —
JSON, миграции не нужно) и отдаёт фронту полем `ChatMessage.usage`. Одному ряду, а не каждому
сегменту: числа относятся к прогону целиком, и копия на каждом заставила бы читающего выбирать
между одинаковыми, а сумма по ним была бы просто неправдой. Неизмеренный прогон (`isEmpty`) не
помечается вовсе — `null` в мете значит «не измерено», и записанный вместо него ноль фронт показал
бы как «контекст пуст».

Отсюда переживают перезагрузку и плашка под ответом, и **счётчик занятого контекста в шапке чата**:
фронт ищет с конца ленты первый ответ с замером (`contextUsageOf`) — суммировать нечего, свежий
замер и есть весь разговор. Поиск обрывает любая плашка сжатия: замер выше неё описывает историю,
часть которой модели больше не едет.

Что отвечает дальше, решает вид сжатия (`CompactMeta.kind`). После **полного** (`/compact`) —
оценка, о ней ниже. После **фоновой суммаризации** (`SUMMARIZE`) — никто: сводка заменила только
начало истории, под плашкой остался живой хвост, и его размер ниоткуда не известен. Пустой счётчик
здесь честнее числа, завышенного на весь сжатый кусок; точное приезжает с первым же ответом.

Оценка — единственное во всей статистике число, которое не замерено:
системная часть плюс документ, который написала модель (выход раунда сжатия, он же теперь весь
разговор). Замерить его некому — провайдер меряет запросы, а между сжатием и следующим вопросом
запросов нет. Мимо оценки проходят обёртка сводки, первый вопрос чата (он входит в системную
часть) и то, что токенизация склейки не равна сумме токенизаций частей, — поэтому число получает
«~» и в счётчике, и во вкладке, а подсказка объясняет, почему оно приблизительное. Точное значение
приезжает само, с первым же ответом после сжатия, и оценку вытесняет. Оценивать не из чего (лента
загружена не с начала, раунд не измерен) — счётчика нет, как и раньше.

**Где какие числа.** Под ответом и в шапке стоит по одному короткому числу — занятому контексту, — а
его подсказка отвечает про этот прогон тремя строками: сколько занято после него, сколько нового
пришлось обработать (`promptTokens − cacheReadTokens`, то есть вход мимо кэша) и сколько
сгенерировано. Остальное — вкладка «Usage» правой панели (`ChatUsage`, `?right=usage`), в разрезе
провайдерского счёта: Context · системная часть · Input (Cache miss) · Input (Cache hit) · Output ·
Total · обращений к модели. Раунды сжатия — и `/compact`, и фоновая суммаризация — входят в итоги
наравне с ответами: их плашки несут такой же замер. Разрез именно такой, чтобы вкладка сверялась с биллингом провайдера
построчно — других способов узнать, что приложение считает верно, у пользователя нет. Своей
вкладкой, а не хвостом «Инфо»: набор читают как одно целое, а среди названия, дат и id он терялся. Складывается по прогонам
всё, кроме контекста и системной части: первый берётся у последнего прогона, вторая — у первого.

**Чего счётчик всё же не видит.** Он показывает заполнение на момент последнего ответа: заданный
следующий вопрос его увеличит, и до следующего ответа это в цифре не отразится. Фоновая
суммаризация (`SummarizeService.trySummarize`, идёт после каждого прогона) в цифре тоже не
отразится, но и старое число за собой не оставит: её плашка счётчик обнуляет — см. выше.

**Пока прогон идёт**, над полем ввода стоит строка `RunStatus`: таймер и прирост input за этот
ответ — поле при прогоне не блокируется (сообщение встаёт в очередь), и строка объясняет пишущему,
чем чат занят. Прирост считает фронт (`runInputGrowth`): живой снимок `RUN_USAGE` минус контекст
прошлого измеренного прогона — сюда попадает и вопрос с вложениями, и всё, что дочитали
инструменты; когда «до» неизвестно (неизмеренная история, плашка сжатия), остаётся нижняя
граница — `toolTokens` самого прогона. Якорь таймера — момент, когда вкладка узнала о прогоне
(`chat.runStartedAt`, по её собственным часам): его ставит и ответ на запуск (`POST /runs`,
`POST /compact`), и событие старта — что придёт первым, а уже поставленный якорь не сдвигается,
иначе реплей или отставшее событие отматывали бы отсчёт назад. Вкладка, открывшая чат посреди
генерации, ставит его по `elapsedMs` из `GET /runs/active`: наружу уходит длительность, а не момент старта, поэтому
перекос часов клиента и сервера отсчёт не портит. У операции (`kind=OPERATION`) прироста нет —
считать его не по чему, — а таймер идёт: сжатие живёт дольше среднего ответа, и без отсчёта плашка
«сжимаю…» неотличима от зависшей. Длительность операции помнит заявка на чат
(`ConversationSlots.Hold`), потому что области прогона у неё нет.

### 7. Режимы ассистента (ChatModeProperties / ChatModeService)

Режим — готовый фрагмент инструкций, подставляемый в системный промпт через плейсхолдер `{mode_instructions}`. Это параллель выбору модели: пользователь переключает его в композере чата, значение хранится в `chat_topic.mode`.

**Конфигурация** (`kb.chat.modes`):

```yaml
kb:
  chat:
    modes:
      - id: analytic
        label: Аналитик
        prompt: classpath:prompt/mode-analytic.md
      - id: developer
        label: Разработчик
        prompt: classpath:prompt/mode-developer.md
      - id: tester
        label: Тестировщик
        prompt: classpath:prompt/mode-tester.md
```

- `ChatModeService` читает тексты режимов из classpath **один раз при старте** и отдаёт фрагмент по id
- Наружу (`GET /api/chats/modes`) отдаётся только `{ id, label }` — сам текст промпта остаётся на бэке
- **«Без режима»** — валидное состояние по умолчанию: `instructionsFor(null)` возвращает пустую строку. Плейсхолдер всё равно должен получить значение, иначе рендер шаблона упадёт
- Разрешение режима зеркалит разрешение модели: поле `mode` в теле запроса → сохранённый `chat_topic.mode` → `null`. Неизвестный id → `400 Bad Request`; режим, убранный из конфига, отфильтровывается через `isAllowed`

### 8. ChatHistoryService и ToolCallService — персистентность сообщений и tool-данные

Хранение истории разложено на четыре класса в `service/chat/memory`, по границам ответственности:

| Класс | Отвечает за |
|---|---|
| `ChatHistoryMemory` | Шов Spring AI: `ChatMemory` поверх истории (§6.1) |
| `ChatHistoryService` | Само сообщение: окно для модели, страницы для UI, дозапись, ремонт хвоста |
| `ToolCallService` | Вызовы инструментов поверх сообщений: `tool_call_index`, меты плашек, детали для модалки |
| `ToolCallEventPublisher` | Live-события `TOOL_CALL` по только что сохранённым рядам |

Поиск по чатам живёт отдельно — `service/chat/topic/ChatSearchService` (§13).

**Таблица `chat_message`** (подробнее в [Модели данных — Чат](модели-данных/чат.md)):

| Поле | Тип | Описание |
|---|---|---|
| `id` | `long` | Первичный ключ |
| `conversation_id` | `String` | ID беседы |
| `content` | `String` | Текст сообщения |
| `type` | `MessageType` | USER, ASSISTANT, SYSTEM, TOOL |
| `position` | `long` | Порядковый номер в беседе |
| `summarized` / `summary` | `boolean` | Суммаризировано ли · является ли само сообщение суммаризацией |
| `tool_data` | `String` (JSON) | **Протокольные** tool-данные: вызовы ассистента и TOOL-ответы (`ToolData`, `ToolDataToJsonConverter`) |
| `meta` | `String` (JSON) | **UI-метаданные**: `ChatMessageMeta` c `ToolInvocationMeta`, `runId`, флагом `toolCalls`, принадлежностью репозиторию (`project` / `projectSwitchFrom`, а на сводке — `visitedProjects`) и моделью ответа |
| `created_at` | `LocalDateTime` | Время создания |

> **Не смешивать `tool_data` и `meta`.** `tool_data` — то, что нужно протоколу LLM, чтобы воспроизвести историю; `meta` — то, что рисует фронтенд. Отдельной таблицы tool-вызовов нет.

**Индекс `tool_call_index`** (`ToolCallIndexEntity`) отображает `conversationId + callId` → id сообщений с полными деталями: сегмент ASSISTANT, выдавший вызов, и строка TOOL-ответа, когда та появится. Индекс заполняется **в момент сохранения** (`ChatHistoryService.append` → `ToolCallService.index`), а не фоновой задачей.

**Ключевые методы `ChatHistoryService`:**

| Метод | Назначение |
|---|---|
| `saveUserMessage(conversationId, text, contextItems)` | Пишет вопрос пользователя до обращения к модели и возвращает сохранённый ряд. Приложенный контекст уходит в `meta` той же вставкой. Транзакция обязана закрыться до старта стрима: advisor памяти читает историю на другом потоке и незакоммиченную строку не увидит |
| `unansweredUserMessage(conversationId)` | Последний ряд чата, если это `USER` — единственное состояние, из которого допустим повтор прогона (§3.2). Появился `ASSISTANT` или `TOOL` — пусто |
| `append(conversationId, messages)` | Дозапись новых сообщений (уже персистнутые `IMessage` отфильтровываются), позиции — от максимума по чату; пишет `tool_data`, зовёт `ToolCallService.index` и `ToolCallEventPublisher.publish` |
| `promptMessages(conversationId)` | Несуммаризированные сообщения — то, что уходит в модель. К вопросу с приложенным контекстом дописывается блок `<attached-context>` (§3.1) |
| `promptRows(conversationId)` | То же окно, но парами «ряд + его текст в промпте» — единственный источник правды о том, что видит модель (вход `SummarizeWindow`) |
| `displayMessages(conversationId)` | Сообщения для отображения пользователю |
| `findLatestPage` / `findPageBefore` | Курсорная keyset-пагинация (`Page` с `hasMore` и `oldestCursor`) |
| `markRunResult(conversationId, runId, model, usage, toolCalls)` | Одной записью проставляет ответам хода плашки вызовов, модель прогона и — последнему из них — его токены (§6.4). Возвращает проставленные плашки для события `TOOL_CALLS`; см. врезку ниже |
| `repairDanglingToolCalls` | Достраивает `assistant.tool_calls` без TOOL-ответа (иначе модель ответит `400`) и индексирует достроенный ответ |

**Ключевые методы `ToolCallService`:**

| Метод | Назначение |
|---|---|
| `index(conversationId, saved)` | Строки `tool_call_index` по `tool_data` только что сохранённых рядов |
| `findToolCallDetail(conversationId, callId)` | Полные детали вызова — **простой lookup через индекс**, без позиционной арифметики по истории |
| `invocationsFor(entity, page)` | Синтезирует меты из `tool_data` для сегментов без `meta.invocations` (оборванные/старые прогоны) |
| `runInvocations(segments, toolCalls)` | Чистая раскладка вызовов прогона по его сегментам: `callId` в метах, вырезание скрытых инструментов. Пишет их `markRunResult` |
| `hasDetails(toolName)` | Сохраняются ли детали вызова этого инструмента в БД |

**Итог прогона пишут одной записью.** В `ChatMemory.add` не приходит ни модель, ни токены, ни
вызовы — advisor памяти передаёт только сообщения, — поэтому `markRunResult` проходит по рядам хода
уже после прогона: дописывает ASSISTANT-рядам плашки вызовов, `meta.model` (и `runId`), а
последнему из них ещё и `meta.usage` (§6.4). Именно одной записью, а не тремя: плашки ищут
необогащённые сегменты по `meta == null`, поэтому порознь это была бы пара с негласным порядком —
модель, проставленная первой, спрятала бы от плашек ряды того же прогона, и вызовы инструментов не
показались бы никогда. Ряды оборванных прогонов, лежащие в том же хвосте, уже помечены своей
моделью и второй раз не переписываются — под ответом стоит та модель, что его написала. Ход
определяется правилом `ChatHistoryService.tailAfterLastUser`, общим с окном сжатия.

**`callIndex` живых событий — счётчик прогона, а не скан истории.** Нумерация живёт в области прогона (`RunScope`) и умирает вместе с ней, поэтому следующий прогон начинает с нуля сам собой — ровно так же считает `ToolInvocationCollector`, из которого приходят итоговые меты, и по этому номеру фронт склеивает живую плашку с итоговой. Восстанавливать номер сканом хвоста истории нельзя: после повтора упавшего прогона в хвосте лежат ещё и его сегменты, которых счётчик коллектора не видел.

> Метода `saveToolCalls()` больше нет. Раньше он писал в конце прогона одно SYSTEM-сообщение-«крошку» с JSON всех вызовов; теперь вызовы приходят вместе с сегментами. «Крошки» старых чатов по-прежнему читаются (флаг `meta.toolCalls`) и на фронте прикрепляются к предыдущему ответу ассистента.

### 9. ChatTopicEntity — топик чата

`ChatTopicEntity` — сущность, представляющая одну беседу. Таблица `chat_topic`:

| Поле | Тип | Описание |
|---|---|---|
| `conversation_id` | `String` (PK) | UUID беседы |
| `user` | `String` | Владелец |
| `user_topic` | `String` | Название, заданное пользователем вручную (`PUT .../topic`) |
| `ai_topic` | `String` | Название, предложенное ИИ (`recordChatInsights`) |
| `model` | `String` | ID выбранной модели (null = дефолтная) |
| `mode` | `String` | ID выбранного режима (null = без режима) |
| `created_at` / `updated_at` | `LocalDateTime` | Аудит Spring Data |

**Два названия вместо флага.** Раньше была одна колонка `topic` плюс булев `is_user`, и авто-имя от ИИ затирало пользовательское. Теперь это разные поля, а `getDisplayTopic()` отдаёт `userTopic`, если он есть, иначе `aiTopic` — ИИ может предлагать тему сколько угодно, ручное название от этого не страдает. На вкладке «Инфо» правой панели видны оба.

**Авто-именование:** `TopicFunction.recordChatInsights` — AI-инструмент, записывающий `ai_topic` на основе диалога.

```
POST /api/chats/{conversationId}/runs
    │
    ├── ChatRunService.start()
    │     ├── Атомарная заявка на чат (409 если уже идёт)
    │     ├── repairDanglingToolCalls()  ← строго до записи вопроса
    │     ├── saveUserMessage()          ← вопрос в БД, id известен
    │     │   (retry: вместо записи — unansweredUserMessage(), иначе 422)
    │     └── executor.execute(() -> run())
    │           ├── Публикация USER_MESSAGE (с id) + RUN_STARTED
    │           ├── chatClient.prompt().stream().chatResponse()  ← без .user(...)
    │           ├── onNext  → STREAM → ChatEventService.publish()
    │           ├── (advisor-цепочка сохраняет сегменты, TOOL_CALL шлёт запись истории)
    │           ├── onComplete → markRunResult + TOOL_CALLS + RUN_DONE + summarize
    │           └── doFinally → частичное сохранение + RUN_STOPPED/RUN_ERROR
    │
    └── Возвращает { "runId": "...", "messageId": 123 }

GET /api/chats/{conversationId}/events?fromSeq=0
    │
    └── ChatEventService.subscribe()
          ├── Replay пропущенных событий (seq > fromSeq)
          └── Живые события → SseEmitter.send()
```

**Типы SSE-сообщений (DTO):**

| DTO | Когда | Поля |
|---|---|---|
| `StreamMessage` | Каждый чанк текста | `message`, `finishReason` (или null) |
| `ToolCallMessage` | Начало/конец вызова инструмента | `toolCall` (ToolInvocation) |
| `ToolCallsMessage` | Завершение прогона | `toolCalls` (список ToolInvocationMeta) |
| `UserMessagePayload` | Эхо сообщения пользователя | `message`, `createdAt` |
| `ChatEvent` | Любое событие в канале | `seq`, `type`, `runId`, `clientMsgId`, `payload` |

### 11. RecordingToolCallback и ToolInvocationCollector

**RecordingToolCallback** — обёртка над каждым `ToolCallback`, которая:
1. Перехватывает вызов инструмента
2. Извлекает `ToolInvocationCollector` из `ToolContext`
3. Записывает `STARTED` → выполняет делегат → записывает `OK` или `ERROR`
4. Извлекает `resultMeta` через `ToolCallResultMetaProvider` (если результат его реализует)
5. Вычисляет `resultGist` самостоятельно (из `resultMeta` или через `CompactToolResultConverter`)
6. Фильтрует аргументы (только из белого списка `ALLOWED_INPUT_ARGUMENTS`)

**ToolInvocationCollector** — потокобезопасный коллектор (`CopyOnWriteArrayList`):
- `record(invocation)` — добавляет запись и отправляет в liveSink (SSE)
- `snapshot()` / `completedSnapshot()` — все вызовы · только завершённые (без STARTED)
- Колбэк «инструмент пошёл» — граница сегмента для буфера `ChatRunService` (см. §3)

**ToolInvocationMeta** — то, что уходит в БД и на фронт: `name`, `arguments`, `status`, `error`, `resultMeta`, `resultGist`, `hasDetails`, `callIndex` и **`callId`** — единственный ключ, нужный модалке деталей (`GET /tool-calls` находит `messageId`/`responseMessageId` сам, через `tool_call_index`). Поля с `null` у старых записей опускаются из JSON.

**ToolCallDetail** — ответ `GET /tool-calls`: `name`, `argumentsRaw`, `status`, `error`, `resultText`, `resultMeta`, `createdAt`. Собирается и на работающем вызове: ASSISTANT-сегмент с аргументами сохранён и проиндексирован до запуска инструмента, поэтому без меты и без TOOL-ответа деталь приходит со `status: STARTED` и пустым `resultText` (ответ без меты — оборванный прогон, там `OK`).

### 12. Суммаризация (SummarizeService)

`SummarizeService` автоматически сжимает длинные диалоги, чтобы не превысить контекстное окно
модели. Класс разделён надвое: сам сервис — только оркестрация (лок на беседу, вызов LLM, атомарный
персист), а вся арифметика живёт в `SummarizeWindow` — классе без side effects, который по строкам
истории отвечает «что сжимать, что оставить и стоит ли раунда».

**Живое окно делится на две группы, и это вся модель.**

**Группа 1 — живой хвост**, его не трогают. Насколько далеко назад он тянется, говорят три правила,
побеждает самое раннее: в хвосте не меньше `overlap-user-messages` вопросов, не меньше
`overlap-messages` сообщений любого рода, и хвост открывается целым ходом (ближайшим
USER-сообщением). Одного правила по числу сообщений мало: вопрос с длинным tool-марафоном вытеснил
бы в сводку последние вопросы пользователя. **Невыполнимое правило просто не применяется** —
удержать пять вопросов там, где их два, нельзя, значит оно молчит и границу задают остальные;
поэтому ни одному из трёх не нужна спасательная ветка. У выравнивания на целый ход есть ровно одно
исключение: если единственный вопрос окна — самое первое его сообщение, назад отступать некуда, и
граница остаётся там, где её поставило правило по числу сообщений. Хвост тогда открывается
серединой хода — это сознательный размен: иначе вопрос с бесконечным tool-марафоном не сжался бы
никогда.

**Группа 2 — всё, что старше**: срез этого раунда, сжимаемый целиком или никак. Стоит ли его сжимать,
спрашивают два порога, и хватает любого: в срезе набралось `message-count-threshold` сообщений или
он весит `token-threshold` токенов. Оба меряют **одно и то же — срез**, поэтому разойтись в том, на
что они срабатывают, не могут.

**Вес считает провайдер, а не эвристика.** Токены среза собираются из замеров прогонов
(`RunTokenUsage` в мете ответов), и собираются по прогону за раз: собственный рост каждого
(`contextTokens - basePromptTokens` — вызовы инструментов и ответ) плюс разрыв до предыдущего
(`basePromptTokens` этого минус `contextTokens` прошлого — вопрос со вложениями). Системная часть
входит в оба конца каждой разности и в них сокращается, так что остаётся ровно то, что раунд из
контекста уберёт.

Одной разностью между концами среза считать нельзя, и это не мелочь: в длинном чате история под
прогонами переписывается — каждая суммаризация меняет кусок окна на сводку, и прогоны по разные её
стороны меряли **разные истории**. Их разность отрицательная (после сжатия контекст резко меньше), и
одно такое место обнулило бы вес всего среза — то есть чат, который сжимали чаще всех, перестал бы
сжиматься вовсе. Слагаемые же измерены каждое внутри своей истории; переписывание видно по
отрицательному разрыву, он отбрасывается, и цена ему — один потерянный вопрос на каждое сжатие.
Смена модели посреди чата лечится тем же самым: токенизация у моделей своя, но каждое слагаемое
измерено одной из них целиком.

Замер на ряду **пользователя** в вес не идёт: там он бывает у одного случая — несостоявшегося
`/compact`, записанного на строку своей команды, — и описывает окно, которое тот раунд прочитал, а не
контекст чата (то же правило на фронте — `runUsage` в `tokenUsage.js`).

Рядом всегда считается прежняя оценка по символам (`chars-per-token`), и **побеждает больший из
двух**. Не «замер, если он есть»: покрывать срез целиком замеры не обязаны — у истории, записанной
версией без них, измерены только последние прогоны, и срез из сорока тяжёлых вопросов плюс один
короткий измеренный прогон весил бы по замеру полторы тысячи токенов, то есть порог не срабатывал бы
на этом чате вовсе. Смешивать источники в одном числе при этом нельзя: кусок весь замером либо весь
оценкой, а в логе видно, чем именно (`~N tokens (estimate)` против `N tokens`).

Вес **всего живого окна** (он только для лога) считается иначе, чем вес среза: замером это не сумма
слагаемых, а `contextTokens` последнего прогона. Системная часть со схемами инструментов уезжает
провайдеру с каждым запросом и в окно входит, а в срез — нет, сжатие её не трогает.

**Сводки в этой арифметике не участвуют.** Они уже сжатое прошлое: уезжают модели в каждом запросе и
передаются суммаризатору как контекст, но повторно не сжимаются и ни к одному порогу не
приплюсовываются.

**Принцип работы:**
1. После каждого ответа AI вызывается `trySummarize(conversationId)` — асинхронно, на virtual thread
2. Блокировка через `SummaryWriter.inConversation` (`Striped<Lock>`) — одна беседа не может
   сжиматься параллельно, ни двумя фоновыми раундами, ни фоновым и `/compact` (замок общий, см. §12)
3. `SummarizeWindow` делит живое окно на две группы, как описано выше
4. Если один из порогов достигнут — весь срез уходит на сжатие, существующие суммаризации
   загружаются как контекст — вместе с ещё не применёнными (`withParked`, см. «Применение сводки
   отложено»): сжатые ими ряды в срез не попадают
5. Если накоплено `summary-collapse-threshold` **применённых** суммаризаций — они схлопываются в
   одну мета-суммаризацию (при непустой очереди схлопывания не бывает)
6. LLM генерирует суммаризацию через отдельный `ChatClient` с промптом `prompt/summarizer.md` и
   своими опциями обращения (`kb.chat.summarize.model` · `reasoning-effort` · `thinking`, см. ниже)
7. Готовая сводка **паркуется** в конец очереди (`chat_pending_summary`), а разметку
   `summarized = true`, ряд сводки (`summary = true`) и плашку пишет уже её применение — оно ждёт
   своего повода, см. «Применение сводки отложено» ниже

**Обращение суммаризатора настраивается отдельно от чата** (`kb.chat.summarize.model`,
`reasoning-effort`, `thinking` — все три по умолчанию пусты, см.
[Конфигурация](конфигурация.md)). Модель, выбранная
пользователем в чате, раунда не касается вовсе: он идёт в фоне по срезу, которого никто не ждёт, —
поэтому и модель подешевле, и убавленные «размышления» здесь ничем не оплачиваются, а на выходе
всё равно пересказ материала, который у модели перед глазами. Опции кладутся поверх настроенных у
самой модели (`SummarizeService.callOptions`): не заданное в конфигурации остаётся как у чата.

**След проектов переживает сжатие отдельно от текста.** Маркеры смены стоят на вопросах, и вместе с
ними уехали бы в сводку — а вопрос «в каком репозитории читан файл из сообщения 40» задают и после.
Поэтому сводка несёт `meta.visitedProjects`: хронологические отрезки «сообщения с N по M прожиты
здесь» (`ProjectSpan`), собранные `ProjectTrace` из спанов предыдущей сводки и носителей своего
куска. Список накопительный, так что последняя сводка окна знает всю историю смен; отрезки закрыты
и описывают только сжатое — живой хвост считается на чтении и записанное не переписывает. Читает их
`ActiveProjectNotice`, печатая таймлайн в блоке `<active-project>`; `summarizer.md` при этом требует
блок **не** сохранять — в отличие от `<project-switched>`, он не факт о разговоре, а справка,
которая пересобирается перед каждым запросом.

В чатах, записанных до появления спанов, их проставляет разовый проход `ProjectStampBackfill` — тем
же `ProjectTrace`, что и обычная запись, поэтому у чтения остаётся одна форма ответа вместо трёх.
Проход опционален и по умолчанию выключен: он переписывает `meta` чужих сообщений вычислением, и
без каталога под снимок (`kb.chat.backfill.dump-path`, см. `конфигурация.md`) не запускается вовсе.
Чат без спанов это переживает — активный проект он назовёт по `chat_topic`, только без диапазонов.

**Формат сводки — разделы, а не сплошная проза.** `summarizer.md` требует фиксированный набор
секций (заголовки всегда по-английски, содержимое — на языке пользователя): `## Overview` —
проза на 80–500 слов, `## User requests`, `## Decisions`, `## Done`, `## Open`, `## Problems`,
`## Artifacts`. Пустая секция не выводится.

Особая среди них — `## User requests`: **один пункт на каждое USER-сообщение среза**, без
бюджета вовсе. Она отвечает на то, ради чего разделы и заведены — намерения пользователя не
должны сжиматься наравне с болтовнёй ассистента и трейсами инструментов. Код в пункте
сворачивается до `[code: 30 lines, SQL migration]`, вложение — до имени и id, лог — до одной
строки: сохраняется запрос, а не его содержимое.

`## Artifacts` и `## Open` тоже без бюджета — по фактам, не по счётчику: вложение или открытый
вопрос, выпавший ради лимита, назад не вернуть. У `## Decisions`, `## Done` и `## Problems`
бюджет не плоский потолок в число пунктов, а объём, оправданный материалом (ориентир — один пункт
на 3–4 сообщения среза); пункт может занимать несколько предложений, если решение или провал того
требует.

При схлопывании (`summary-collapse-threshold`) секции мержатся по отдельности, и `## User requests`
с `## Artifacts` переносятся пункт в пункт, без пересжатия — иначе на каждом коллапсе они теряли бы
часть, а потери копятся экспоненциально. Правило продублировано в `COLLAPSE_FOOTER`
(`SummarizeService`), потому что мета-суммаризация приходит модели отдельной инструкцией.

Формат держится на промпте: код сводку не разбирает и не валидирует, он только оборачивает её в
`<summary>` с диапазоном позиций. Слабая модель может отдать и прозу — история от этого не ломается,
теряется только структура.

**Целостность пар «ASSISTANT с tool_calls ↔ ответ инструмента»** держится не выравниванием границы, а
разметкой: `summarized` проставляется по позициям до первого **оставленного** сообщения, поэтому
граница не может встать между сегментом и его ответами, каким бы правилом она ни была выбрана.
Выравнивание на USER-сообщение — про то, что читает модель (хвост не должен открываться ответом на
невидимый вопрос), а не про протокол.

**Чего эта схема не обещает: потолка над живым окном.** Все три правила двигают границу только
назад, поэтому марафон инструментов внутри последних пяти вопросов остаётся живым целиком — и живое
окно на это время больше `token-threshold`. Заперто оно не навсегда: каждый следующий вопрос сдвигает
пятый-с-конца вперёд, и марафон уезжает в срез сам. Это осознанный размен на границу, которую можно
предсказать, не моделируя её в голове; оба края закреплены тестами
`aToolMarathonInsideTheLastFiveTurnsStaysLive` и `theMarathonIsCompressedOnceLaterQuestionsPushItOutOfTheTail`.

Порог по токенам заявлен **в токенах, а не в числе сообщений**, поэтому дробить контекст на большее
число сообщений, чтобы он казался дешевле, не выйдет: оценка берёт с каждого сообщения фиксированную
протокольную надбавку (`PER_MESSAGE_CHARS`, ~4 токена — роль и JSON-обвязка) сверх его текста и
tool-данных. Без неё пустая протокольная TOOL-строка стоила бы ровно ноль.

**Оценка меряет то, что реально уезжает модели, а не то, что лежит в БД.** Вес берётся с
`ChatHistoryService.promptRows` — с той же строки, из которой строится промпт. Разница не
косметическая: к вопросу с вложением при каждом чтении дописывается опись приложенного
(`ContextItemService`), в `chat_message.content` её нет, а длина сводки вложения ничем не ограничена
— считая сохранённую колонку, оценка не видела бы описи вовсе. Единственность источника закреплена
`PromptRowSourceOfTruthTest` (в том числе правило «опись — только у вопроса», §3.1: решает его одна
сборка ряда, а не каждая сторона сама), а цена ошибки — парой тестов в `SummarizeWindowTest`: одно и
то же окно переходит порог с описью и не переходит без неё.

**Раунд не проходит молча: он оставляет плашку и свой замер.** Запись общая с `/compact`
(`SummaryWriter.writeCompacted`): та же строка-плашка, тот же эндпоинт деталей, та же модалка со
сводкой — отличает их только `CompactMeta.kind` (`SUMMARIZE` против `COMPACT`). Молчать нельзя по
двум причинам сразу: пользователь иначе не узнаёт, что часть разговора модель больше не видит, а
счётчик контекста продолжает показывать замер прогона, который мерил уже несуществующую историю
(§9). В ленте плашка тоньше и без чисел экономии — фоновое сжатие никто не просил, и разговор оно не
прерывает; во что оно обошлось контексту, по его замеру не считается: раунд читал не контекст чата,
а пересказ сжимаемого куска своим промптом.

Замер раунда — тем же полем `meta.usage`, что и у ответа, и собран тем же `RunTokenUsage.Tally`
(`RoundUsageAdvisor`: своей области прогона у фоновой операции нет, а обращений у раунда бывает
несколько — у суммаризатора есть инструмент `MessageLookupFunction`). Без него суммаризация была бы
тратой чата мимо его же статистики — ровно та же дыра в `Total`, что и у неучтённого `/compact`.

**Тесты разложены по этой же границе.** `SummarizeWindowTest` бьёт прямо в `SummarizeWindow` — вся
арифметика проверяется без единого мока, потому что у класса нет side effects.
`SummarizeServiceTest` оставляет за собой только проводку: что раунд доходит до парковки готовой
сводки, а на пустом ответе модели не доходит. Что припаркованное потом попадает в историю и по
какому поводу — `PendingSummaryServiceTest`.

##### Применение сводки отложено (PendingSummaryService)

**Написать сводку и применить её — два разных решения, и второе про деньги.** Провайдер кэширует
промпт с первого байта: системное сообщение, схемы инструментов, история. Сжатие подменяет начало
истории, то есть обнуляет кэш **всего** чата — следующий запрос оплачивается целиком, по полной
цене за каждый токен несжатой части. На длинном разговоре это дороже, чем несколько лишних запросов
по несжатой истории. Поэтому раунд свой результат не применяет, а паркует в `chat_pending_summary`
(очередь на чат; единственный писатель и читатель — `PendingSummaryService`), и ждёт повода:

- **пауза** (`applyIfPaused`, порог `apply-after`) — обычный путь. Меряется от последнего ряда чата
  (`ChatMessageRepository.lastCreatedAt`): кэш протухает от последнего запроса, чем бы тот ни был.
  Зовётся перед сохранением нового вопроса — то есть ровно тогда, когда сжатая история впервые
  понадобится, и при этом пауза ещё измерима: следующий ряд не записан. Порог ставится чуть выше
  собственного времени жизни кэша у провайдера — тогда терять уже нечего;
- **размер контекста** (`applyIfOversized`, доля `apply-at-ratio` от окна модели) — ждать больше
  нельзя: разговор дорос до размера, на котором сам по себе дорог, и потерянный кэш стал меньшей
  половиной сделки. Проверяется по завершении прогона, по его `contextTokens`. Окно берётся у
  модели прогона (`kb.chat.default-model.context-tokens` / `kb.chat.models[].context-tokens`) —
  окна моделей различаются на порядок, и доля от чужого окна означала бы либо сжатие впустую, либо
  сжатие с опозданием. Модель, у которой окно не названо, порога не имеет вовсе и ждёт паузы; так
  же ведёт себя неизмеренный прогон — «неизвестно» это не ноль.

Пока сводка припаркована, сжатый ею кусок остаётся живым: модель видит его целиком. Раунды от этого
не останавливаются — следующий получает припаркованное **контекстом** и сжимает то, что накопилось
за ним (`SummarizeService.withParked` подставляет припаркованные сводки на место сжатых ими рядов —
ровно то окно, какое было бы после применения). Иначе один раз припарковавшийся чат не сжимался бы
до самой паузы, а на модели без названного окна — и вовсе до предела контекста. Сжать один и тот же
кусок дважды при этом невозможно: подменённые ряды в срез не попадают.

Отсюда и очередь: припаркованных сводок у чата бывает несколько, идущих подряд кусками. Применяются
они **все разом, по порядку и одной транзакцией** — остановка на середине оставила бы в промпте
живой кусок между двумя сжатыми. Плашка у каждой своя: у них разные куски и разные деньги.

Расти без предела очередь не может: `apply-at-queue` (по умолчанию 3) применяет её сразу после
парковки, без всякого другого повода. Отложенное сжатие промпт не укорачивает, и каждый следующий
раунд читает окно длиннее предыдущего — на этом числе оплата длины перевешивает кэш, который
применение обесценит. Для чата на модели без названного окна это вообще единственный предел, кроме
паузы: доле `apply-at-ratio` там не от чего считаться.

Схлопывания в метасводку (`summary-collapse-threshold`) пока очередь не пуста не бывает: метасводка
заменяет собой перечисленные ею сводки, а у припаркованной замена означала бы потерянный ряд — с ним
её плашку и деньги её раунда, которых больше нигде нет. Порог считает только применённые сводки:
той, которой в промпте ещё нет, он и не удлиняется.

Полное сжатие (`/compact` и авто-compact) припаркованные сводки **выбрасывает** (`discard`): оно
заменяет сводкой весь контекст, и отложенные описывали бы историю, которой в промпте больше нет.
Выбрасывает после удавшегося обращения к модели — упавший раунд очередь оставляет на месте — и
забирает при этом деньги их раундов себе на плашку (`CompactMeta.carried`): заплачено за них было,
а своего ряда у них после удаления нет, и молча потерянные, они разошлись бы со счётом провайдера
ровно на свою стоимость. На плашке это только деньги, без контекстных чисел
(`RunTokenUsage.spentTogether`): фронт складывает их в итог по чату и никогда не читает как
занятый контекст.

Каждый ряд очереди несёт всё, чем потом будут записаны оба его ряда: позиции и текст —
строке-сводке, числа и `meta.usage` — плашке, `meta.visitedProjects` — следу проектов. Пересчитать
это при применении не из чего: раунд, который читал и оплатил сжимаемый кусок, к тому времени давно
кончился.

Применение — та же `SummaryWriter.writeCompacted`, но замок берётся **без ожидания**
(`tryInConversation`): обе точки применения стоят на пути живого запроса, а раунд сжатия под тем же
замком держит обращение к модели. Повод придёт снова, а секунды ответа на нём терять не за что. От
двойной записи (пауза и предел контекста могут сойтись на одном чате) защищает заявка через
удаление: `claim(id) == 0` — строку забрал кто-то другой. Заявка лежит **внутри** той же
транзакции, что и запись: удаление, пережившее неудавшуюся запись, стёрло бы сводку насовсем —
писала её модель, и второй раз её никто не напишет, потому что сжатый кусок уже не живой. И само
применение **ничего не бросает наружу**: зовут его с путей начала и конца прогона, где упавшая
оптимизация цены не должна ни отказывать пользователю в вопросе, ни оставлять чат занятым.

Плашки применение рассылает событиями `COMPACT_APPLIED` (`CompactPayload`, без `runId` — прогона
здесь нет), по одному на плашку. Дописать их в конец ленты нельзя: время у плашки — время сжатого
куска, и место в ленте у неё в середине, там, где свёрнутое кончается. Открытая вкладка ищет это
место сама, по времени (`chatEventReducer`); плашку старше всей загруженной страницы она
пропускает — та приедет со своей страницей при прокрутке вверх. У фоновой суммаризации свёрнутый
кусок — начало разговора, поэтому в длинном чате её плашка чаще всего оказывается именно там, вне
загруженной страницы, и появляется только при прокрутке вверх.

Счётчик контекста в шапке применение обнуляет, а не пересчитывает. Замеры, стоящие в ленте ЗА
плашкой, сделаны до применения — они мерили историю, начало которой сводка уже заменила собой, — и
отличает их не место в ленте, а id ряда: плашка записана в момент применения, то есть позже всего,
что к тому моменту в чате было (`tokenUsage.contextUsageOf`). Пустой счётчик здесь честнее числа,
завышенного на весь свёрнутый кусок; точное придёт с первым же ответом.

**SummarizeProperties** (`kb.chat.summarize.*`):

| Параметр | Значение по умолчанию | Описание |
|---|---|---|
| `token-threshold` | 30000 | Вес **сжимаемого среза**, при котором стартует раунд (больший из замера по прогонам и оценки) |
| `message-count-threshold` | 30 | Число сообщений в срезе, при котором стартует раунд (второй порог той же пары, хватает любого) |

#### Сжатие по команде — `/compact` (CompactService)

То же «заменить историю сводкой», но по просьбе пользователя и с двумя принципиальными отличиями
от фоновой суммаризации.

**Историю никто не пересказывает.** Суммаризатор рендерит срез в текст и режет результаты
инструментов до `resultGist` — коротких превью. `CompactService` отдаёт модели окно как есть, теми
же `Message`, которыми живёт чат: протокольные `tool_calls` с полными аргументами и TOOL-строки с
полными результатами внутри. Отсюда и отдельный промпт `prompt/compactor.md`: у модели на входе не
пересказ, а сам разговор, ссылаться на `[msg:N]` не на что (позиций в протокольных сообщениях нет),
а детализация требуется выше — живого хвоста после сжатия не останется, и сводка становится
единственной памятью разговора.

**Сжимается всё живое окно ДО команды**, включая уже накопленные сводки: ни порогов, ни живого
хвоста, ни выравнивания границы — граница и так проходит по концу истории (плюс сама команда, см.
ниже).

**Запрос собран в форме обычного прогона — ради кэша промпта.** Провайдер отдаёт по льготной
ставке ту часть запроса, которая совпадает с предыдущим, и совпадение считается от первого байта:
системное сообщение, за ним схемы инструментов, за ними история. Раунд сжатия идёт ровно по тому
окну, которое чат только что возил модели, — то есть при совпадающем начале почти весь его вход
оплачивается как кэш. Свой системный промпт и отсутствие инструментов расходились бы с чатом с
нулевой позиции, и самая дорогая операция чата оставалась бы единственной, которая платит за весь
контекст по полной ставке. Отсюда четыре требования, и все обязательны:

- тот же `sys.md` с теми же подстановками — их собирает `SystemPromptService.placeholders`, одно
  место на оба запроса: две копии списка разошлись бы на первом добавленном плейсхолдере, и кэш
  обнулился бы молча;
- тот же `ChatToolset` (схемы инструментов);
- та же модель — контроллер резолвит настройки тем же `RunOptionsResolver.resolve`, что и прогон,
  ничего не переопределяя;
- то же окно, собранное тем же кодом — `ChatHistoryService.promptRowsBefore`. Отсекать хвост у
  вызывающего было нельзя: команда `/compact` — обычная USER-строка и потому открывает ход, а блок
  `<active-project>` достаётся ряду, открывшему последний (`ActiveProjectNotice.anchor`). Отфильтруй
  готовые `PromptRow`, и блок уехал бы вместе с командой — модель не узнала бы, в каком репозитории
  написано то, что она сжимает.

Расходится с запросом чата только последнее сообщение — то самое, которое просит сжать.

**Инструменты уезжают схемами, но исполнять их некому.** Схемы нужны префиксу запроса, а вот
выполнить вызов посреди сжатия нельзя: `sys.md` требует начинать каждый ответ с
`recordChatInsights`, и без запрета сжатие ходило бы кругами вместо документа (а в развёртывании с
правом записи могло бы и тронуть репозиторий). Рубежа два: `ChatClientAttributes
.TOOL_CALLING_ADVISOR_AUTO_REGISTER = false` выключает адвайзер tool-цикла, который `ChatClient`
иначе подставляет сам, и `compactor.md` явно снимает роль, назначенную системным промптом. Вызов
вместо документа — отказ с отдельным текстом; история при этом не тронута.

Адвайзеров памяти по-прежнему нет: клиент из `ChatClientRegistry` подмешал бы то же окно вторым
слоем, а ответ записал бы в историю обычной репликой ассистента.

**Команда остаётся видна в истории, но не участвует в сжатии.** Сообщение `/compact <текст>`
сохраняется обычной USER-строкой — как любая реплика — но из окна, которое уходит модели, раунд
отрезает всё от позиции команды и дальше: команда не материал для сжатия, а управляющий сигнал. Вместо неё последним
сообщением запроса встаёт инструкция, собранная в `CompactService`: что сделать, справка о чате
(тема, проект, режим, счётчик сообщений — по нему модель сверяет число пунктов `## User requests`)
и хвост команды `/compact <текст>` в роли фокуса сжатия. По завершении раунда позиция самой команды
входит в тот же размеченный `summarized`-диапазон, что и сжатое окно, — механизм тот же, которым
фоновая суммаризация уже прячет старые сообщения от модели, не убирая их из `displayMessages`
(`summarized` исключает из промпта, `summary` — из показа; у обычных сообщений, включая команду,
`summary` остаётся `false`). Дальше команда видна пользователю, но не едет модели.

**Занятость чата — общая с прогоном.** `ConversationSlots.claim` занимает ту же заявку, что берёт
прогон, поэтому вопрос во время сжатия получает 409, а сжатие поверх идущей генерации не
начинается вовсе: обе операции читают и переписывают одну историю. Своей области прогона (`RunScope`)
операция не заводит — останавливать нечего, это один блокирующий вызов модели без стриминга, — и
кнопка «остановить» в композере на время сжатия неактивна. Таймер над полем ввода при этом идёт как
у обычного ответа: якорь ставит ответ на `POST /compact` или `COMPACT_STARTED` — что придёт первым,
и уже поставленный не сдвигается (ни реплеем, ни отставшим событием), — а вкладка, открытая
посреди раунда, берёт длительность из `GET /runs/active` — её помнит сама заявка
(`ConversationSlots.Hold`, монотонные часы), потому что области прогона у операции нет. Прироста
input у сжатия не бывает: он считается по живым замерам `RUN_USAGE`, а раунд — одно обращение,
измеряемое только по концу.

Порядок: `claim` → `repairDanglingToolCalls` (оборванная пара `tool_calls` без ответа отравила бы
весь запрос) → проверка «сжимать нечего» (422, без сохранения команды) → сохранение команды
(`ChatHistoryService.saveUserMessage`) → эхо `USER_MESSAGE` (тот же payload, что и у обычного
вопроса — фронт не пишет для него отдельный обработчик) → `COMPACT_STARTED` → **синхронный** ответ
`{runId, messageId}` → фоновый раунд (снятие окна, вызов модели, запись сводки) → `COMPACT_DONE` /
`COMPACT_ERROR`. «Сжимать нечего» проверяется синхронно и до сохранения нарочно: реплика, которая
ничего не сделала, не должна маячить в истории. Отказ исполнителя запустить фоновый раунд гасится
тем же `COMPACT_ERROR`: `COMPACT_STARTED` уже разошёлся по вкладкам, и ошибка в ответе на запрос
разблокировала бы только свою.

**След сжатия остаётся в истории.** Кроме сводки раунд пишет второй ряд — строку-плашку
«контекст сжат»: `summarized = true`, `summary = false`, текста нет, весь смысл в мете
(`ChatMessageMeta.compact` → `CompactMeta`: сколько сообщений свернулось, длина сводки, id её ряда и
вид сжатия — `COMPACT` у команды, `AUTO_COMPACT` у авто-сжатия, `SUMMARIZE` у фоновой
суммаризации; ряд без вида, записанный до его появления, читается как `COMPACT`). У сводки и плашки роли зеркальные — сводка едет модели и не показывается, плашка
показывается и модели не едет, — поэтому это два ряда, а не один: ни один флаг по отдельности
такого ряда не описывает. Плашка и есть то, что видит пользователь после перезагрузки страницы:
без неё сжатие жило бы одним SSE-событием и на перезагрузке исчезало бы бесследно. По её id
`GET /compact?messageId=…` отдаёт текст сводки (`CompactService.detail`) — без обёртки, адресованной
модели; иначе результат сжатия не виден вообще ниоткуда. Время у обоих рядов — время **завершения**
раунда, а не команды: раунд живёт десятки секунд, а подпись под плашкой говорит, когда сжатие
закончилось.

**Токены раунда стоят на той же плашке** — полем `meta.usage`, тем же, что и у обычного ответа
(`RunTokenUsage`, собранный накопителем прогона на один вызов). Правило сборки обязано быть общим:
иначе одни и те же деньги в двух местах интерфейса назывались бы разными числами. Без этой записи
сжатие было бы единственной тратой чата мимо его же статистики — `Total` во вкладке «Usage»
переставал бы сходиться со счётом провайдера ровно на стоимость каждого `/compact`. Те же числа
едут в `COMPACT_DONE`, чтобы живая вкладка и перезагруженная показали одну плашку.

Заголовочный `contextTokens` этой записи описывает контекст **самого раунда** (сжатое окно плюс
сводка), а не то, что осталось в чате после него, — поэтому `contextUsageOf` на плашке
останавливается и дальше отвечает оценкой (см. §9).

**Раунд, который сводки не дал, оплачен так же** — и его замер тоже остаётся в чате. Плашки у него
нет (сводки он не написал, а историю трогать нельзя), поэтому `meta.usage` пишется на строку самой
команды: она уже сохранена и остаётся в истории неотвеченной, как любой упавший вопрос
(`CompactService.spentRound`). Те же числа едут в `COMPACT_ERROR` вместе с id этой строки, чтобы
открытая вкладка досчитала итог сразу, а не после перезагрузки. Замер на USER-ряду бывает только
так, и контекстом чата он не является ни в каком виде — это прочитанное раундом окно вместе с его
собственной инструкцией, при том что окно осталось в чате как было. Отсюда правило фронта: замер на
ряду пользователя идёт в `chatUsageTotals` и больше никуда (`tokenUsage.js`).

**Запись общая с фоновой суммаризацией — `SummaryWriter.writeCompacted`**: разметка `summarized`
(диапазон от начала окна до позиции команды включительно), строка `summary = true` и видимая
строка-плашка — одной транзакцией.
Общий у них и замок на чат — `SummaryWriter.inConversation`, полосатый (`Striped`) по
`conversationId`. Держать его нужно вокруг всего раунда, а не одной записи: обе операции сначала
читают живое окно и лишь потом объявляют его сжатым, и два раунда, прочитавшие одно окно, положат
поверх него две сводки. Занятость чата тут не спасает — фоновая суммаризация стартует по `RUN_DONE`
и живёт уже вне занятого слота, так что без общего замка `/compact` сразу после ответа гоняется с
ней. Поэтому окно `/compact` снимает сам раунд, под замком, а не поток запроса.
Пустой ответ модели раунд отменяет целиком — но только сводку: разметить окно сжатым, не сохранив
сводку, значит стереть чат, а вот сама команда к этому моменту уже сохранена отдельно и при ошибке
раунда остаётся в истории как обычный неотвеченный вопрос.

**Своей сводки `/compact` не откладывает** — её попросили сейчас, и кэш чата он обнуляет осознанно.
Заодно он выбрасывает припаркованную фоновую сводку, если та ждала повода: его собственная сводка
заменила весь контекст, и описывать отложенной больше нечего.

#### Авто-сжатие у предела контекста (AutoCompactService)

**Последний рубеж, и ждать здесь нечего и некого.** Фоновая суммаризация сжимает только начало окна
и написанное ещё и паркует, а два-три прогона с инструментами набивают окно быстрее, чем она
успевает хоть что-то записать. Прогон, начатый на переполненном окне, не отвечает плохо — он не
начинается вовсе: провайдер отвергает запрос по длине, и чат становится непригоден без единого
способа починить его изнутри.

**Порог — доля `auto-compact-at-ratio` от окна модели** (`context-tokens`, оттуда же, откуда его
берёт `applyIfOversized`; модель без названного окна автоматически не сжимается никогда). Меряется
вес всего живого окна — `SummarizeWindow.windowTokens`, больший из `contextTokens` последнего
прогона и оценки по символам: порог про то, сколько уедет провайдеру со следующим запросом, а
уедет оно целиком. Запас под самим окном нужен: раунд сжатия читает тот же контекст, который
сжимает.

**Раунд идёт синхронно, в начале прогона** — `ChatRunService.run`, после сохранения вопроса и до
сборки промпта. Место единственно возможное: вопрос уже на месте (сжатие обязано оставить его
живым и знает это по позиции), промпт ещё не собран, а деньги несостоявшегося раунда есть куда
деть — область прогона на руках. Цену — десятки секунд ожидания перед ответом — платит один прогон
из очень многих, и платит он её вместо отказа. Упасть раунд права не имеет: сжатие это страховка
прогона, а не его часть, и `AutoCompactService` глотает свои ошибки — прогон тогда уедет на
несжатом окне, то есть ровно так, как было бы без него.

**Сам раунд — тот же `CompactService.compact`**: то же окно, тот же запрос ради кэша, та же запись
одной транзакцией. Отличается только `CompactTarget`:

- **вид плашки** `AUTO_COMPACT` — сжатие никто не просил, и в ленте это должно быть видно;
- **граница разметки** — последний ряд сжатого окна, а не вопрос: у `/compact` диапазон захватывает
  саму команду, здесь захватить вопрос значило бы начать прогон без вопроса;
- **время обоих рядов** — время последнего сжатого ряда, а не конца раунда: под плашкой уже лежит
  вопрос этого прогона, и по времени конца раунда она встала бы после него;
- **замер несостоявшегося раунда** уходит в накопитель идущего прогона (`RunScope.addCall`) — своего
  ряда у такого раунда здесь нет вовсе.

Плашка рассылается тем же `COMPACT_APPLIED`, что и применение отложенной сводки, — по той же
причине: место у неё в середине ленты, и открытая вкладка ищет его сама, по времени. `runId` у
события есть — прогона, который за раунд заплатил; своей занятости чата сжатие не заводит, её
вкладкам уже показывает сам прогон. Припаркованную фоновую сводку раунд выбрасывает так же, как
`/compact`, и по той же причине.

### 13. Поиск по чатам

Два независимых поиска, оба живут в `ChatSearchService` (`service/chat/topic`):

- **`GET /api/chats/search?q=&limit=`** → `List<ChatSearchResult>` — поиск по всем чатам пользователя: совпадения по названию чата и по содержимому сообщений объединяются по чату. Обслуживает лупу над списком чатов (`limit` зажимается в `1..50`)
- **`GET /api/chats/{id}/messages/search?q=`** → `List<MessageSearchHit>` — поиск внутри одного открытого чата, для find-бара (Ctrl+F). Ищет на бэке, потому что история пагинирована и во фронте загружен лишь хвост; фронт затем догружает страницы, пока нужное сообщение не появится в DOM

---

### 14. SearchAgentService — sub-agent поиска

`SearchAgentService` — изолированный mini-agent, доступный основной чат-модели как инструмент `searchCodebase`:

- **Изоляция:** нет chat memory, только `task` строка на вход
- **Инструменты:** read-only подмножество git/document tools (из `kb.search.subagent.allowed-tools`)
- **Рекурсивная защита:** `searchCodebase` исключён из allowed-tools по построению
- **Не оборачивается в `RecordingToolCallback`:** внутренние шаги sub-agent'а не попадают в пользовательский лог вызовов
- **System prompt:** `prompt/search-agent.md` — в нём же контракт входа: `task` может прийти набором ключевых слов, и это валидный вход; уточняющих вопросов сабагент не задаёт (спросить некого — вызов одноразовый), а отчёт разрешён только после реального вывода инструментов, не вместо него
- **Ручной цикл:** через `ToolCallingManager` с жёстким лимитом итераций (`maxIterations`)
- **При превышении лимита:** принудительная суммаризация (tool-less вызов)
- **Результат:** `SearchAgentResult` — `report`, `complete`, `iterations`, `durationMs` (скрыто от модели)

**SubAgentConfig** (`kb.search.subagent.*`): `enabled`, `model-id`, `max-tokens`, `max-iterations`, `allowed-tools`.

### 15. Библиотека фраз (PhraseController)

Фразы — готовые подсказки над полем ввода в пустом чате. Хранятся в БД (таблица `phrase`) и управляются через админку.

**Публичные эндпоинты** (`/api/phrases`):
- `GET /api/phrases` — только enabled, `ORDER BY category, position`
- `PATCH /api/phrases/{id}/favorite?value=` — переключить избранное

**Админские эндпоинты** (`/api/admin/phrases`):
- `GET /api/admin/phrases?q=` — все фразы (вкл. выключенные), `q` — быстрый поиск по label (ILIKE)
- `POST` · `PUT /{id}` · `DELETE /{id}` — создать (в конец категории) · изменить (смена категории → переезд в конец новой) · удалить
- `PATCH /{id}/favorite` · `/{id}/enabled` · `/{id}/move` — тогглы и переупорядочивание

На фронте блок рисует `Phrases.jsx`: фильтр по категориям плюс сентинелы «все» и «избранное». Плейсхолдеры `{{...}}` остаются литералами — пользователь правит их руками.

### 16. SettingsController — конфигурация AI

`SettingsController` (`/api/settings`) — read-only эндпоинт для панели «Настройки»:

- `GET /api/settings/ai-config` — снапшот AI-конфигурации: **chat** (`defaultModel`, `models`, `options`), **embedding** (модель, batch size, chunker, cache), **searchCodebase** (enabled, modelId, maxTokens, maxIterations), **summarize** (пороги из §12)
- `GET /api/settings/tools` — каталог инструментов, доступных модели: имя, описание и аргументы из JSON-схемы (`ToolCatalogService` поверх `ChatToolset`). Отдельным эндпоинтом, а не веткой снапшота: это описания и схемы, они на порядок длиннее всей остальной конфигурации, а читает их одна группа панели

### 17. HTTP Basic Auth (SecurityConfig)

`SecurityConfig` — простая stateless HTTP Basic-аутентификация:

- **Пользователь:** один in-memory пользователь из `SecurityProperties` (`kb.security.username`/`password`)
- **Пароль:** BCrypt-хэширование
- **Session:** `SessionCreationPolicy.STATELESS`; **CSRF:** отключён
- **Публичные пути:** `/actuator/health`, `/actuator/health/**`
- **Миграция:** `V2026.06.20_00__set_default_chat_topic_user.sql` — переназначает все существующие чаты на сконфигурированного пользователя

### 20. Поток данных при запросе

```
1. Frontend отправляет POST /api/chats/{conversationId}/runs
   body={ text, contextItems, model, mode, project, clientMsgId (защита от задвоения) }

2. ChatController
   ├─ checkChat() — владелец + «тронуть» updatedAt (часы приложения)
   ├─ resolveModel() / resolveMode() — параметр → сохранённое в чате → null
   └─ chatModeService.instructionsFor(mode) → фрагмент для {mode_instructions}

3. ChatRunService.start()
   ├─ Атомарная заявка на чат (409 если уже идёт генерация)
   ├─ repairDanglingToolCalls() — достроить пары от оборванного прогона
   ├─ saveUserMessage() — вопрос в БД до обращения к модели
   │   (повтор: unansweredUserMessage() вместо записи, иначе 422)
   └─ executor.execute(() -> run())

4. run():
   ├─ Публикует USER_MESSAGE (с id) + RUN_STARTED
   ├─ ChatClient.prompt()   ← своего .user(...) нет: вопрос уже в истории
   │    ├─ System prompt (sys.md + mode_instructions)
   │    ├─ ToolContext (conversationId, collector, userName — явно!)
   │    └─ advisors: CONVERSATION_ID, RUN_ID
   └─ spec.stream().chatResponse().subscribe(...)

5. Модель отвечает (потоково), tool-цикл ведёт ToolCallingAdvisor
   ├─ Текст → STREAM → ChatEventService.publish()
   ├─ Вызов инструмента → RecordingToolCallback → ToolInvocationCollector
   ├─ Сегмент (текст + tool_calls) и TOOL-ответы → MessageChatMemoryAdvisor
   │   └─ ChatHistoryService.append → chat_message.tool_data + tool_call_index
   │       └─ TOOL_CALL → ChatEventService.publish()
   └─ Буфер хвоста сбрасывается на границе сегмента

6. onComplete:
   ├─ markRunResult() — одной записью: плашки вызовов (runId/callId, без скрытых инструментов),
   │                     модель прогона на ответах хода, токены на последнем из них
   ├─ TOOL_CALLS + RUN_DONE → ChatEventService.publish()
   └─ summarizeService.trySummarize() (асинхронно)

7. doFinally (CANCEL/ON_ERROR):
   ├─ repairDanglingToolCalls() → persistPartial() с маркером [stopped]/[error]
   └─ RUN_STOPPED/RUN_ERROR → ChatEventService.publish()

8. Frontend: GET /api/chats/{id}/events
   ├─ Replay пропущенных событий (seq > fromSeq)
   └─ Живые события → applyChatEvent() → setChats()
```
