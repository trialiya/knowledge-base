## Обзор чат-системы

Документ описывает архитектуру и ключевые компоненты чат-системы Knowledge Base. Чат — это AI-ассистент, который отвечает на вопросы пользователя, используя инструменты (tools) для доступа к базе знаний, Git-репозиторию и вложениям.

**Связанные документы:**
- [API Reference](api-reference.md) — эндпоинты `ChatController`, `GitController`, `PhraseController`, `SettingsController`
- [AI-инструменты](ai-инструменты.md) — полный список инструментов
- [Модели данных — Чат](модели-данных/чат.md) — сущности `ChatTopicEntity`, `ChatMessageEntity`, `ToolCallIndexEntity`
- [Конфигурация](конфигурация.md) — `ChatConfig`, параметры AI, `ChatModelProperties`, `ChatModeProperties`, `SecurityConfig`, `SubAgentConfig`
- [Фронтенд — обзор архитектуры](фронтенд-обзор-архитектуры.md) — как чат устроен на клиенте

### 1. Архитектура чата

```
Пользователь (Frontend)
    │  HTTP (REST + SSE events)
    ▼
ChatController  (/api/chats)
    │
    ├── ChatRunService — запуск фоновой генерации (virtual threads)
    │       ├── ChatClient (Spring AI)
    │       │     ├── ChatModel (OpenAI-совместимый)
    │       │     ├── Advisor-цепочка (см. §6.3):
    │       │     │     ToolCallingAdvisor → MessageChatMemoryAdvisor
    │       │     │     → ToolPreparingAdvisor → MessageLoggingAdvisor
    │       │     ├── ChatMemory → ChatMemoryService → PostgreSQL (chat_message)
    │       │     ├── ToolCallbacks (функции + MCP) → RecordingToolCallback → ToolInvocationCollector
    │       │     └── System Prompt (classpath:prompt/sys.md, плейсхолдер {mode_instructions})
    │       └── ChatEventService → ConversationHub (in-memory pub/sub + replay)
    │
    ├── ChatEventService — SSE-канал: стриминг + кросс-вкладочная синхронизация
    │       └── ConversationHub — лог событий + fan-out на подписчиков (SseEmitter)
    │
    ├── ChatModeService — фрагменты инструкций «режимов» ассистента
    ├── ChatRuntimeMonitor — мониторинг утечек (логирование размеров реестров)
    ├── ChatRuntimeShutdown — остановка прогонов и SSE-подписок при shutdown
    ├── ChatTopicRepository → PostgreSQL (chat_topic)
    ├── ChatMemoryService → chat_message + tool_call_index (детали вызовов, поиск)
    └── SummarizeService (фоновая суммаризация)

GitController  (/api/git)
    └── GitService — fuzzy-поиск и чтение tracked-файлов репозитория

SettingsController  (/api/settings)
    └── GET /api/settings/ai-config — снапшот AI-конфигурации для панели настроек

SecurityConfig — HTTP Basic Auth (stateless, in-memory user)
```

**Ключевые особенности:**
- **Фоновые прогоны (background runs)** — генерация ответа не привязана к HTTP-запросу: `POST /runs` запускает задачу и сразу возвращает `runId`, ответ приходит через SSE event channel. Ответ переживает перезагрузку страницы и виден всем вкладкам
- **SSE event channel** — единый поток событий (`GET /events`) для стриминга ответа и кросс-вкладочной синхронизации. При подключении реплеятся пропущенные события (по `seq`), затем идут живые
- **Остановка генерации** — явный сигнал `POST /runs/{runId}/stop` вместо разрыва соединения
- **Посегментное сохранение** — tool-цикл ведёт `ToolCallingAdvisor`, а `MessageChatMemoryAdvisor` работает **внутри** цикла и сохраняет каждый сегмент (текст ассистента + `tool_calls`, ответы инструментов) отдельным сообщением. Отдельного «сохранения tool calls в конце прогона» больше нет
- **Протокольные tool-данные в сообщении** — вызовы и ответы инструментов лежат в `chat_message.tool_data` (JSON), а UI-метаданные — в `chat_message.meta`. Индекс `tool_call_index` отображает `callId` → строки сообщений, что даёт точечный `GET /tool-calls` для модалки деталей
- **Режимы ассистента** — «Аналитик», «Разработчик», «Тестировщик»: подстановка фрагмента инструкций в системный промпт (см. §7)
- **Инструменты (tools)** — AI может вызывать функции для поиска документов, чтения файлов, истории коммитов, правки файлов рабочего дерева, а также `searchCodebase` (sub-agent для многошагового поиска)
- **Компактные результаты** — `CompactToolResultConverter` сжимает результаты в `resultGist` для отображения в UI
- **Частичное сохранение при остановке/ошибке** — при `RUN_STOPPED`/`RUN_ERROR` накопленный хвост сегмента сохраняется с маркером `[stopped]`/`[error]`
- **Починка оборванных пар** — `repairDanglingToolCalls` достраивает `assistant.tool_calls` без TOOL-ответа, иначе модель отвергла бы такой диалог
- **Суммаризация** — длинные диалоги автоматически сжимаются, чтобы не превысить контекстное окно
- **Выбор модели и режима** — переключаются для каждого чата по отдельности
- **Поиск** — по всем чатам пользователя (`GET /search`) и внутри одного чата (`GET /messages/search`, find-бар Ctrl+F)
- **Внешние инструменты через MCP** — к чат-модели можно подключить внешние MCP-серверы (`kb.mcp.enabled` + `spring.ai.mcp.client.*`) — конкретный сервер не встроен и настраивается оператором
- **Библиотека фраз** — готовые подсказки над полем ввода в пустом чате, управляются из БД через [PhraseController](api-reference.md)
- **Вставка файлов и документов (`/file`, `/doc`)** — fuzzy-поиск прямо в композере чата, вставка как чипы с превью содержимого
- **HTTP Basic Auth** — stateless-аутентификация с единственным in-memory пользователем из конфига (`kb.security.*`)

### 2. ChatController — точка входа

`ChatController` (`/api/chats`) — контроллер чата. Зависимости:

| Зависимость | Назначение |
|---|---|
| `ChatClient` | Основной клиент Spring AI для общения с моделью |
| `ChatMemory` | Управление историей сообщений |
| `ChatTopicRepository` | CRUD для топиков чата |
| `ChatMemoryService` | Персистентное хранение сообщений, детали tool calls, поиск |
| `ChatModelProperties` | Конфигурация доступных моделей (из `kb.chat.*`) |
| `ChatModeProperties` / `ChatModeService` | Конфигурация и тексты режимов ассистента |
| `ChatRunService` | Запуск фоновой генерации ответа |
| `ChatEventService` | Публикация событий в SSE-канал |
| `Clock` | Часы аудита Spring Data — ими же датируется «тронуть чат» (`updatedAt`) |

**Эндпоинты** (подробнее в [API Reference](api-reference.md)):

| Эндпоинт | Назначение |
|---|---|
| `POST /api/chats/{id}/runs` | Запустить фоновую генерацию (возвращает `runId` и `messageId` сохранённого вопроса), `?model=`, `?mode=`, `?clientMsgId=` |
| `GET /api/chats/{id}/events` | SSE-поток событий чата (стриминг + синхронизация), `?fromSeq=` |
| `POST /api/chats/{id}/runs/{runId}/stop` | Остановить активный прогон (идемпотентно) |
| `GET /api/chats/{id}/runs/active` | runId активного прогона (или `{}`) |
| `POST /api/chats/{id}/messages` | Синхронный (не потоковый) запрос |
| `GET /api/chats/{id}/messages` | Курсорная страница сообщений (`beforeCreatedAt`/`beforeId`/`limit`) |
| `GET /api/chats/{id}/messages/search` | Поиск сообщений внутри чата (find-бар) |
| `GET /api/chats/{id}/tool-calls?callId=` | Полные детали одного вызова инструмента |
| `GET /api/chats` | Список чатов пользователя (метаданные, без сообщений) |
| `GET /api/chats/search?q=&limit=` | Поиск чатов по названию и содержимому сообщений |
| `GET /api/chats/{id}` | Конкретный чат (`?includeMessages=`) |
| `DELETE /api/chats/{id}` | Удаление чата |
| `PUT /api/chats/{id}/topic` | Установка/обновление названия (пользовательского) |
| `GET /api/chats/models` · `PUT /api/chats/{id}/model` | Список моделей · задать модель чата |
| `GET /api/chats/modes` · `PUT /api/chats/{id}/mode` | Список режимов · задать режим чата |

Служебные сообщения-«крошки» вызовов инструментов (флаг `meta.toolCalls`) при выдаче обрезаются до преамбулы — JSON пользователю не показывается. Удаление чата останавливает идущую генерацию и рассылает событие `CHAT_DELETED`, чтобы открытые на нём вкладки закрыли его.

#### Фоновые прогоны (Background Runs)

Генерация ответа не привязана к HTTP-запросу:

1. **`POST /runs`** — принимает сообщение, **сохраняет его синхронно** (см. §3), запускает генерацию в фоновом потоке (virtual thread) и сразу возвращает `{ "runId": "...", "messageId": 123 }`. Если генерация уже идёт — `409 Conflict`
2. **`GET /events`** — постоянное SSE-соединение. При подключении реплеит пропущенные события (по `fromSeq`), затем шлёт живые
3. **`POST /runs/{runId}/stop`** — явная остановка: `dispose()` → `CANCEL` → частичное сохранение + событие `RUN_STOPPED`
4. **`GET /runs/active`** — для восстановления состояния после перезагрузки страницы

**Преимущества:**
- Ответ продолжает генерироваться после перезагрузки страницы
- Все вкладки видят один и тот же ответ (кросс-вкладочная синхронизация)
- Остановка — явный сигнал, а не разрыв соединения
- `clientMsgId` защищает от задвоения оптимистичного пузыря
- Вопрос пользователя не теряется, даже если прогон упадёт до подписки на стрим

### 3. ChatRunService — фоновые прогоны

`ChatRunService` — центральный сервис, запускающий генерацию как фоновую задачу:

- **`start(conversationId, user, userMessage, resolvedModel, modeInstructions, clientMsgId)`** — атомарная заявка на чат (`activeByConversation`), затем синхронно `repairDanglingToolCalls` + `saveUserMessage`, затем запуск в `chatRunExecutor` (virtual threads + `DelegatingSecurityContextExecutorService`). Возвращает `StartedRun(runId, userMessageId)`
  - **`userMessage = null` — повтор упавшего прогона** (`POST /runs?retry=true`): нового сообщения не появляется, ходом остаётся последний неотвеченный вопрос (`unansweredUserMessage`). Если модель успела выдать хоть что-то — текст или вызов инструмента — повтор запрещён (`422`), см. §3.2
- **`stop(conversationId, runId)`** — `dispose()` реактивного стрима
- **`stopAll()` / `awaitQuiescence(timeout)`** — гашение всех прогонов при остановке приложения (см. §5)
- **`activeRun(conversationId)`** — делегирует в `ChatEventService`

**Поток выполнения (`run()`):**
1. Публикует `USER_MESSAGE` (эхо для других вкладок, с `id` сохранённого сообщения) и `RUN_STARTED`. На повторе сообщение не новое, но событие всё равно публикуется: вкладки сверяют пузырь по `id` и срезают всё, что стоит после него, — так пузырь с ошибкой упавшего прогона исчезает везде сразу
2. Создаёт `ChatClient` prompt: `mode_instructions` в системный промпт, `toolContext` (явная передача пользователя — операторы Reactor исполняются на других потоках, куда thread-local `SecurityContext` не доезжает), advisor-параметры `CONVERSATION_ID` и `RUN_ID_PARAM`. Своего `.user(...)` в промпте **нет** — вопрос уже в истории, его подставит advisor памяти
3. Подписывается на реактивный стрим: `onNext` → `STREAM`, `onComplete` → `attachRunMeta` + `TOOL_CALLS` + `RUN_DONE` + суммаризация
4. `doFinally`: `CANCEL` → частичное сохранение + `RUN_STOPPED`, `ON_ERROR` → частичное сохранение + `RUN_ERROR`
5. `cleanup()`: закрывает хаб прогона, снимает заявку

**Границы сегментов и буфер.** Завершённые сегменты сохраняет advisor-цепочка по ходу прогона, поэтому в буфере держится только хвост текущего сегмента — иначе `persistPartial` задублировал бы уже сохранённое. Буфер сбрасывается на `finishReason=TOOL_CALLS` и по колбэку `ToolInvocationCollector` (вызов инструмента — надёжная граница: агрегированный tool-чанк `ToolCallingAdvisor` отфильтровывает из потока).

**Порядок в `persistPartial`:** сначала `repairDanglingToolCalls`, только потом запись частичного текста — иначе записанный первым `partial` навсегда спрятал бы оборванную пару (`repairDanglingToolCalls` смотрит только на последнюю строку), и модель отвечала бы `400` на каждый следующий запрос этого чата.

**Гонка «стоп до подписки»:** `cancel()` ставит флаг ДО чтения `disposable`, а `run()` ставит `disposable` ДО чтения флага — так остановка не проваливается в окно между постановкой задачи в пул и подпиской на стрим.

#### 3.1. Контекст, приложенный к сообщению

Файл, приложенный в композере, попадает не только в список вложений чата, но и **в само
сообщение** — ссылкой в `chat_message.meta.contextItems` (см. `ContextItem` в
[модели данных](модели-данных/чат.md)). Раньше вложение существовало отдельно от диалога, и
модель узнавала о нём, только если сама догадывалась спросить список вложений.

Ключевые решения:

- **Ссылка, а не копия.** В историю уходит id, а не содержимое: файл может быть на мегабайт, и
  в промпте он остался бы навсегда. `ContextItemService.render` собирает опись приложенного при
  **каждом** чтении истории (`ChatMemoryService.findByConversationId`) и дописывает её к тексту
  вопроса блоком `<attached-context>`. Содержимое модель читает инструментом
  `getAttachmentContent` тогда, когда оно понадобилось.
- **Переименовали — увидит новое имя, удалили — не увидит ничего.** Следствие того же резолва
  при чтении: удалённое вложение просто выпадает из блока, а не остаётся вечным обещанием файла,
  которого больше нет.
- **Записанный текст не меняется.** Блок живёт только в `UserChatMessage`, отданном модели;
  `chatMessage().getContent()` по-прежнему отдаёт то, что написал пользователь, — на этом держатся
  и дедупликация в `saveAll`, и показ сообщения в ленте.
- **Клиенту верят только на ссылку.** `ContextItemService.resolve` проверяет, что вложение
  принадлежит этому чату (иначе чужой id стал бы способом прочитать чужой файл), и берёт подпись с
  самого объекта, а не из запроса.
- **Момент привязки — не проблема.** Мы сами пишем USER-ряд в `start()` (см. этап предсохранения),
  поэтому элементы уходят в `meta` той же вставкой: ни знания id заранее, ни второго запроса.

Сжатие истории про это знает: `summarizer.md` требует сохранять имя и id вложения дословно —
блок `<attached-context>` исчезает вместе со сжатым сообщением, и потерянный id означает файл,
до которого больше не добраться.

#### 3.2. Повтор упавшего прогона

Повторить ход можно **ровно в одном состоянии**: вопрос сохранён, а модель не выдала ничего — ни текста, ни вызова инструмента. Тогда в истории дописывать нечего, и повтор просто запускает прогон поверх неё заново, без второго `USER`-ряда.

Как только ответ начался, повтор запрещён. Переиграть такой ход молча можно было бы только двумя способами, и оба хуже прямого продолжения диалога: задвоить вопрос вторым `USER`-рядом либо стереть сделанное моделью, включая побочные эффекты уже выполненных инструментов. Поэтому дальше пользователь пишет сам — «продолжай».

Решает это `ChatMemoryService.unansweredUserMessage`: последний ряд чата, если это `USER`. Проверка идёт **после** `repairDanglingToolCalls` — достроенный TOOL-ответ как раз и означает, что ответ уже начался, и он же закрывает окно повтора. В обратном порядке последним рядом ещё был бы вопрос, и прогон стартовал бы поверх незакрытой пары.

На фронте то же решение принимается заранее, в момент ошибки, — там ещё известно, доехал ли вопрос до бэка (`constants/retryMode.js`):

| Режим | Когда | Что делает «Повторить» |
|---|---|---|
| `resend` | Сбой самого `POST /runs` | Отправляет текст вопроса заново — на бэке его нет |
| `continue` | `RUN_ERROR`, и прогон не выдал ни текста, ни вызова инструмента | `POST /runs?retry=true` — прогон поверх той же истории |
| нет режима | `RUN_ERROR` после начатого ответа | Кнопки нет вовсе |

Бэк остаётся единственным арбитром: если состояние успело измениться (другая вкладка, гонка с событием), `retry=true` получает `422`, кнопка с пузыря снимается и показывается пояснение.

### 4. ChatEventService и ConversationHub — SSE event channel

**ChatEventService** — in-memory pub/sub поверх `ConversationHub`:

- **`subscribe(conversationId, fromSeq)`** — создаёт/находит хаб, подписывает `SseEmitter` с replay пропущенных событий. Таймаут эмиттера — `kb.chat.timeout.sse` (по умолчанию 30 минут)
- **`publish(conversationId, type, runId, clientMsgId, payload)`** — публикует событие всем подписчикам
- **`publishIfPresent(...)`** — публикует только в уже существующий хаб (используется для `CHAT_DELETED`: поднимать хаб ради удаления незачем)
- **`startRun`/`endRun`** — управление жизненным циклом прогона в хабе
- **`sendHeartbeats()`** — периодические keep-alive, чтобы прокси не рвали простаивающее соединение
- **`closeIfIdle()` / `closeAll()`** — выгрузка простаивающего хаба и гашение всех при shutdown

**ConversationHub** — канал одного чата:

- **Лог событий** (`eventLog`) — хранит события только активного прогона, очищается при старте и завершении
- **Подписчики** (`subscribers`) — `SseEmitter` всех открытых вкладок
- **Replay** — при подключении с `fromSeq` реплеятся все события с `seq > fromSeq`
- **Потокобезопасность** — `ReentrantLock` (не `synchronized`, чтобы избежать pinning на виртуальных потоках)
- **Закрытие** — `closed` флаг предотвращает гонку «выгрузка ↔ новая подписка»

**ChatEvent** — запись одного события:

| Поле | Тип | Описание |
|---|---|---|
| `seq` | long | Монотонный номер (точка дозагрузки) |
| `type` | ChatEventType | Тип события |
| `runId` | String | К какому прогону относится |
| `clientMsgId` | String | ID клиента-инициатора (защита от задвоения) |
| `payload` | Object | Полезная нагрузка |

**ChatEventType:**

| Тип | Payload | Когда |
|---|---|---|
| `USER_MESSAGE` | `UserMessagePayload` | Эхо сообщения для других вкладок (`id`, `text`, `createdAt`) |
| `RUN_STARTED` | — | Начало генерации |
| `STREAM` | `StreamMessage` | Чанк текста |
| `TOOL_PREPARING` | — | Модель начала формировать вызов инструмента, имя ещё неизвестно — фронт показывает «готовлю данные…». Работает не вполне корректно, см. `docs/todo/tool-preparing.md` |
| `TOOL_CALL` | `ToolCallMessage` | Обновление вызова инструмента |
| `TOOL_CALLS` | `ToolCallsMessage` | Итоговый список вызовов сегмента |
| `RUN_DONE` | — | Успешное завершение |
| `RUN_STOPPED` | — | Остановлена пользователем |
| `RUN_ERROR` | `{ message }` | Прервана ошибкой |
| `CHAT_DELETED` | — | Чат удалён (в т.ч. из другой вкладки) — вкладки закрывают его |

### 5. ChatRuntimeMonitor и ChatRuntimeShutdown

**ChatRuntimeMonitor** — временный мониторинг утечек: периодически логирует размеры in-memory реестров (`eventHubs`, `activeRuns`, `claimedChats`). Интервал: `kb.chat.monitor-interval-ms` (по умолчанию 60000). Значение ≤ 0 отключает мониторинг.

**ChatRuntimeShutdown** — гашение рантайма при остановке приложения (слушает `ContextClosedEvent`, то есть срабатывает ДО graceful shutdown Tomcat):

1. `ChatRunService.stopAll()` — все активные прогоны отменяются как обычный стоп: `dispose()` → `CANCEL` → частичное сохранение с маркером `[stopped]` → событие `RUN_STOPPED` уходит ещё живым подписчикам
2. `awaitQuiescence(kb.chat.shutdown-grace-ms)` — ожидание, пока терминальная обработка допишет в БД (по умолчанию 5000 мс; пул соединений закроется сразу после shutdown)
3. `ChatEventService.closeAll()` — все `SseEmitter` завершаются, реестр хабов очищается

Зачем: подписка вкладки на `GET /events` — долгоживущий async-запрос. Пока эмиттер не завершён, Tomcat считает запрос активным, а в Spring Boot 4 graceful shutdown включён по умолчанию — одна открытая вкладка задерживала остановку на все 30 с (`spring.lifecycle.timeout-per-shutdown-phase`), после чего соединение всё равно обрывалось (`Graceful shutdown aborted with one or more requests still active`). Вкладки видят обрыв потока и переподключаются с backoff уже к поднявшемуся инстансу, дозагружая пропущенное по `fromSeq`.

### 6. ChatClient и ChatConfig

`ChatConfig` — центральная конфигурация чата. Создаёт бины:

#### 6.1 ChatMemory

```java
MessageWindowChatMemory.builder()
    .chatMemoryRepository(chatMemoryService)
    .maxMessages(300)
    .build();
```

`maxMessages` — **не** размер контекста, уходящего в модель. Контекст определяет `SummarizeService`: помеченные `summarized` сообщения выпадают из `findByConversationId`, а пороги живут в `kb.chat.summarize.*`. `maxMessages` работает только на записи (`add` подрезает историю перед `saveAll`), а так как `saveAll` — append-only, наблюдаемого эффекта у подрезки здесь нет. Значение держат высоким, чтобы оно не могло тихо потерять сообщение из необычно большого батча. В панели «Настройки → Модели» его намеренно не показывают: число, которое ни на что не влияет, читалось бы как лимит контекста.

#### 6.2 chatRunExecutor

```java
@Bean(destroyMethod = "shutdown")
public ExecutorService chatRunExecutor() {
    return new DelegatingSecurityContextExecutorService(
            Executors.newVirtualThreadPerTaskExecutor());
}
```

Виртуальные потоки + перенос `SecurityContext` на worker-поток.

#### 6.3 ChatClient и advisor-цепочка

- **ChatModel** — OpenAI-совместимая модель
- **System Prompt** — `classpath:prompt/sys.md` с плейсхолдером `{mode_instructions}`
- **Advisor-цепочка** (снаружи внутрь, по возрастанию `getOrder()`):

| Advisor | Порядок | Роль |
|---|---|---|
| `ToolCallingAdvisor` | `DEFAULT_ORDER` | Ведёт tool-цикл. Внутренняя история **отключена** (`disableInternalConversationHistory`): в каждой итерации промпт несёт только `[system, последний tool-ответ]`, остальной контекст перечитывается из `ChatMemory`. Это и есть режим Spring AI, при котором каждый сегмент сохраняется отдельным сообщением |
| `MessageChatMemoryAdvisor` | `+100` | **Внутри** цикла: `before()` подставляет историю и дописывает новое user/tool-сообщение в хранилище, `after()` сохраняет ассистентское сообщение каждой итерации — включая промежуточные сегменты с `tool_calls`. Требует репозитория, умеющего round-trip tool-сообщений (`ChatMemoryService`: `chat_message.tool_data`) |
| `ToolPreparingAdvisor` | `LOWEST_PRECEDENCE` | Внутри цикла: на каждой итерации шлёт `TOOL_PREPARING` перед раундом выполнения инструментов |
| `MessageLoggingAdvisor` | `LOWEST_PRECEDENCE` | Внутри цикла, самый внутренний: DEBUG-логирование фактического списка сообщений, уходящего в модель. Выключен по умолчанию |

**ToolCallbacks** — все функции оборачиваются в `RecordingToolCallback`:

| Функция | Условие подключения |
|---|---|
| `TopicFunction` | всегда — авто-именование чата, id/имя пользователя, дата-время |
| `MessageLookupFunction` | всегда — поиск исходных сообщений |
| `DocumentFunction` | всегда — работа с документами базы знаний |
| `GitFunction` | всегда — чтение Git-репозитория |
| `AttachmentFunction` | всегда — работа с вложениями |
| `SearchAgentFunction` | `kb.search.subagent.enabled=true` |
| `GitEditFunction` | `kb.git.edit-enabled=true` **и** рабочее дерево доступно на запись |
| MCP-инструменты | `kb.mcp.enabled=true` (внешние серверы из `spring.ai.mcp.client.*`) |

Оба условных бина отсутствуют целиком, когда выключены, — модель не видит инструментов, которые могли бы только упасть. У `gitEditFunction` вторая проверка нужна для read-only монтирования: при `edit-enabled=true` и недоступном на запись дереве бин возвращает `null` и пишет предупреждение в лог.

### 7. Режимы ассистента (ChatModeProperties / ChatModeService)

Режим — готовый фрагмент инструкций, подставляемый в системный промпт через плейсхолдер `{mode_instructions}`. Это параллель выбору модели: пользователь переключает его в композере чата, значение хранится в `chat_topic.mode`.

**Конфигурация** (`kb.chat.modes`):

```yaml
kb:
  chat:
    modes:
      - id: analytic
        label: Аналитик
        prompt: classpath:prompt/mode-analytic.md
      - id: developer
        label: Разработчик
        prompt: classpath:prompt/mode-developer.md
      - id: tester
        label: Тестировщик
        prompt: classpath:prompt/mode-tester.md
```

- `ChatModeService` читает тексты режимов из classpath **один раз при старте** и отдаёт фрагмент по id
- Наружу (`GET /api/chats/modes`) отдаётся только `{ id, label }` — сам текст промпта остаётся на бэке
- **«Без режима»** — валидное состояние по умолчанию: `instructionsFor(null)` возвращает пустую строку. Плейсхолдер всё равно должен получить значение, иначе рендер шаблона упадёт
- Разрешение режима зеркалит разрешение модели: параметр запроса `?mode=` → сохранённый `chat_topic.mode` → `null`. Неизвестный id → `400 Bad Request`; режим, убранный из конфига, отфильтровывается через `isAllowed`

### 8. ChatMemoryService — персистентность сообщений и tool-данные

`ChatMemoryService` реализует `ChatMemoryRepository` и отвечает за сохранение сообщений в PostgreSQL.

**Таблица `chat_message`** (подробнее в [Модели данных — Чат](модели-данных/чат.md)):

| Поле | Тип | Описание |
|---|---|---|
| `id` | `long` | Первичный ключ |
| `conversation_id` | `String` | ID беседы |
| `content` | `String` | Текст сообщения |
| `type` | `MessageType` | USER, ASSISTANT, SYSTEM, TOOL |
| `position` | `long` | Порядковый номер в беседе |
| `summarized` / `summary` | `boolean` | Суммаризировано ли · является ли само сообщение суммаризацией |
| `tool_data` | `String` (JSON) | **Протокольные** tool-данные: вызовы ассистента и TOOL-ответы (`ToolData`, `ToolDataToJsonConverter`) |
| `meta` | `String` (JSON) | **UI-метаданные**: `ChatMessageMeta` c `ToolInvocationMeta`, `runId`, флаг `toolCalls` |
| `created_at` | `LocalDateTime` | Время создания |

> **Не смешивать `tool_data` и `meta`.** `tool_data` — то, что нужно протоколу LLM, чтобы воспроизвести историю; `meta` — то, что рисует фронтенд. Отдельной таблицы tool-вызовов нет.

**Индекс `tool_call_index`** (`ToolCallIndexEntity`) отображает `conversationId + callId` → id сообщений с полными деталями: сегмент ASSISTANT, выдавший вызов, и строка TOOL-ответа, когда та появится. Индекс заполняется **в момент сохранения** (`saveAll`), а не фоновой задачей.

**Ключевые методы:**

| Метод | Назначение |
|---|---|
| `saveUserMessage(conversationId, text, contextItems)` | Пишет вопрос пользователя до обращения к модели и возвращает сохранённый ряд. Приложенный контекст уходит в `meta` той же вставкой. Транзакция обязана закрыться до старта стрима: advisor памяти читает историю на другом потоке и незакоммиченную строку не увидит |
| `unansweredUserMessage(conversationId)` | Последний ряд чата, если это `USER` — единственное состояние, из которого допустим повтор прогона (§3.2). Появился `ASSISTANT` или `TOOL` — пусто |
| `saveAll` | Сохраняет новые сообщения (append-only: уже персистнутые отфильтровываются), пишет `tool_data` и заполняет `tool_call_index`; публикует live-события `TOOL_CALL` |
| `findByConversationId` | Несуммаризированные сообщения — то, что уходит в модель. К вопросу с приложенным контекстом дописывается блок `<attached-context>` (§3.1) |
| `findChatMessageByConversationId` | Сообщения для отображения пользователю |
| `findLatestPage` / `findPageBefore` | Курсорная keyset-пагинация (`Page` с `hasMore` и `oldestCursor`) |
| `findToolCallDetail(conversationId, callId)` | Полные детали вызова — **простой lookup через индекс**, без позиционной арифметики по истории |
| `invocationsFor(entity, page)` | Синтезирует меты из `tool_data` для сегментов без `meta.invocations` (оборванные/старые прогоны) |
| `attachRunMeta(conversationId, runId, invocations)` | По завершении прогона проставляет `runId`/`callId`/`messageId` в метах и вырезает скрытые инструменты |
| `repairDanglingToolCalls` | Достраивает `assistant.tool_calls` без TOOL-ответа (иначе модель ответит `400`) |
| `searchChats(user, q, limit)` / `searchMessages(conversationId, q)` | Поиск по всем чатам · внутри одного чата |
| `hasDetails(toolName)` | Сохраняются ли детали вызова этого инструмента в БД |
| `backfillToolCallIdsIfNeeded()` | Run-once бэкфилл данных, записанных до появления `tool_call_index`/`callId`: маркер в `backfill_state` ставится в той же транзакции, повторные старты — no-op (`ToolCallIdBackfillRunner`, без флагов конфигурации) |

> Метода `saveToolCalls()` больше нет. Раньше он писал в конце прогона одно SYSTEM-сообщение-«крошку» с JSON всех вызовов; теперь вызовы приходят вместе с сегментами. «Крошки» старых чатов по-прежнему читаются (флаг `meta.toolCalls`) и на фронте прикрепляются к предыдущему ответу ассистента.

### 9. ChatTopicEntity — топик чата

`ChatTopicEntity` — сущность, представляющая одну беседу. Таблица `chat_topic`:

### 10. Стриминг (SSE)

```
POST /api/chats/{conversationId}/runs
    │
    ├── ChatRunService.start()
    │     ├── Атомарная заявка на чат (409 если уже идёт)
    │     ├── repairDanglingToolCalls()  ← строго до записи вопроса
    │     ├── saveUserMessage()          ← вопрос в БД, id известен
    │     │   (retry=true: вместо записи — unansweredUserMessage(), иначе 422)
    │     └── executor.execute(() -> run())
    │           ├── Публикация USER_MESSAGE (с id) + RUN_STARTED
    │           ├── chatClient.prompt().stream().chatResponse()  ← без .user(...)
    │           ├── onNext  → STREAM → ChatEventService.publish()
    │           ├── (advisor-цепочка сохраняет сегменты и шлёт TOOL_PREPARING/TOOL_CALL)
    │           ├── onComplete → attachRunMeta + TOOL_CALLS + RUN_DONE + summarize
    │           └── doFinally → частичное сохранение + RUN_STOPPED/RUN_ERROR
    │
    └── Возвращает { "runId": "...", "messageId": 123 }

GET /api/chats/{conversationId}/events?fromSeq=0
    │
    └── ChatEventService.subscribe()
          ├── Replay пропущенных событий (seq > fromSeq)
          └── Живые события → SseEmitter.send()
```

**Типы SSE-сообщений (DTO):**

| DTO | Когда | Поля |
|---|---|---|
| `StreamMessage` | Каждый чанк текста | `message`, `finishReason` (или null) |
| `ToolCallMessage` | Начало/конец вызова инструмента | `toolCall` (ToolInvocation) |
| `ToolCallsMessage` | Завершение прогона | `toolCalls` (список ToolInvocationMeta) |
| `UserMessagePayload` | Эхо сообщения пользователя | `message`, `createdAt` |
| `ChatEvent` | Любое событие в канале | `seq`, `type`, `runId`, `clientMsgId`, `payload` |

### 11. RecordingToolCallback и ToolInvocationCollector

**RecordingToolCallback** — обёртка над каждым `ToolCallback`, которая:
1. Перехватывает вызов инструмента
2. Извлекает `ToolInvocationCollector` из `ToolContext`
3. Записывает `STARTED` → выполняет делегат → записывает `OK` или `ERROR`
4. Извлекает `resultMeta` через `ToolCallResultMetaProvider` (если результат его реализует)
5. Вычисляет `resultGist` самостоятельно (из `resultMeta` или через `CompactToolResultConverter`)
6. Фильтрует аргументы (только из белого списка `ALLOWED_INPUT_ARGUMENTS`)

**ToolInvocationCollector** — потокобезопасный коллектор (`CopyOnWriteArrayList`):
- `record(invocation)` — добавляет запись и отправляет в liveSink (SSE)
- `snapshot()` / `completedSnapshot()` — все вызовы · только завершённые (без STARTED)
- Колбэк «инструмент пошёл» — граница сегмента для буфера `ChatRunService` (см. §3)

**ToolInvocationMeta** — то, что уходит в БД и на фронт: `name`, `arguments`, `status`, `error`, `resultMeta`, `resultGist`, `hasDetails`, `callIndex` и **`callId`** — единственный ключ, нужный модалке деталей (`GET /tool-calls` находит `messageId`/`responseMessageId` сам, через `tool_call_index`). Поля с `null` у старых записей опускаются из JSON.

**ToolCallDetail** — ответ `GET /tool-calls`: `name`, `argumentsRaw`, `status`, `error`, `resultText`, `resultMeta`, `createdAt`.

### 12. Суммаризация (SummarizeService)

`SummarizeService` автоматически сжимает длинные диалоги, чтобы не превысить контекстное окно модели.

**Принцип работы:**
1. После каждого ответа AI вызывается `trySummarize(conversationId)` — асинхронно, на virtual thread
2. Блокировка через `Striped<Lock>` — одна беседа не может суммаризироваться параллельно
3. Проверяются два порога (оба из `kb.chat.summarize.*`)
4. Если порог превышен — сообщения до `liveMessages.size() - overlapMessages` сжимаются
5. Существующие суммаризации загружаются как контекст
6. Если накоплено `summary-collapse-threshold` суммаризаций — они схлопываются в одну мета-суммаризацию
7. LLM генерирует суммаризацию через отдельный `ChatClient` с промптом `prompt/summarizer.md`
8. Старые сообщения помечаются `summarized = true`, новая суммаризация сохраняется как `SYSTEM` сообщение с `summary = true`

**SummarizeProperties** (`kb.chat.summarize.*`):

| Параметр | Значение по умолчанию | Описание |
|---|---|---|
| `token-threshold` | 30000 | Оценочный бюджет токенов «живого» окна |
| `message-count-threshold` | 50 | Минимум сжимаемых сообщений |
| `overlap-messages` | 30 | Свежие сообщения, остающиеся вне сжатого окна |
| `summary-collapse-threshold` | 5 | Сколько суммаризаций схлопываются в мета-суммаризацию |
| `chars-per-token` | 4 | Символов на оценочный токен (грубая эвристика, без токенайзера) |

`SummarizeConfig` — read-only проекция для панели настроек.

### 13. Поиск по чатам

Два независимых поиска, оба живут в `ChatMemoryService`:

- **`GET /api/chats/search?q=&limit=`** → `List<ChatSearchResult>` — поиск по всем чатам пользователя: совпадения по названию чата и по содержимому сообщений объединяются по чату. Обслуживает лупу над списком чатов (`limit` зажимается в `1..50`)
- **`GET /api/chats/{id}/messages/search?q=`** → `List<MessageSearchHit>` — поиск внутри одного открытого чата, для find-бара (Ctrl+F). Ищет на бэке, потому что история пагинирована и во фронте загружен лишь хвост; фронт затем догружает страницы, пока нужное сообщение не появится в DOM

### 14. SearchAgentService — sub-agent поиска

`SearchAgentService` — изолированный mini-agent, доступный основной чат-модели как инструмент `searchCodebase`:

- **Изоляция:** нет chat memory, только `task` строка на вход
- **Инструменты:** read-only подмножество git/document tools (из `kb.search.subagent.allowed-tools`)
- **Рекурсивная защита:** `searchCodebase` исключён из allowed-tools по построению
- **Не оборачивается в `RecordingToolCallback`:** внутренние шаги sub-agent'а не попадают в пользовательский лог вызовов
- **System prompt:** `prompt/search-agent.md`
- **Ручной цикл:** через `ToolCallingManager` с жёстким лимитом итераций (`maxIterations`)
- **При превышении лимита:** принудительная суммаризация (tool-less вызов)
- **Результат:** `SearchAgentResult` — `report`, `complete`, `iterations`, `durationMs` (скрыто от модели)

**SubAgentConfig** (`kb.search.subagent.*`): `enabled`, `model-id`, `max-tokens`, `max-iterations`, `allowed-tools`.

### 15. Библиотека фраз (PhraseController)

Фразы — готовые подсказки над полем ввода в пустом чате. Хранятся в БД (таблица `phrase`) и управляются через админку.

**Публичные эндпоинты** (`/api/phrases`):
- `GET /api/phrases` — только enabled, `ORDER BY category, position`
- `PATCH /api/phrases/{id}/favorite?value=` — переключить избранное

**Админские эндпоинты** (`/api/admin/phrases`):
- `GET /api/admin/phrases?q=` — все фразы (вкл. выключенные), `q` — быстрый поиск по label (ILIKE)
- `POST` · `PUT /{id}` · `DELETE /{id}` — создать (в конец категории) · изменить (смена категории → переезд в конец новой) · удалить
- `PATCH /{id}/favorite` · `/{id}/enabled` · `/{id}/move` — тогглы и переупорядочивание

На фронте блок рисует `Phrases.jsx`: фильтр по категориям плюс сентинелы «все» и «избранное». Плейсхолдеры `{{...}}` остаются литералами — пользователь правит их руками.

### 16. SettingsController — конфигурация AI

`SettingsController` (`/api/settings`) — read-only эндпоинт для панели «Настройки»:

- `GET /api/settings/ai-config` — снапшот AI-конфигурации: **chat** (`defaultModel`, `models`, `options`), **embedding** (модель, batch size, chunker, cache), **searchCodebase** (enabled, modelId, maxTokens, maxIterations), **summarize** (пороги из §12)

### 17. HTTP Basic Auth (SecurityConfig)

`SecurityConfig` — простая stateless HTTP Basic-аутентификация:

- **Пользователь:** один in-memory пользователь из `SecurityProperties` (`kb.security.username`/`password`)
- **Пароль:** BCrypt-хэширование
- **Session:** `SessionCreationPolicy.STATELESS`; **CSRF:** отключён
- **Публичные пути:** `/actuator/health`, `/actuator/health/**`
- **Миграция:** `V2026.06.20_00__set_default_chat_topic_user.sql` — переназначает все существующие чаты на сконфигурированного пользователя

### 18. Таймауты

Длинные прогоны с инструментами упираются в несколько независимых дедлайнов — все вынесены в конфиг:

| Параметр | Значение | Что ограничивает |
|---|---|---|
| `spring.ai.openai.timeout` (`KB_CHAT_STREAM_TIMEOUT`) | 10m | Дедлайн запроса SDK openai-java (он же реально отменяет вызов) и таймауты нижележащего OkHttp. Дефолт SDK (60 с) слишком мал для долгих tool-раундов и рвёт стрим на полуслове |
| `kb.chat.timeout.sse` (`KB_CHAT_SSE_TIMEOUT`) | 30m | Таймаут `SseEmitter` одной вкладки (окно replay/переподключения) |
| `spring.mvc.async.request-timeout` | 30m | Общий дедлайн async-запросов Spring MVC |
| `kb.chat.shutdown-grace-ms` | 5000 | Ожидание дозаписи оборванных ответов при остановке (см. §5) |

### 20. Поток данных при запросе

```
1. Frontend отправляет POST /api/chats/{conversationId}/runs
   body="текст вопроса", ?model=, ?mode=, ?clientMsgId= (защита от задвоения)

2. ChatController
   ├─ checkChat() — владелец + «тронуть» updatedAt (часы приложения)
   ├─ resolveModel() / resolveMode() — параметр → сохранённое в чате → null
   └─ chatModeService.instructionsFor(mode) → фрагмент для {mode_instructions}

3. ChatRunService.start()
   ├─ Атомарная заявка на чат (409 если уже идёт генерация)
   ├─ repairDanglingToolCalls() — достроить пары от оборванного прогона
   ├─ saveUserMessage() — вопрос в БД до обращения к модели
   │   (повтор: unansweredUserMessage() вместо записи, иначе 422)
   └─ executor.execute(() -> run())

4. run():
   ├─ Публикует USER_MESSAGE (с id) + RUN_STARTED
   ├─ ChatClient.prompt()   ← своего .user(...) нет: вопрос уже в истории
   │    ├─ System prompt (sys.md + mode_instructions)
   │    ├─ ToolContext (conversationId, collector, userName — явно!)
   │    └─ advisors: CONVERSATION_ID, RUN_ID
   └─ spec.stream().chatResponse().subscribe(...)

5. Модель отвечает (потоково), tool-цикл ведёт ToolCallingAdvisor
   ├─ Текст → STREAM → ChatEventService.publish()
   ├─ Перед раундом инструментов → TOOL_PREPARING (ToolPreparingAdvisor)
   ├─ Вызов инструмента → RecordingToolCallback → ToolInvocationCollector
   ├─ Сегмент (текст + tool_calls) и TOOL-ответы → MessageChatMemoryAdvisor
   │   └─ ChatMemoryService.saveAll → chat_message.tool_data + tool_call_index
   │       └─ TOOL_CALL → ChatEventService.publish()
   └─ Буфер хвоста сбрасывается на границе сегмента

6. onComplete:
   ├─ attachRunMeta() — runId/callId/messageId в метах, вырезание скрытых инструментов
   ├─ TOOL_CALLS + RUN_DONE → ChatEventService.publish()
   └─ summarizeService.trySummarize() (асинхронно)

7. doFinally (CANCEL/ON_ERROR):
   ├─ repairDanglingToolCalls() → persistPartial() с маркером [stopped]/[error]
   └─ RUN_STOPPED/RUN_ERROR → ChatEventService.publish()

8. Frontend: GET /api/chats/{id}/events
   ├─ Replay пропущенных событий (seq > fromSeq)
   └─ Живые события → applyChatEvent() → setChats()
```
