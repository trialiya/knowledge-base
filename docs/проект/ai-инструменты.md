# AI-инструменты

> **Связанные документы:** [Введение](введение.md) · [Архитектура](архитектура.md) · [Модели данных](модели-данных/.content.md) · [API Reference](api-reference.md) · [Конфигурация](конфигурация.md) · [Руководство по установке](руководство-по-установке.md)

Система предоставляет AI-ассистенту набор инструментов для работы с базой знаний, Git-репозиторием и системной информацией. Инструменты вызываются через `ToolController` (`POST /api/tools`).

Все инструменты используют **`CompactToolResultConverter`** — конвертер, который сжимает результаты в компактное превью (`resultGist`). Каждый DTO-результат реализует интерфейс `ToolCallResponseItem` с методом `toGist()`, возвращающим краткую сводку.

Список ниже — описание для разработчика; пользователю тот же набор виден в панели «Настройки → Инструменты». ## 0.1 Незаполненные аргументы

Слабые модели регулярно пропускают аргументы, которые схема помечает как
обязательные. Spring AI ничего с этим не делает: отсутствующий аргумент
доходит до `Method.invoke` как `null`. Для типа-обёртки это безобидно — тело
инструмента увидит `null` и ответит. Для **примитива** рефлексия не может его
распаковать и бросает `IllegalArgumentException` из самого `invoke`, а
значит — не `ToolExecutionException`, обработчик его не видит, и один
пропущенный `boolean` роняет весь прогон чата, а не один вызов.

Отсюда два правила, которым следуют все инструменты в пакете `functions`:

1. **Никаких примитивов в сигнатуре `@Tool`.** Только `Long` / `Integer` /
   `Boolean`, чтобы пропуск пришёл как `null` и на него можно было ответить.
2. **На пропуск отвечают осознанно** — через `ToolArgs`
   (`io.github.trialiya.kb.tools`): либо значение по умолчанию
   (`orDefault`, `positiveOrDefault`), либо ошибка с именем аргумента
   (`requireText`, `requireContent`, `requireId`, `requireValue`,
   `requireInt`, `requireNonEmpty`). Ошибка возвращается модели как результат
   инструмента — она читает, какой аргумент заполнить, и повторяет вызов.

Значение по умолчанию ставится только там, где инструмент действительно может
без аргумента обойтись (в схеме `required = false`: лимиты, режимы, флаги).
То, о чём вызов вообще идёт — id, путь, поисковый запрос, записываемое
содержимое, — обязательно: подставлять вместо него нечего.

Разграничение пустой строки:

- для **имени** (id, путь, запрос, заголовок) пустая строка и пробелы — то же
  самое, что пропуск: `requireText`;
- для **содержимого** (тело файла, текст секции, замена в `editFile`) ошибка
  только на `null`: явная `""` — это осмысленная инструкция (создать пустой
  файл, удалить фрагмент), и путать её с пропуском нельзя: `requireContent`.

Инвариант «вызов без единого аргумента всегда получает ответ» закреплён тестом
`ToolArgumentGapsTest` — он находит инструменты сканированием пакета (новый
класс попадает под проверку сам, без правки теста) и гоняет каждый `@Tool`
через настоящий `MethodToolCallback` с телом `{}`. Примитив в сигнатуре
инструмента ломает этот тест. Там же лежит `PrimitiveArgumentTool` — намеренно
неправильный инструмент, ни к какому чату не подключённый: он фиксирует само
поведение Spring AI, и если очередная версия начнёт подставлять примитив сама
или хотя бы заворачивать ошибку в `ToolExecutionException`, тест упадёт с этим
объяснением, и правило можно будет пересмотреть.

## 1. Поиск и чтение документов

### `searchDocuments`
Гибридный поиск по документам (keyword + semantic). Результаты включают `parentList` — хлебные крошки (предки от корня до родителя).
- **Параметры:** `query` (String), `mode` (hybrid|semantic|keyword), `threshold` (double), `limit` (int), `kwWeight` (double), `semWeight` (double)
- **Возвращает:** список документов с релевантностью и `parentList`

### `grepDocuments`
Поиск по **содержимому** документов — построчный, как `grepContent` по репозиторию. Отвечает на другой вопрос, чем `searchDocuments`: тот ранжирует документы по релевантности теме, этот говорит, где именно встречается формулировка, — с этого начинается правка.
- **Параметры:** `pattern` (String), `regex` (Boolean|null, default true), `contextLines` (Integer|null, default 1, 0–10), `maxResults` (Integer|null, default 50, 1–200), `documentId` (Long|null — искать только внутри этого документа и его потомков)
- **Возвращает:** список `DocumentGrepMatch` с полями: `documentId`, `title`, `sectionPath` (путь секции в адресации `getDocumentOutline` — прямой вход в `getDocumentSection` / `updateDocumentSection`), `matchLine` (номер строки), `text` (блок строк)
- **Формат `text`:** тот же, что у `git grep -C`: строки совпадений обрамлены `:N:`, контекст — `-N-`. Без контекста (`contextLines=0`) разметки нет, возвращается сама строка
- **Регистр:** поиск всегда регистронезависимый, включая кириллицу (`CASE_INSENSITIVE | UNICODE_CASE`)
- **Реализация:** поиск идёт в Java (`DocumentGrep`), а не в SQL: `REGEXP` в PostgreSQL и H2 пишется по-разному, а путь секции всё равно требует разбора markdown. Тела документов читаются по одному (`findDescriptionById` поверх структурного списка строк) — как в экспорте и синхронизации, чтобы grep не был операцией, которая утаскивает всю базу в heap. Чтобы это не стоило запроса на каждый документ базы, кандидаты сначала отсекаются в SQL по `ILIKE`, когда шаблон — обычная строка (без regex-метасимволов; при `regex=true` тоже — большинство шаблонов метасимволов не содержит). Настоящий regex префильтра не имеет и проходит по всем телам

### `findDocumentsByName`
Поиск документов по названию (точное или частичное совпадение).
- **Параметры:** `name` (String)
- **Возвращает:** список документов (сначала точные совпадения)

### `getDocument`
Получение документа по ID с полным содержимым и дочерними узлами.
- **Параметры:** `documentId` (String)
- **Возвращает:** `DocumentDto`

### `getTreeSkeleton`
Получение всей структуры базы знаний (id, title, type, parentId).
- **Параметры:** нет
- **Возвращает:** плоский список всех узлов

## 2. Управление документами

### `createDocument`
Создание нового документа или папки.
- **Параметры:** `title` (String), `type` (document|folder), `parentId` (String|null), `description` (String)
- **Возвращает:** созданный документ

### `updateDocument`
Обновление существующего документа (название и/или содержимое).
- **Параметры:** `documentId` (Long), `title` (String|null), `description` (String|null) — хотя бы одно из `title`/`description` должно быть заполнено, иначе ошибка
- **Возвращает:** обновлённый документ

### `editDocument`
Точечная правка документа: замена точного фрагмента `oldString` на `newString` в его содержимом — документный аналог `editFile`.
- **Параметры:** `documentId` (Long), `oldString` (String), `newString` (String — пропуск это ошибка, явная `""` удаляет фрагмент), `replaceAll` (Boolean|null, default false)
- **Возвращает:** обновлённый документ (`DocumentShort`)
- **Алгоритм:** точное посимвольное совпадение. Ни одного совпадения или больше одного (без `replaceAll`) — ошибка с указанием, что делать дальше
- **Ни чтения заранее, ни `expectedDescriptionVersion`:** контракт точного совпадения несёт и то, и другое. Фрагмент, который встречается в сохранённом тексте ровно один раз, взят из текущего текста; фрагмент, которого там уже нет, даёт ошибку с требованием перечитать — то же самое, что сказал бы конфликт версий, только на вызов раньше. Замена уходит в `DocumentService.patchDescription(id, patch)` — версию не проверяет, всё остальное (снимок истории, оптимистичная блокировка, инкремент `descriptionVersion`, переиндексация) как у обычного обновления
- **Когда что:** `editDocument` — заменить формулировку; `updateDocumentSection` — переписать секцию целиком; `updateDocument` — переписать документ целиком

## 4. Работа с Git-репозиторием

Все инструменты чтения обслуживают **отслеживаемые** файлы (по индексу Git; `.gitignore` исключён,
как в самом git) плюс untracked-файлы, которые проекту явно разрешили Ant-глобами
`kb.projects[].allow-globs` (см. [Конфигурация](конфигурация.md)). Внутри этих глобов истина —
рабочее дерево: `.gitignore` там ничего не скрывает. Такие файлы видны в дереве и в поиске по
имени и читаются, но **создать** файл в этой зоне нельзя, а `grepContent` заходит туда только по
явному `includeUntracked=true`. **Править** их можно только при `kb.projects[].untracked-edit-enabled`
(по умолчанию выключено — зона read-only); там, где можно, правка не индексирует файл, он остаётся
untracked. В выдаче инструментов они помечены `[untracked]`: у узла дерева и у `getFileContent` —
поле `tracked=false`, в списке изменений — статус `U`. Что разрешено этому проекту, модели сказано
в системном промпте.

### `getFileTree`
Получение дерева файлов репозитория (один уровень).
- **Параметры:** `path` (String|null — корень), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком `GitFileNode` в `result`

### `getFileContent`
Получение содержимого файла из репозитория.
- **Параметры:** `filePath` (String), `fromLine` (int|null), `toLine` (int|null), `project` (String|null — прочитать другой репозиторий вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и `GitFileContent` в `result`; поля `GitFileContent`: `path`, `content` (текст или null для бинарных), `binary`, `sizeBytes`, `language` (определяется по расширению), `lineCount` (всего строк), `truncated` (true если вернулась только часть), `fromLine`/`toLine` (фактический диапазон)
- **Для больших файлов (>512 КБ)** без указания диапазона возвращается фрагмент: начало + конец, `truncated=true`

### `getFileOutline`
Структурный анализ файла кода (классы, методы, поля и т.д.).
- **Параметры:** `filePath` (String), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и `GitFileOutline` в `result` (поля `path`, `language`, `lineCount`, `parser`) со списком `GitSymbol` (имя, `startLine`, `endLine`)
- **Движок:** tree-sitter (Java, TypeScript, Python, SQL) → фолбэк на regex при недоступности tree-sitter. Поле `parser` показывает, какой движок использован (`tree-sitter` или `regex`).

### `searchFiles`
Поиск файлов в репозитории по имени/пути.
- **Параметры:** `pattern` (String), `maxResults` (int, default 20), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком найденных файлов (`GitFileNode`) в `result`

### `grepContent`
Поиск текста внутри файлов репозитория (git grep).
- **Параметры:** `pattern` (String), `pathGlob` (String|null — по правилам git pathspec: без wildcard это префикс пути (`notes` — весь каталог), а wildcard переходит через `/` (`*.java` — любой `.java` на любой глубине)), `regex` (Boolean|null, default true), `contextLines` (Integer|null, default 1), `maxResults` (Integer|null, default 50), `includeUntracked` (Boolean|null, default false — искать ещё и в untracked-файлах, разрешённых проекту `allow-globs`), `project` (String|null — искать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком `GitGrepMatch` в `result`; поля совпадения: `path`, `matchLine` (int — номер строки совпадения), `text` (строка с совпадением)
- **Предупреждение:** если pattern содержит regex-символы (`|`, `.*`, `^`, `$` и др.) но `regex=false` — возвращается предупреждение

### `getCommitLog`
История коммитов.
- **Параметры:** `maxCount` (Integer|null, default 20, max 100), `filePath` (String|null), `includeMessageBody` (Boolean|null, default false — заполнить `body` полным сообщением каждого коммита), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком `GitCommit` в `result`. `message` — subject (первый абзац, переносы склеены пробелами); всё, что ниже первой пустой строки, лежит в `body` и заполняется только при `includeMessageBody=true`. Флаг здесь именно потому, что тело коммита в этом проекте идёт на тысячи символов: два десятка коммитов с телами — это десятки тысяч токенов контекста за ответ на вопрос «какие вообще были коммиты»

### `getCommitDiff`
Изменения для указанного коммита.
- **Параметры:** `commitHashes` (String), `includePatch` (Boolean|null, default false), `filePath` (String|null), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком `GitCommit` с вложенными `GitDiffEntry` + diff (опционально) в `result`
- **Тело сообщения здесь без флага, но только когда хеш один:** спросили про названный коммит — `body` рядом с его диффом самая дешёвая половина ответа на «почему это меняли». На списке из нескольких хешей тела не возвращаются: иначе через `getCommitDiff` вернулась бы ровно та цена контекста, ради которой в `getCommitLog` заведён флаг. Отсюда и разделение ролей: `getCommitLog` — указатель (по строке на коммит), `getCommitDiff` — разбор одного

### `getUncommittedChanges`
Незакоммиченные изменения отслеживаемых файлов в рабочей директории (staged и unstaged).
- **Параметры:** `includePatch` (Boolean|null, default false), `project` (String|null — работать в другом репозитории вместо проекта чата, см. «Проект в аргументах» ниже)
- **Возвращает:** `ToolResult` с id репозитория и списком изменённых файлов (`GitDiffEntry`) + diff (опционально) в `result`
- **Ограничения:** untracked-файлы не возвращаются (в том числе попадающие под `.gitignore`) — у них нет истории в Git и их нельзя прочитать через `getFileContent`. Исключение — untracked-файлы, разрешённые `kb.projects[].allow-globs`: они читаемы (и, при `untracked-edit-enabled`, ассистент их правит), поэтому показываются со статусом `U` — целиком как содержимое, блоба для diff у них нет. Статус отдельный, а не `A`: в индексе таких файлов нет, и сами по себе в коммит они не попадут. Файлы, созданные через `createFile`/`editFile` вне глобов, попадают в индекс и показываются со статусом `A`

### `createFile`
Создание нового файла в репозитории (рабочее дерево остаётся не закоммичено).
- **Параметры:** `filePath` (String), `content` (String — пропуск это ошибка, явная `""` создаёт пустой файл)
- **Возвращает:** `GitEditResult` с полями: `path`, `action` (create|overwrite|skip), `message` (статус)
- **Ограничения:** 
  - Инструмент доступен, только когда проект принимает запись (`kb.projects[].edit-enabled`) И его рабочее дерево доступно на запись
  - По умолчанию отключён (read-only)
  - Если файл уже существует — возвращается ошибка (используйте `editFile`)
  - В зоне `allow-globs` создавать нельзя никогда — даже при `untracked-edit-enabled`

### `editFile`
Редактирование существующего файла в репозитории (замена текста, точное совпадение).
- **Параметры:** `filePath` (String), `oldString` (String), `newString` (String — пропуск это ошибка, явная `""` удаляет фрагмент), `replaceAll` (Boolean|null, default false)
- **Возвращает:** `GitEditResult` с полями: `path`, `action`, `message`, `oldContent` (оригинал), `newContent` (результат)
- **Алгоритм:** точное совпадение `oldString` в файле. Если совпадений несколько или ни одного — ошибка. Если ровно одно — замена и сохранение
- **Ограничения:**
  - Доступен, только когда проект принимает запись (`kb.projects[].edit-enabled`) И его рабочее дерево доступно на запись
  - untracked-файл, разрешённый `allow-globs`, правится только при `kb.projects[].untracked-edit-enabled`; иначе — отказ с указанием, что зона отдана на чтение
  - **Чтения заранее не требуется** — безопасность даёт сам контракт точного совпадения: привести уникальный фрагмент может только тот, кто видел текущее содержимое, а несовпадение возвращает ошибку с именем инструмента для перечитывания. То же и в скриптовой песочнице: `kb.edit` чтения не требует. Правило «сначала прочитай» осталось только у записи файла целиком — `kb.writeBytes` (см. `ScriptSession.requireRead`), где дословного фрагмента нет вовсе
  - По умолчанию отключён (read-only)

> **Примечание:** `createFile` и `editFile` НЕ коммитят файлы — изменения остаются в рабочем дереве для пользователя. Цель: дать AI возможность подготовить код, а пользователю полный контроль над коммитом и наличием автоматизма.

### Проект в аргументах

Какой репозиторий читает инструмент, решает не аргумент, а прогон: проект чата
едет в `ToolContext` (`ProjectContext`), и `GitRegistry` отдаёт по нему нужный
`GitService`. В схему инструмента `ToolContext` не попадает, поэтому модель
этого выбора не видит и заполнить его не может — и это защита, а не недоделка:
один неверный id в одном сгенерированном аргументе означал бы молча прочитанный
чужой репозиторий.

Необязательный аргумент `project` есть у **всех** read-only инструментов —
`getFileContent`, `grepContent`, `getFileTree`, `searchFiles`, `getFileOutline`,
`getCommitLog`, `getCommitDiff`, `getUncommittedChanges`, `searchCodebase` и
`runScript`. Он перекрывает проект прогона на один вызов и существует ради
случая, который контекст обслужить не может: вопроса, заданного намеренно про
другой репозиторий — кросс-проектного сравнения («как это сделано в A, а как в
B») или возврата к проекту, который в этом чате выбирали раньше и с которого уже
ушли. Пропущенный или пустой `project` означает проект чата, так что обычный
вызов остаётся прежним.

Назвать чужой проект модель может только зная его id, а знать ей его неоткуда —
поэтому список выдаётся блоком `<active-project>` на последнем вопросе окна
(`ActiveProjectNotice` поверх `ProjectPromptService`): активный проект, затем те,
на которых чат уже работал, затем остальные настроенные. Проекты, чей репозиторий
не открылся, не перечисляются вовсе. Выдуманный id падает на
`ProjectCatalog#require` с перечислением настроенных, то есть громко.

В системном промпте этого блока нет намеренно: проект — свойство разговора, а не
приложения, и сказанное один раз на весь чат относилось бы и к сообщениям,
прочитанным в другом репозитории. Блок собирается на чтении, в БД не попадает и
стоит ровно на одном ряду — том, который открывает текущий ход.

Чату, который репозиторий менял, блок печатает и таймлайн — с какого по какое
сообщение где прожито. Номера те же, что в `[msg:N]`, так что диапазон можно не
только прочесть, но и раскрыть через `getOriginalMessages`. Собирается он
`ProjectTrace` из двух источников: носителей в живой истории (`meta.project` —
базовый штамп первого сообщения и маркеры смен) и спанов на последней
строке-сводке (`meta.visitedProjects`), куда след уезжает при сжатии. Сводки
накопительные — каждая наследует спаны предыдущей, поэтому за исчезнувшими из
окна маркерами тянуться не приходится. Чат, не менявший репозиторий, таймлайна не
получает вовсе: строка «messages 1-140» не сообщает ничего.

Цена такого аргумента — молчаливая подмена репозитория, поэтому каждый ответ
**называет проект, который на самом деле отвечал**. Называет один раз: git-
инструменты отдают ответ в общей обёртке `ToolResult` — `{"project": "...",
"result": <ответ>}`, — а элементы выдачи id не повторяют. Вызов читает ровно один
репозиторий, и пятьсот копий одного id в дереве файлов стоили бы контекста на
пустом месте. `ScriptResult` и `SearchAgentResult` обёртки не носят: у них
`project` и так собственное поле верхнего уровня. Форма для модели одна и та же —
`project` рядом с ответом.

Обёртка — место и для будущих общих параметров ответа: добавить их к `ToolResult`
дешевле, чем к каждому DTO по отдельности. Разворачивает её
`RecordingToolCallback`, так что сводка и метаданные вызова считаются по
содержимому, как и у инструментов без обёртки. REST-контроллеры отдают DTO голыми:
там репозиторий назвал сам вызывающий, параметром запроса.

Промпт (`sys.md`) требует брать id для ссылки `/files?path=…&project=…` из
ответа, а не из активного проекта — иначе ссылка на файл соседнего репозитория
открыла бы файл с тем же путём в своём.

Эхо — не только для модели. Ответ, привязанный к репозиторию, реализует
`ProjectScoped`; `RecordingToolCallback` снимает с него id в
`ToolInvocation#project`, а `ToolInvocationCollector#hasSeenFile` по нему решает,
в том ли репозитории модель видела файл, — чтобы чтение в одном не засчиталось за
«видели» для записи одноимённого пути в другом. Списка имён инструментов для
этого нет: сверяется то, что вернул сам вызов, а `null` означает «результат к
репозиторию не привязан» (документы, вложения).

Правки (`createFile`, `editFile`) аргумента не получают: писать в репозиторий,
который пользователь в этом чате не выбирал, — не тот риск, который окупается
удобством. По той же причине `runScript` с чужим проектом идёт **read-only**,
сколько бы прав ни было у того проекта: назвать соседний репозиторий даёт чтение,
но не запись, иначе аргумент стал бы обходом выбора пользователя. Записывать —
через смену проекта в чате.

## 5. Умный поиск (searchCodebase)

### `searchCodebase`
Многошаговый поиск по коду репозитория и базе знаний через сабагента. В отличие от одиночного `grepContent`, сабагент сам итеративно вызывает grep, обзор структуры и чтение файлов, возвращая сжатый отчёт с цитатами `path:line`.

- **Параметры:**
  - `task` (String) — подробная постановка задачи на естественном языке: что искать и зачем. Чем конкретнее (термины, имена классов/методов, область), тем лучше результат. Набор ключевых слов без «зачем» тоже валиден — сабагент обязан искать по нему, а не переспрашивать: вызов одноразовый, ответить на уточняющий вопрос некому.
  - `context` (String, опционально) — брифинг от вызывающей модели: что разговор уже установил (находки прошлых поисков, отброшенные пути и имена, ограничение пользователя за вопросом) и чего он хочет от отчёта сверх самой задачи. Единственный канал: сабагент разговора не видит и узнать это иначе не может, поэтому факты надо называть, а не ссылаться на «сказанное выше». В запросе встаёт после задачи, разделом `KNOWN TO THE CALLER`, и повторяется вместе с ней при финальной суммаризации. Для сабагента это брифинг, а не улика: своей находкой он его не выдаёт, а противоречие ему называет в отчёте (см. `prompt/search-agent.md`)
  - `scope` (String, опционально) — область поиска: `"code"` | `"docs"` | `"all"` (по умолчанию all)
  - `pathGlob` (String, опционально) — glob для ограничения путей в коде, например `"backend/**/*.java"`. null — без ограничения.
  - `project` (String, опционально) — искать в другом репозитории вместо проекта чата (см. «Проект в аргументах» выше). Проект решается один раз здесь и уезжает в `ToolContext` сабагента: весь его прогон читает названный репозиторий. Сам сабагент о проектах не знает — в его промпте их нет, — поэтому по своей воле никуда не уходит.
- **Возвращает:** `SearchAgentResult` с полями:
  - `project` (String) — id репозитория, в котором сабагент искал: без него цитаты `path:line` не к чему привязать
  - `report` (String) — сжатый отчёт с цитатами `path:line`
  - `complete` (boolean) — true если сабагент завершил поиск самостоятельно; false если исчерпан бюджет итераций или произошла ошибка
  - `iterations` (int) — количество раундов tool-call
  - `durationMs` (long, скрыто от модели) — длительность в миллисекундах

**Когда использовать `searchCodebase` вместо `grepContent`:**
- `grepContent` — простое точное совпадение, один-два запроса («где вызывается `save()`?»)
- `searchCodebase` — широкий или неоднозначный вопрос, требующий нескольких шагов (grep → структура → чтение фрагментов) и/или объединения кода и документов («как устроена авторизация и где она проверяется?»)

**Ограничения сабагента:**
- Только read-only инструменты (grepContent, searchFiles, getFileTree, getFileOutline, getFileContent, searchDocuments, grepDocuments, findDocumentsByName, getDocument, getDocumentOutline, getDocumentSection, getTreeSkeleton)
- Не может вызывать сам себя (защита от рекурсии через `allowed-tools`)
- Жёсткий лимит итераций (`maxIterations`, по умолчанию 30) — при исчерпании принудительная суммаризация
- Отдельная модель (может отличаться от основной — например, более дешёвая/быстрая)
- Настраивается через `kb.search.subagent.*` в [Конфигурации](конфигурация.md)

## 6. Системные инструменты

### `getCurrentDateTime`
Текущие дата и время в часовом поясе пользователя.
- **Параметры:** нет
- **Возвращает:** строка с датой/временем

### `getUserName`
Имя текущего пользователя.
- **Параметры:** нет
- **Возвращает:** имя пользователя

### `getChatId`
ID текущего чата.
- **Параметры:** нет
- **Возвращает:** ID чата

### `getOriginalMessages`
Получение оригинальных сообщений чата по позициям.
- **Параметры:** `positions` (List of int)
- **Возвращает:** полные тексты сообщений

### `recordChatInsights`
Запись темы разговора (вызывается автоматически при каждом ответе).
- **Параметры:** `topic` (String — 3 слова)
- **Возвращает:** void

### `readSkill`
Загрузка навыка — инструкции по требованию. Навыки двух сортов, и объявляются они в разных местах промпта намеренно (`SkillService`):

- **Встроенные** — markdown-файлы в `prompt/skills/`; чтобы завести следующий, достаточно положить туда файл и добавить строку в каталог `SkillService`. Каталог с триггерами («когда загружать») модель видит в системном промпте (плейсхолдер `{skill_catalogue}`, раздел «Skills») — одинаковый для всех моделей. Слабой (`weak: true`) вдобавок велит загрузить навык само руководство по скриптам: его расширенная половина (`script-run-extended.md`) сегодня и есть это указание, потому что ждать от такой модели выбора по триггеру не приходится.
- **Проектные** — файлы рабочего дерева проекта, объявленные в `kb.projects[].skills` (имя, триггер, путь). Их список — свойство разговора, а не приложения: он меняется со сменой проекта, поэтому объявляется не в системном промпте (там он рвал бы кэш промпта при каждой смене), а в блоке `<active-project>` на текущем вопросе. Загружаются они только пока их проект активен — навык прежнего проекта неотличим от несуществующего; текст читается с диска в момент вызова, так что pull или смена ветки обновляют его без рестарта (файла может и не быть на текущей ветке — это ответ инструмента, не 500; предел размера — 64 КБ).

Встроенных навыков сейчас два — `script-writing` и `script-editing`, оба про `runScript`, поэтому они существуют только при `kb.script.enabled`, а `script-editing` виден лишь там, где скриптам можно писать (`ScriptEditPolicy`, попроектно); сам инструмент регистрируется, когда есть хоть один навык, встроенный или проектный. Текст навыка живёт в контексте как результат вызова и не переживает сжатие истории: суммаризатор и компактор фиксируют в сводке только факт загрузки, а модель по правилу из каталога перечитывает навык заново (`SkillService`, `SkillFunction`).
- **Параметры:** `name` (String — имя из каталога)
- **Возвращает:** `name`, `content` — текст инструкции целиком

## 7. Компактные результаты (CompactToolResultConverter)

Все инструменты используют `CompactToolResultConverter`, который преобразует полные DTO в сжатое превью:

- **`resultGist`** — краткая текстовая сводка результата (например, `"size=1\n4512b4a 2026-06-03 Trialiya: feature: show compact tool result previews..."`)
- **`ToolCallResponseItem`** — интерфейс с методом `toGist()`, реализуемый всеми DTO: `GitFileContent`, `GitFileOutline`, `GitCommit`, `GitGrepMatch`, `GitFileNode`, `GitDiffEntry`, `DocumentDto`, `DocumentGrepMatch`, `AttachmentDto`, `SearchAgentResult`
- **`OutlineResult`** — DTO-обёртка для `getFileOutline`, содержит `path`, `language`, `lineCount`, `parser`, `symbols` и реализует `ToolCallResponseItem`
- **`SearchAgentResult`** — результат `searchCodebase`, реализует `ToolCallResponseItem` и `ToolCallResultMetaProvider`. Gist: `"⚠ неполно • 3 шаг(ов) • краткий фрагмент отчёта…"`. ResultMeta: `complete`, `iterations`, `durationMs`, `reportChars`, `model`, `usage`. `durationMs`, `model` и `usage` помечены `@JsonIgnore` и модели не отдаются — они операционные, и в деталях вызова их читает человек (см. [обзор чат-системы](обзор-чат-системы.md), §6.4).

### ToolInvocation

`ToolInvocation` — отдельный record (не вложен в `ToolInvocationCollector`):

| Поле | Тип | Описание |
|---|---|---|
| `name` | String | Имя инструмента |
| `arguments` | Map | Параметры вызова |
| `status` | String | `STARTED`, `OK`, `ERROR` |
| `error` | String | Сообщение об ошибке (при ERROR) |
| `resultGist` | String | Краткая сводка результата (из `CompactToolResultConverter`) |
