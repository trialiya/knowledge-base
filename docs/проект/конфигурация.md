### Проекты (`kb.projects`)

Репозитории, с которыми работает ассистент. **Пока поддерживается ровно один включённый**, и вторая
живая запись не игнорируется молча, а роняет старт (`ProjectCatalog`): ссылки на файлы
(`/files?path=…`) и панель «Файлы» проекта не несут, поэтому во втором репозитории путь
`backend/build.gradle` открылся бы не тот — а это ошибка, которую никто не заметит.

Записи с `enabled: false` не считаются и не проверяются — так второй проект и готовят заранее: блок
лежит в конфигурации (путь может быть ещё не смонтирован), пока флаг не переключат. Для приложения
выключенного проекта нет: репозиторий не открывается, в `GET /api/chats/projects` его нет, вызов с
его id отклоняется. Чат, который его выбрал, сохраняет id и едет на дефолтном проекте — по этому
расхождению фронт и понимает, что нужно сказать «проект больше недоступен».

Бэкенд при этом уже адресует репозиторий по `id` на всём пути: чат хранит выбранный проект
(`chat_topic.project`, `GET /api/chats/projects` + `PUT /api/chats/{id}/project`), прогон везёт его
в `ToolContext` (`projectId`), инструменты и `/api/git/**` резолвят репозиторий через
`GitRegistry`. Вызов, который проект не назвал, получает **первый** проект списка.

```yaml
kb:
  projects:
    - id: default                          # [a-z0-9._-], попадёт в URL как есть
      label: ${PROJECT_LABEL:Project}      # опционально; по умолчанию = id
      path: ${PROJECT_PATH:${kb.git.project-path}}
      # edit-enabled: false                # опционально; по умолчанию = kb.git.edit-enabled
```

| Параметр | Значение | Описание |
|---|---|---|
| `kb.projects[].id` | — | Ключ проекта; обязателен, только строчные буквы, цифры, `. _ -` |
| `kb.projects[].label` | `= id` | Отображаемое имя |
| `kb.projects[].path` | `${PROJECT_PATH}` | Путь к Git-репозиторию |
| `kb.projects[].edit-enabled` | `= kb.git.edit-enabled` | Разрешить правку рабочего дерева **этого** репозитория |
| `kb.projects[].enabled` | `true` | `false` — проект не обслуживается и не проверяется: заготовка на будущее |

### Git (`kb.git.*`)

| Параметр | Значение | Описание |
|---|---|---|
| `kb.git.project-path` | — | Прежняя форма записи единственного проекта. Читается только когда `kb.projects` не задан вовсе: тогда из неё собирается проект с `id=default`. В поставляемом `application.yaml` она подставляется как значение по умолчанию для `kb.projects[0].path`, поэтому деплой, задающий только `PROJECT_PATH`/`KB_GIT_PROJECT_PATH`, работает без изменений |
| `kb.git.edit-enabled` | `${KB_GIT_EDIT_ENABLED:false}` | Значение по умолчанию для `kb.projects[].edit-enabled`: открыть модели инструменты `createFile`/`editFile` (`GitEditFunction`). По умолчанию выключено — только чтение. Даже при `true` инструменты не регистрируются, если ни одно рабочее дерево недоступно на запись (например, read-only mount); вызов к проекту, который запись не принимает, отклоняется по имени проекта (`GitRegistry.requireEditable`) |

### Скрипты (`kb.script.*`)

Конфигурация через `ScriptProperties` (`config/model/ScriptProperties.java`) — record с префиксом `kb.script`. Управляет инструментом `runScript` (`ScriptFunction`/`ScriptRunner`): модель пишет один JS-скрипт, который сам обходит репозиторий через объект `kb`, вместо серии отдельных вызовов `grepContent`/`getFileContent`/... Снимок этой конфигурации (без текстов руководств) отдаётся панели «Настройки → Скрипты» через `GET /api/settings/ai-config` (`SettingsController.ScriptSection`, см. [API Reference](api-reference.md)) вместе с пробным запуском (`POST /api/settings/script/run`, `ScriptTestController`) — тем же движком, но всегда read-only.

```yaml
kb:
  script:
    enabled: ${KB_SCRIPT_ENABLED:false}        # выдать ли runScript модели вообще
    edit-enabled: ${KB_SCRIPT_EDIT_ENABLED:true}  # разрешить запись из скриптов (kb.edit/kb.create, kb.writeBytes/kb.createBytes)
    guide: classpath:prompt/script-run.md
    extended-guide: classpath:prompt/script-run-extended.md
    edit-guide: classpath:prompt/script-run-edit.md
    extended-edit-guide: classpath:prompt/script-run-edit-extended.md
    timeout: ${KB_SCRIPT_TIMEOUT:10s}   # бюджет по умолчанию на один прогон
    max-timeout: 30s                    # потолок для timeoutSeconds из вызова
    cancel-poll: 50ms                   # период опроса сторожевого потока
    limits:
      max-files-read: 0      # 0 → дефолт из кода (2000)
      max-bytes-read: 0      # 0 → дефолт из кода (32MB)
      max-calls: 0           # 0 → дефолт из кода (2000)
      max-log-chars: 0       # 0 → дефолт из кода (20000)
      max-result-chars: 0    # 0 → дефолт из кода (20000)
      max-edited-files: 0    # 0 → дефолт из кода (20)
      max-edited-bytes: 0    # 0 → дефолт из кода (256KB)
    deny-globs: []   # пути, скрытые от скриптов поверх .gitignore
    allow-globs: []  # непусто — видны только совпадающие пути
```

- **`enabled`** — по умолчанию выключено: выполнение присланного кода — поверхность отказа в обслуживании (heap на community-сборке GraalJS ничем не ограничен, см. javadoc `ScriptRunner`), а не только вопрос доступа к файлам. Явный opt-in, как и `kb.mcp.enabled`.
- **`edit-enabled`** — необходимо, но не достаточно: запись из скриптов действует только когда проект принимает запись (`kb.projects[].edit-enabled`, по умолчанию `kb.git.edit-enabled`) и его рабочее дерево доступно на запись — те же условия, что открывают `editFile`/`createFile` (см. `ScriptEditPolicy`, `GitRegistry.editsAllowed`). Отдельный флаг — чтобы можно было держать обычные инструменты правки включёнными, а скриптам отдавать только чтение.
- **`guide`/`extended-guide`/`edit-guide`/`extended-edit-guide`** — руководство в системном промпте, в четырёх комбинациях (справочник × обучающая часть, чтение × запись), собранных один раз при старте (`ScriptGuideService`). Обучающая половина (`extended-*`) добавляется только для прогона, чья модель помечена `weak` (`ChatModelProperties.ModelOption#weak`, см. «Модели чата» ниже) — сильная модель получает только справочник по `kb`, лимитам и видам ошибок.
- **`limits.*`** — бюджеты одного прогона; ограничивают бэкенд (файлы, байты, вызовы `kb.*`, символы в логе/результате, файлы/байты на запись), а не контекст модели — в него попадают только возвращённое значение и лог, у которых свои пределы. Повторный `kb.*`-вызов с теми же аргументами в рамках одного прогона отвечается из кэша и не тратит бюджет (`ScriptSession#call`).
- **`deny-globs`/`allow-globs`** — видимость файлов поверх правил `GitService` (только отслеживаемые, `.gitignore` уже исключён): `deny-globs` прячет дополнительно, `allow-globs`, если задан, сужает видимое до совпадающего.

### Модели чата (`kb.chat.*`)

Конфигурация через `ChatModelProperties` (`config/model/ChatModelProperties.java`) — record с префиксом `kb.chat`:

```yaml
kb:
  chat:
    default-model:
      id: ${AI_MODEL}              # ID дефолтной модели
      label: ${AI_MODEL_LABEL:Default}  # Название в UI
      weak: ${AI_MODEL_WEAK:true}  # Нужен ли этой модели обучающий раздел runScript
    models:                         # Дополнительные модели (опционально)
      - id: ${KB_CHAT_MODELS_0_ID}
        label: ${KB_CHAT_MODELS_0_LABEL}
        weak: ${KB_CHAT_MODELS_0_WEAK:true}
      - id: ${KB_CHAT_MODELS_1_ID}
        label: ${KB_CHAT_MODELS_1_LABEL}
        weak: ${KB_CHAT_MODELS_1_WEAK:true}
        base-url: ${KB_CHAT_MODELS_1_BASE_URL:}   # Свой эндпоинт (опционально)
        api-key: ${KB_CHAT_MODELS_1_API_KEY:}     # Обязателен, если задан base-url
```

#### Свой хост и токен у отдельной модели

`base-url` и `api-key` у элемента `kb.chat.models` — необязательные. Как это читается:

| `base-url` | `api-key` | Что получается |
|---|---|---|
| не задан | не задан | Обычный случай: модель отвечает с общего эндпоинта `spring.ai.openai.base-url` тем же ключом `spring.ai.openai.api-key` |
| задан | задан | Модель получает собственное соединение: свой HTTP-клиент, свой адрес и свой токен |
| задан | не задан | **Ошибка при старте**: чужой хост с ключом от хоста по умолчанию — комбинация, которой никто не имеет в виду, поэтому приложение не поднимается |
| не задан | задан | Тот же хост, отдельный токен (другой аккаунт или квота) — тоже отдельное соединение |

Соединения строит `ChatModelRegistry` (`config/ChatModelRegistry.java`) один раз на старте, а не на
запрос: у OkHttp-клиента свой пул соединений. Всё, кроме адреса и токена, наследуется от
автоконфигурации — таймаут, ретраи, прокси, заголовки и весь блок
`spring.ai.openai.chat.options.*`, так что второй эндпоинт остаётся вторым эндпоинтом и не
превращается втихую во второй набор параметров генерации. Исключение — признаки провайдера (GitHub
Models, Microsoft Foundry): к другому хосту они не относятся и при заданном `base-url` сбрасываются,
иначе Spring AI переписал бы адрес обратно на адрес провайдера. Провайдер нового хоста по-прежнему
определяется по самому адресу. По id модели выбирается и клиент
(`ChatClientRegistry`, у всех клиентов одна и та же цепочка advisor-ов и один и тот же набор
инструментов), и соединение саб-агента поиска, если `kb.search.subagent.model-id` указывает на такую
модель.

Оба поля работают только внутри `kb.chat.models`. У `kb.chat.default-model` эндпоинт — это и есть
`spring.ai.openai.*`, поэтому `base-url`/`api-key` там отклоняются при старте: связать их было бы не с
чем, а панель настроек показывала бы пилюлю «отдельное подключение» для соединения, которого нет.
Если своё подключение нужно именно модели по умолчанию, добавьте её в `kb.chat.models` с тем же `id` —
такая запись обслуживает и прогоны, где модель явно не выбрана.

Наружу (`GET /api/chats/models`, `GET /api/settings/ai-config`) ни адрес, ни токен не отдаются —
только флаг `ownEndpoint`, по которому «Настройки → Модели» рисуют пилюлю «отдельное подключение».
`toString` у `ModelOption` печатает вместо токена `***`: `@JsonIgnore` закрывает только API, а
свойства попадают ещё и в логи.

`weak` решает, получает ли модель расширенную половину руководства по `runScript`
(`script-run-extended.md` и её приписку про правки) — см. `ScriptGuideService`. По умолчанию
`true` (безопасное предположение для любой модели, для которой явно не сказано обратное); не
задан — значит модель считается слабой. Раньше это было одно поле деплоя
(`kb.script.extended-guide-enabled`), теперь — свойство каждой модели: сильная модель в списке
экономит контекст, а слабая рядом всё ещё получает подсказки.

### Режимы ассистента (`kb.chat.modes`)

Список готовых «режимов» ассистента (Аналитик, Разработчик, Тестировщик, …) — параллель `kb.chat.default-model`/`kb.chat.models`. Конфигурация через `ChatModeProperties` (`config/model/ChatModeProperties.java`) — record с префиксом `kb.chat`. Каждый режим подставляет свой фрагмент инструкций в системный промпт через плейсхолдер `{mode_instructions}` (см. `prompt/sys.md` и `ChatModeService`); наружу (`GET /api/chats/modes`) отдаются только `id`/`label`, сам текст промпта остаётся на бэкенде.

```yaml
kb:
  chat:
    modes:
      - id: analytic
        label: Аналитик
        prompt: classpath:prompt/mode-analytic.md
      - id: developer
        label: Разработчик
        prompt: classpath:prompt/mode-developer.md
      - id: tester
        label: Тестировщик
        prompt: classpath:prompt/mode-tester.md
```

По умолчанию режим не выбран («без режима» — плейсхолдер `{mode_instructions}` заполняется пустой строкой; фронт хранит и передаёт выбранный режим так же, как модель, см. `PUT /api/chats/{conversationId}/mode` в [API Reference](api-reference.md)).

### Системный промпт (`kb.system-prompt.*`)

Конфигурация через `SystemPromptProperties` (`config/model/SystemPromptProperties.java`) — record с префиксом `kb.system-prompt`. Системный промпт разделён на две части:

- **`prompt`** (reference) — основные правила, таблица выбора инструментов, цепочки вызовов — отдаётся всем моделям
- **`extended-prompt`** (tutorial) — дерево решений, примеры работы, частые ошибки — добавляется только для «слабых» моделей (флаг `kb.chat.default-model.weak` / `kb.chat.models[].weak`)

Обе части подставляются в системный промпт через плейсхолдер `{system_extended}` в `prompt/sys.md` (см. `SystemPromptService` и `ChatRunService`):

```yaml
kb:
  system-prompt:
    prompt: classpath:prompt/sys.md                   # Справочник для всех моделей
    extended-prompt: classpath:prompt/sys-extended.md # Обучение для слабых моделей
```

Стратегия аналогична `kb.script.guide`/`kb.script.extended-guide` (см. выше): слабая модель получает подробные примеры и подсказки, сильная — только краткий справочник, чтобы сэкономить токены.

### ChatConfig — конфигурация чата

`ChatConfig` (`config/ChatConfig.java`) — центральный класс конфигурации чата. Создаёт бины:

- **chatRunExecutor** — `ExecutorService` на виртуальных потоках + `DelegatingSecurityContextExecutorService` (переносит `SecurityContext` на worker-поток). `destroyMethod = "shutdown"`
- **ChatMemory** — `MessageWindowChatMemory` с персистентным хранением через `ChatMemoryService`, скользящее окно 50 сообщений
- **SearchAgentService** — только если `kb.search.subagent.enabled=true`. Создаёт sub-agent с ограниченным набором read-only инструментов из `allowed-tools`
- **ChatToolset** — набор инструментов основного чата: встроенные (`@Tool` из пакета `functions`, каждый в обёртке `RecordingToolCallback`) и пришедшие с внешних MCP-серверов. Собран в одном месте, потому что читателей у него двое: `ChatClient` получает `all()`, а `ToolCatalogService` строит из тех же callbacks каталог для панели «Настройки → Инструменты» — так панель не может показать инструмент, которого у модели нет
- **ChatClient** — основной клиент Spring AI:
  - **ChatModel** — OpenAI-совместимая модель
  - **System Prompt** — загружается через `@Value("classpath:prompt/sys.md") Resource sysPrompt` и передаётся в `.defaultSystem(sysPrompt)`
  - **MessageChatMemoryAdvisor** — автоматически добавляет историю
  - **ToolCallbacks** — `.defaultTools(...)` с 6 ToolCallbacks: `TopicFunction`, `MessageLookupFunction`, `DocumentFunction`, `GitFunction`, `AttachmentFunction`, `SearchAgentFunction` (опционально)

### SecurityConfig — HTTP Basic Auth

`SecurityConfig` (`config/SecurityConfig.java`) — stateless HTTP Basic-аутентификация:

- **PasswordEncoder** — `BCryptPasswordEncoder`
- **InMemoryUserDetailsManager** — один пользователь из `SecurityProperties` (`kb.security.username`/`password`)
- **SecurityFilterChain** — CSRF отключён, `SessionCreationPolicy.STATELESS`, `/actuator/health` публичный, всё остальное требует аутентификации

```java
    public SecurityProperties {
        username = (username == null || username.isBlank()) ? "admin" : username;

    }
}
```

### sys.md — системный промпт

`prompt/sys.md` — системный промпт ассистента, загружаемый через `@Value` + `Resource`. Определяет:

- **Роль:** «Ассистент для работы с базой знаний»
- **Критические правила:** запрет на выдумку, скрытые инструменты, синтаксис ссылок `[Название](/?doc=ID)`
- **Алгоритм ответа:** вопрос → нужны ли данные → вызов инструмента → ответ
- **Скрытые инструменты:** `recordChatInsights`, `getUserName`, `getCurrentDateTime`, `getOriginalMessages` — вызываются фоново, не упоминаются пользователю
- **Git-репозиторий: общие ограничения** — read-only, только tracked файлы, diff'ы усекаются до 500 строк, файлы >512 КБ возвращаются фрагментом
- **Таблица выбора инструментов** — сопоставление задач и инструментов (вкл. `searchCodebase`)
- **searchFiles vs grepContent** — сравнительная таблица
- **Когда `searchCodebase`, а когда `grepContent`** — правила выбора
- **Цепочки вызовов** — правила оркестрации (поиск → чтение)
- **grepContent: шпаргалка по запросам** — таблица примеров с pattern, pathGlob, regex
- **Ссылки на сообщения** — `[msg:XYZ]` для цитирования позиций в чате

### search-agent.md — промпт sub-agent

`prompt/search-agent.md` — системный промпт search sub-agent, загружаемый через `@Value` + `Resource`. Определяет:

- **Роль:** «специалист по поиску», только чтение
- **Стратегия:** разбить задачу на термины → grep/search → getFileOutline → getFileContent с диапазоном
- **Ограничения git-инструментов**
- **searchFiles vs grepContent** — сравнительная таблица
- **grepContent: шпаргалка по запросам**
- **Жёсткие правила:** не выдумывать, исправлять ошибки аргументов, экономить токены
- **Формат ответа:** Итог, Места (path:line), Связи

## Профиль H2 (`application-h2.yaml`)

Активируется через `SPRING_PROFILES_ACTIVE=h2`. Использует H2 в PostgreSQL-режиме с файловым хранением.

| Параметр | Значение |
|---|---|
| `spring.datasource.url` | `jdbc:h2:file:./data/kb;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE` |
| `spring.datasource.driver-class-name` | `org.h2.Driver` |
| `spring.jpa.database-platform` | `org.hibernate.dialect.H2Dialect` |
| `spring.h2.console.enabled` | `true` |
| `spring.h2.console.path` | `/h2-console` |
| `spring.flyway.locations` | `classpath:db/migration-h2` |
| `semantic.enabled` | `false` |

Конфигурация H2 задаётся в классе `H2JdbcConfig` — создаёт `JdbcTemplate` для H2.
