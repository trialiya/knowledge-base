# Обзор работы с git

Документ описывает, как приложение работает с git-репозиториями проектов: откуда модель читает
код, что и на каких условиях она пишет в рабочее дерево, какие команды над репозиторием даёт
человеку интерфейс и где всё это сходится. Это обзор устройства, а не справочник: параметры
эндпоинтов, аргументы инструментов и ключи конфигурации описаны в документах ниже, здесь — как
они связаны и почему именно так.

### 1. Три поверхности над одним репозиторием

С git приложение работает от имени двух разных субъектов, и это главное деление всего, что ниже.
**Модель** читает репозиторий инструментами и, если проекту это разрешено, правит файлы в рабочем
дереве. **Человек** смотрит репозиторий в панели «Файлы», ревьюит незакоммиченное и запускает
git-команды — переключение ветки, stash, коммит, fetch/pull/push. Команды модели недоступны ни
одним инструментом, а правки модели никогда не коммитятся: коммит — всегда действие человека.

```
   Модель (@Tool)                          Человек (панель «Файлы», вкладка «Репозиторий» в чате)
   GitFunction · GitEditFunction ·                 gitApi.js  (?project=…)
   runScript (kb.*)                                     │
        │ ToolContext.project                           ├── GitController         GET /api/git/**   чтение
        │                                               ├── GitCommandController  POST /api/git/**  команды
        │                                               └── ChatFileRevertController                откат правок модели
        └──────────────────────┬────────────────────────────────┘
                               ▼
                         GitRegistry ─── ProjectCatalog (kb.projects)
                               │  forProject · requireEditable · requireGitCommands · requireGitPush
                               ▼
                   GitService — один экземпляр на проект, открытый JGit Repository
                     ├─ RepoPaths · VisibleFiles · Pathspec   какие пути существуют и как пишутся
                     ├─ RepoFiles · FileViews · CommitFiles · RepoBrowse · Diffs   чтение
                     ├─ GitGrepRunner (+ GitGrep)              единственный subprocess на чтении
                     ├─ GitWriter                              правки модели — в индекс, без коммита
                     ├─ GitBranches                            ветка, upstream, ahead/behind
                     └─ GitCommands                            fetch · pull · push · switch · stash · commit · discard · merge --abort
```

Пакет `service/file/git` наружу отдаёт `GitRegistry`, `GitService` и три исключения, по которым
вызывающий различает исходы (§5); остальные классы package-private — это внутренности одной
операции над деревом, и обращаться к ним мимо сервиса не должен никто.

### 2. Проекты: какой репозиторий имеется в виду

Репозиториев может быть несколько — по записи в `kb.projects`, — и каждый путь, по которому
называют репозиторий, несёт **id проекта**: адрес панели файлов (`?project=`), чипы композера,
аргументы и ответы инструментов, сохранённый выбор чата (`chat_topic.project`). Список
разрешается один раз при старте в `ProjectCatalog`: значения по умолчанию подставлены, путь
абсолютный, выключенные записи (`enabled: false`) не открываются и нигде не перечисляются.

Кто не назвал проект, получает **первый в списке** — и отвечает на это ровно одно место,
`ProjectCatalog.defaultProject()`: сводка, фоновая задача, чат, который проект не выбирал, запрос
к `/api/git/**` без параметра. Id, названный *явно* — параметром запроса, аргументом инструмента,
выбором в отправляемом сообщении, — но не сконфигурированный, отвечает отказом по имени, а не
тихим чтением другого репозитория: адрес, переживший смену конфигурации, не должен открыть чужой
файл с тем же путём. Одно исключение — сохранённый выбор чата (`chat_topic.project`): если проект с
тех пор убрали из конфигурации, чат едет на проекте по умолчанию, а по расхождению сохранённого id
со списком проектов интерфейс и понимает, что надо сказать «проект больше недоступен».

`GitRegistry` держит по одному `GitService` на открывшийся репозиторий. Экземпляр владеет
открытым JGit `Repository` — индексом, базой объектов, файловыми дескрипторами, — поэтому
создавать его на вызов нельзя, а закрывает все экземпляры сам реестр при остановке контекста.
Репозиторий, который не открылся (mount не доехал, путь — не рабочее дерево), стоит своего проекта
и ничего больше: сервер стартует, остальные проекты обслуживаются, вызовы к сломанному
отклоняются по имени. Исключение — проект по умолчанию: без него не работает ничего, и старт
падает.

**Как проект попадает в вызов инструмента.** Не аргументом, а через `ToolContext`
(`ProjectContext`): проект — свойство прогона, а не решение модели на каждом вызове. Проект прогона
разрешает `RunOptionsResolver` — из выбора в сообщении либо из сохранённого выбора чата, — в контекст
его кладёт `ChatRunService` при старте прогона, саб-агент поиска передаёт дальше то, что нёс
родительский прогон. Необязательный аргумент `project` у читающих инструментов, эхо репозитория в
`ToolResult`, блок `<active-project>` и почему его нет в системном промпте — в
[AI-инструменты](ai-инструменты.md), «Проект в аргументах»; правила для модели — в `prompt/sys.md`,
«Reading another project».

### 3. Что репозиторий показывает: пути и границы

**Отслеживаемые файлы — по индексу git.** Дерево, поиск по имени, `grep`, статус — всё отвечает
по индексу, и файл, которого в нём нет, для приложения не существует, даже если лежит на диске;
`.gitignore` исключён так же, как в самом git. Единственное расширение — untracked-зона
`kb.projects[].allow-globs`, внутри которой истина — рабочее дерево; её правила (что видно, что
правится, почему там нельзя создавать, статус `U`) — в [Конфигурация](конфигурация.md), «Проекты».
Для устройства важно одно: на «можно ли отдать этот путь вообще» отвечает один класс,
`VisibleFiles`, и его спрашивают и читающие инструменты, и `GitWriter`, — чтобы у чтения и записи
не было двух разных представлений о видимом. Каждый глоб обязан начинаться с литерального
сегмента, а не с wildcard: обход укоренён в этом префиксе, и он же ограничивает радиус поражения
от опечатки.

**Как пишется путь — `RepoPaths`.** Путь всегда repo-relative, через `/`, и три класса символов
в нём запрещены, каждый по своей причине: управляющие символы и разделители строк (git печатает
такое имя в кавычках с экранированием, и путь перестаёт совпадать сам с собой между индексом, API
и диском), двойная кавычка (то же самое независимо от `core.quotePath`), форматирующие символы
Unicode — bidi-переопределения и разделители чипов композера `⟦⟧` (имя пишется одним способом, а
показывается другим — в списке, где отмечают файлы для коммита, это недопустимо). Всё остальное —
законное имя: путь доходит до git одним аргументом процесса или литеральным фильтром JGit,
никогда не shell-словом.

**Граница дерева — по файловой системе, не по строке.** Текстовой нормализации (`normalize()` и
сравнение префикса) недостаточно: отслеживаемая символьная ссылка наружу или symlink-каталог по
дороге проходят её, а чтение или запись ложатся туда, куда ведёт ссылка. Поэтому `RepoPaths`
разрешает самый глубокий существующий компонент пути и проверяет, что *он* внутри дерева. Сам
репозиторий при этом может жить за символической ссылкой (`/tmp` → `/private/tmp`) — сравнение
идёт с разрешённым корнем.

**Пределы.** Значения — константы рядом с кодом, который их применяет; здесь они названы, чтобы
было ясно, где искать:

| Что ограничено | Где задано |
|---|---|
| Файл больше 512 КБ отдаётся фрагментом (`truncated=true`), бинарный — без содержимого | `RepoFiles.MAX_FILE_SIZE`, `BINARY_SNIFF_BYTES` |
| Патч одного файла — до 500 строк | `Diffs.MAX_DIFF_LINES` |
| Блоб из истории, который поднимается в память целиком, — до 32 МБ | `CommitFiles.MAX_BLOB_SIZE` |
| `git grep` — 20 секунд и 20 000 строк вывода | `GitGrepRunner.GREP_TIMEOUT`, `MAX_OUTPUT_LINES` |
| Сообщение коммита — 4000 символов, файлов в одном коммите — 1000 | `GitCommands.MAX_MESSAGE_CHARS`, `MAX_COMMIT_PATHS` |

Служебный мусор ОС и IDE (`.DS_Store`, `Thumbs.db` и подобное) вырезается из выдачи всегда —
списки в `RepoPaths`.

### 4. Чтение: рабочее дерево и снимок ревизии

У чтения два источника, и это два разных пути в коде, а не флаг. **Рабочее дерево** — то, что на
диске: с незакоммиченными правками, с untracked-зоной, с размером файла и признаком «отслеживается».
**Дерево коммита** (`CommitFiles`, параметр `rev` у `browse`, `files/content`, `grep`, `tree`) —
`git show <rev>:<path>` точечными чтениями, без обхода дерева целиком: файл там существует в одних
коммитах и отсутствует в других, размера на диске у него нет, а по одному пути в разных коммитах
лежат разные объекты. `rev` — что угодно, что git понимает как коммит: хеш полный или короткий,
ветка, тег, `HEAD~2`; в ответе всегда полный хеш коммита, который отдал файл.

Что у двух источников общее, вынесено в классы без репозитория внутри. `RepoBrowse` раскладывает
плоский список путей в дерево браузера — одни узлы, один порядок, одни предки, чем бы ни был
снимок. `FileViews` превращает байты в ответ читающего инструмента — язык по имени, счётчик
строк, запрошенный диапазон, усечение — одинаково для диска и для истории. Панель «Файлы» открывает
путь **одним** запросом `GET /api/git/browse`: бэкенд сам определяет, файл это или каталог, и
заодно отдаёт листинги каталогов-предков, чтобы дерево слева раскрылось до узла.

Две «карты» репозитория отвечают на разные вопросы и потому разделены: `GitRefs` (ветки и теги —
что *можно открыть* как снимок; хеши не перечисляются, их ищут через `GET /api/git/commits/search`)
и `GitBranchStatus` (где *стоит* рабочее дерево: ветка, upstream, `ahead`/`behind`, есть ли
незакоммиченное, идёт ли merge). Счётчики читаются по refs на диске и свежи ровно настолько,
насколько свеж последний fetch, — в сеть чтение не ходит никогда, иначе открытие панели стало бы
сетевым запросом.

### 5. JGit или subprocess

Всё, что можно, делается **в процессе через JGit** — без argv, без разбора текстового вывода, с
ответами в типах (`MergeResult` несёт пути конфликтов, а не строку, которую надо парсить). Наружу
выходят три вещи, и у каждой своя причина:

| Операция | Как выполняется | Почему |
|---|---|---|
| `git grep` (`grepContent`, `GET /api/git/grep`) | subprocess `git grep` (`GitGrepRunner`, командная строка — `GitGrep`) | У JGit нет grep. Единственный subprocess на чтении: дедлайн и разбор кодов выхода git живут здесь и больше нигде |
| `fetch`, `pull`, `push` | subprocess `git` | Нужны учётные данные хоста — ssh-agent, credential helper, `insteadOf`; системный git их уже знает, а учить им JGit значило бы воспроизводить окружение вместо того, чтобы им пользоваться |
| `merge --abort` | subprocess `git` | JGit этого не умеет |
| `switch`, `stash`, `commit`, `discard`, статус, история, диффы, чтение | JGit | Ничего, кроме этого репозитория, им не нужно |

Shell нет ни в одном случае: `ProcessBuilder` получает массив аргументов, глагол всегда наш, а
пользовательский ввод доходит до команды проверенным именем ветки, repo-relative путём или
сообщением коммита — никогда списком аргументов.

Из subprocess следует требование к деплою: рабочее дерево принадлежит хостовому пользователю, а
контейнер работает от `kb`, и git без исключения `safe.directory` на такой каталог отвечает
«dubious ownership». Исключения ставит `docker/start.sh` при старте по тем же переменным, что читает
бэкенд (`PROJECT_PATH`, `PROJECT2_PATH`, `KB_PROJECTS_<i>_PATH`); глобов `safe.directory` не
понимает, поэтому — по одному на проект. Бинарный `git` есть в runtime-образе именно ради этого.

Отказы разведены по типам, потому что у вызывающего на них разные ответы: `GitCommandFailedException`
— команда отказала: для subprocess это собственный вывод git без пересказа («Permission denied
(publickey)», «couldn't find remote ref» — это и есть подсказка, что чинить), для JGit-команд —
такая же короткая фраза от приложения («No such branch», «Nothing to commit»);
`IllegalStateException` — команду не удалось запустить вовсе; `GitGrepTimeoutException` — поиск не
уложился в дедлайн (`503` на странице поиска; модели уходит само сообщение о таймауте, и сузить
поиск — её решение); `GitBusyException` —
репозиторий занят другой командой (§7).

### 6. Правки модели: рабочее дерево, но не история

Инструменты `createFile` и `editFile` (`GitEditFunction`) существуют как бин только когда **хотя
бы один** проект принимает запись (`ChatConfig#gitEditFunction`); иначе их просто нет в списке
инструментов модели, и read-only режим не требует никакой другой настройки. Присутствие бина
говорит лишь, что *какой-то* проект пишущий; проект конкретного вызова проверяется по имени через
`GitRegistry.requireEditable`, и отказ уходит модели по каналу ошибок инструмента, а не падает
I/O-исключением на середине записи.

«Можно ли писать в этот проект» — один вопрос из двух половин, и отвечает на него одно место,
`GitRegistry.editsAllowed`: сконфигурированное намерение (`kb.projects[].edit-enabled`) **и**
физическая возможность (`GitService.isRepoWritable` — ro-mount отбирает запись, что бы ни стояло
в конфигурации). Тот же ответ получают инструмент `editFile` и пишущие методы `runScript`
(`ScriptEditPolicy` добавляет к нему второй затвор — `kb.script.edit-enabled`). Файловая система
спрашивается намеренно при каждом ответе: перемонтированный ro-mount отбирает права у работающего
сервера. Панель настроек этого не переспрашивает — она показывает снимок на момент старта: флаг
конфигурации проекта по умолчанию и существует ли бин инструментов записи; доступность дерева на
запись прямо сейчас отдельно отдаёт `GET /api/admin/system`.

**Что делает правку безопасной — контракт точного совпадения, а не предварительное чтение.**
`oldString` обязан встречаться в файле ровно один раз (или `replaceAll`), символ в символ: модель,
способная процитировать такой фрагмент, цитирует текущее содержимое, а не способная получает отказ
с именем инструмента, которым надо прочитать. Проверка «читала ли модель файл» поверх этого не
нужна и не должна добавляться — ни здесь, ни в песочнице скриптов (`kb.edit` следует тому же
контракту). Она нужна только там, где такого контракта нет: у замены содержимого целиком
(`kb.writeBytes`, `ScriptSession#requireRead`), и там «видела ли модель файл» считается **вместе с
проектом** (`ToolInvocationCollector#hasSeenFile`): чтение пути в одном репозитории не засчитывается
за запись одноимённого пути в другом.

**Каждая правка заканчивается в индексе, не в коммите.** `GitWriter` стейджит созданный или
изменённый файл, и в `getUncommittedChanges` он виден как `A`/`M` — тот же список, который панель
«Файлы» показывает в режиме «Изменения», а окно коммита предлагает отметить галочками. Правка
untracked-файла (только при `untracked-edit-enabled`) файл не индексирует — он остаётся под
статусом `U`, чтобы модель не считала его идущим в следующий коммит.

**Откат** (`ChatFileRevert`, `POST /api/chats/{id}/revert-files`) — не git-команда, а отмена того,
что сделал ассистент, и решает её история чата, а не git: `editFile` обратим своими же аргументами,
созданный файл удаляется после сверки содержимого, ответ с правками через `runScript` не
откатывается вовсе. Как строится план, что считается за ответ, коды отказов — в
[Обзор чат-системы](обзор-чат-системы.md), §3.4.

### 7. Команды пользователя

`GitCommands` — то, что человек делает с репозиторием из интерфейса, и **не возможность модели**:
ни один `@Tool` сюда не ведёт, системный промпт о командах молчит, `GitCapabilities` описывает
кнопки, а не инструменты. Разрешение отдельное от правок модели — `kb.projects[].git-commands.enabled`
говорит, что *человек* вправе делать с самим репозиторием, а `edit-enabled` — что *модель* вправе
писать в рабочее дерево, — но затвор тот же: конфигурация **и** дерево доступно на запись. Пишут все
команды, `fetch` в том числе (он двигает refs), поэтому ro-mount отбирает их разом. `push` — единственная
команда, публикующая содержимое репозитория за пределы деплоя, — под собственным флагом
`push-enabled` и собственным затвором `requireGitPush`.

Что доступно **прямо сейчас**, интерфейс спрашивает `GET /api/git/capabilities` вместе с
состоянием ветки — при каждом сигнале «репозиторий сдвинулся», а не один раз на приложение и не из
закэшированного списка проектов: перемонтированный ro-mount отбирает
команды у работающего сервера, а не открывшийся репозиторий их никогда и не имел.

**По одной команде на репозиторий.** Каждая команда что-то пишет, две перекрывшиеся перемешали бы
записи, и вторая прочитала бы состояние, которого ни одна из них не производила. Поэтому у проекта
`ReentrantLock`, который держится на всю команду и **никогда не ждётся**: запрос, заставший
занятый репозиторий, получает `GitBusyException` («повторите чуть позже»), а не встаёт в очередь за
чужим fetch со спиннером на экране.

Каждый глагол — свой эндпоинт, а не один «выполнить команду» с аргументом: у них разные
аргументы, предусловия и отказы, а эндпоинт, принимающий команду, — это командная строка, которой
здесь намеренно нет. Точные флаги, что стейджит коммит и коды ответов — в
[API Reference](api-reference.md), «Локальные команды пользователя» и разделы `fetch`/`pull`/`push`.
Для устройства важен общий принцип: **ни одна команда не уничтожает и не перезаписывает работу
кликом**. `pull` — только fast-forward, merge-коммит — решение, а решений кликом «обновить» не
принимают; `push` не форсируется ни в каком написании; `switch` отказывает, если перезаписал бы
незакоммиченное, и называет файлы; конфликтный `stash pop` stash не удаляет; `discard` — единственная
команда, которая уничтожает работу, — берёт один путь и никогда всё дерево; коммит без
`user.name`/`user.email` — отказ, а не история за подписью, которую JGit выдумал бы из окружения.
`merge --abort` — гарантированный выход из конфликтного дерева, и причина, по которой конфликтный
pull не тупик. Каждый ответ (`GitCommandResult`) везёт состояние ветки *после* команды, чтобы
клиент не рисовал кадр состояния до команды, которую только что выполнил.

### 8. Git из чата

Те же команды доступны на вкладке «Репозиторий» панели чата (`ChatRepoPanel`, `useChatGit`);
параметр `chat` у эндпоинта говорит, что команда запущена из чата: пока в чате работает модель,
команда отклоняется, а выполненная — включая отказ — оставляет ряд в истории чата, о котором остальные
вкладки узнают событием `GIT_COMMAND`. Что именно записывается и какие коды отвечают — в
[API Reference](api-reference.md), «Параметр `chat`».

Два устройства, которых в справочнике нет. Занятость чата не проверяется, а *занимается*
(`ChatGitLog.claimIdleAndOwned` берёт ту же заявку, что держат прогон и сжатие — `ConversationSlots`),
поэтому «свободен» и «занял» — одно атомарное действие, и запрет работает в обе стороны: вопрос в
чат во время команды получает `409`. Ряд истории (`GitEventMeta`) хранит вывод git целиком, а фраза
для модели собирается на чтении из команды, исхода и ветки — формулировку можно менять, не
переписывая историю. Неудача записи ряда не превращается в отказ команды: репозиторий к тому моменту
уже сдвинулся, и ответить на успешный pull ошибкой значило бы заставить панель нарисовать
состояние, которого больше нет. В черновике чата, id которого ещё выдуман фронтом, команд нет вовсе:
записывать некуда.

### 9. Клиент

`api/gitApi.js` — тонкие обёртки над `/api/git/*`; адрес файла в них — **пара** (проект, путь),
потому что `backend/build.gradle` есть в каждом репозитории, и хвост каждого метода — один объект
опций, а не позиционные аргументы. Компоненты разложены по тому, где их показывают:

| Где | Что |
|---|---|
| `filesPanel/git/` | Строка ветки (`GitBranchBar`), меню команд (`GitMenu`, `GitBranchList`), состояние ветки и права (`useGitBranch`), сценарий команд — что спросить до и где показать отказ после (`useGitActions`) |
| `filesPanel/changes/` | Режим «Изменения»: список без патчей (`useUncommittedChanges`), патч одного файла по клику (`useChangeDiff`), раскладка плоско/деревом |
| `common/git/` | Общее для нескольких поверхностей: окно коммита с выбором файлов (`CommitDialog`, `useCommitSelection`) и окно push со списком того, что уедет (`PushDialog`, `useOutgoingCommits`) — у панели «Файлы» и чата; карточка вывода git (`GitOutputCard`) — там же и в ленте чата; выбор снимка ревизии (`RevisionPicker`, `useRevisions`) — у панели «Файлы» и единого поиска |
| `chatPanel/git/` | Вкладка «Репозиторий» (`ChatRepoPanel`, `useChatGit`) — те же хуки плюс два правила §8 |

Два правила, которые стоит знать, прежде чем трогать эту часть. `runGitCommand` поднимает сигнал
«репозиторий сдвинулся» **и на успехе, и на отказе**: конфликтный `stash pop` сначала накладывает
stash и только потом отказывает, и панель, обновляющаяся только на успехе, показывала бы
состояние, которого больше нет. И сигналов два: `refreshToken` — «рабочее дерево могло измениться»
(правка инструментом, коммит), `refsToken` — только remote-tracking refs (их двигает один `fetch`);
второй общий на всё приложение, потому что хуков ветки два — в «Файлах» и в чате, — а репозиторий у
них один. Кэш дерева (`fileTreeStore`) — по паре «проект + ревизия», с TTL на листинги: путь
`backend/build.gradle` есть в каждом репозитории, и общий кэш показал бы дерево одного проекта в
другом, а снимок ревизии — вместо рабочего дерева.

### 10. Что здесь не про репозиторий проекта

`git.properties` в JAR (ветка, коммит, `dirty` в панели администрирования) — про сборку *самого
приложения*, а не про проекты, и делается плагином `gradle-git-properties` при сборке; см.
[Разработка и контрибьюция](разработка-и-контрибьюция.md), «Метаданные сборки». К `GitService`
это отношения не имеет.
