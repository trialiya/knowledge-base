## Сущности

### ChatMessageEntity
Таблица: `chat_message`. Реализует `Message` (Spring AI) и `Persistable<Long>`.

| Поле | Тип | Описание |
|---|---|---|
| `id` | long | PK. `isNew()` → `id == 0L` |
| `conversationId` | String | FK → chat_topic.conversation_id |
| `content` | String | Текст сообщения |
| `type` | MessageType | USER, ASSISTANT, SYSTEM, TOOL |
| `position` | long | Порядок в беседе |
| `summarized` | boolean | Попало ли в саммари |
| `summary` | boolean | Является ли само сообщение саммари |
| `createdAt` | LocalDateTime | Время создания |
| `meta` | ChatMessageMeta | **UI-метаданные**: вызовы инструментов, приложенный к вопросу контекст, токены прогона и признаки служебных рядов (сжатие, git-команда) — JSON через `ChatMessageMetaToJsonConverter` |
| `toolData` | ToolData | **Протокольные** tool-данные (вызовы ассистента и TOOL-ответы) — JSON через `ToolDataToJsonConverter` |

Все поля кроме `id` — `final`.

> **`meta` и `toolData` не смешивают.** `toolData` — то, что нужно протоколу LLM, чтобы воспроизвести историю диалога; `meta` — то, что рисует фронтенд. Отдельной таблицы tool-вызовов нет.

Метод `getMessage()` возвращает Spring AI wrapper в зависимости от type:
- `USER` → `UserChatMessage`
- `ASSISTANT` → `AssistantChatMessage`
- `SYSTEM` → `SystemChatMessage`
- `TOOL` → `ToolChatMessage`

Метод `getInvocations()` → `List<ToolInvocationMeta>` (из `meta`, может быть null).

Метод `getContextItems()` → `List<ContextItem>` (из `meta`, никогда не null).

**SYSTEM-сообщения** хранят суммаризации (`summary = true`). Раньше в них же писались «крошки» с JSON всех вызовов прогона; теперь вызовы сохраняются вместе с обычными сегментами ассистента, но старые чаты с крошками читаются по-прежнему — их опознаёт флаг `meta.toolCalls`, а `toolInvocationMetas` прикрепляются к предыдущему AI-сообщению.

### ChatMessageMeta
Record. Хранится в поле `meta` как JSON.

| Поле | Тип | Описание |
|---|---|---|
| `runId` | String | К какому прогону относится сообщение (`@Nullable`) |
| `toolCalls` | boolean | Сообщение — служебная «крошка» вызовов, пользователю не показывается |
| `invocations` | List\<ToolInvocationMeta\> | UI-метаданные вызовов (никогда не null, пустой список по умолчанию) |
| `contextItems` | List\<ContextItem\> | Приложенное пользователем к вопросу (никогда не null) |
| `project` | String | Проект, в который перешёл чат этим сообщением; на строке-сводке — проект, на котором закончилось сжатое (`@Nullable`) |
| `projectSwitchFrom` | String | Проект, к которому относится история выше; заполняется парой с `project` (`@Nullable`) |
| `model` | String | Модель, написавшая ответ (только ASSISTANT). `null` — «неизвестно»: ответ старее поля, а не «модель по умолчанию» (`@Nullable`) |
| `compact` | CompactMeta | Итог сжатия контекста: `{ messages, summaryChars, summaryId, kind, carried }`. Стоит ровно на строке-плашке, которую сжатие оставило вместо себя, и он же её признак. `kind` — чем сжатие вызвано (`COMPACT` — команда пользователя, `SUMMARIZE` — фоновая суммаризация); незнакомый вид и его отсутствие у рядов, записанных раньше поля, читаются как `COMPACT`. `carried` — деньги отложенных фоновых сводок, которые это сжатие выбросило: полное сжатие заменяет собой их кусок истории, ряда у них после этого не остаётся, а заплачено за них было, и без этого поля они выпали бы из итога по чату. Только деньги, без контекстных чисел (`RunTokenUsage.spentTogether`) (`@Nullable`) |
| `gitEvent` | GitEventMeta | Git-команда, выполненная пользователем из этого чата: `{ command, project, ok, output, branch }`. Стоит на собственном ряду — `USER` с пустым текстом — и он же его признак. Человек видит на нём карточку вывода, модель — блок `<git-command>`, который собирается на чтении в `ChatHistoryService.promptRow` и в базу не пишется (`@Nullable`) |
| `fileRevert` | FileRevertMeta | Откат файловых правок ответа, выполненный пользователем: `{ project, paths }`. Как и `gitEvent`, стоит на собственном ряду — `USER` с пустым текстом — и он же его признак. Человек видит плашку со списком файлов, модель — блок `<files-reverted>`, который собирается на чтении в `PromptNotices` и в базу не пишется (`@Nullable`) |
| `interjection` | boolean | Вопрос доставлен ПОСРЕДИ прогона, между итерациями tool-цикла. Такой ряд не открывает ход, и всё, что ищет «последний вопрос», обязано смотреть сквозь него (`tailAfterLastUser` и его фронтовый двойник) |
| `usage` | RunTokenUsage | Токены прогона: `{ contextTokens, basePromptTokens, toolTokens, outputTokens, promptTokens, cacheReadTokens, cacheWriteTokens, totalTokens, modelCalls }`. Стоит на **последнем** ASSISTANT-ряду прогона и только на нём — числа относятся к прогону целиком. Есть и на строке-плашке сжатия — и у `/compact`, и у фоновой суммаризации: раунд сжатия тоже обращение к модели, и в итогах чата он считается наравне с ответами (его `contextTokens` при этом описывает контекст самого раунда, а не то, что осталось в чате после него). На USER-ряду бывает ровно в одном случае: сжатие, которое обращение к модели сделало, а сводки не дало, пишет свой замер на строку собственной команды — плашки у него нет, а деньги заплачены (`CompactService.spentRound`); контекстом чата такой замер не является, и в итог по чату (`ChatUsageService`) он идёт только деньгами. `null` — «не измерено» (эндпоинт без `stream_options.include_usage`), а не ноль. Смысл каждого числа — в [обзоре чат-системы](../обзор-чат-системы.md), §6.4 (`@Nullable`) |

`invocations`, `model` и `usage` дописывают по завершении прогона одной записью
(`ChatHistoryService.markRunResult`): на записи не известно ничего из этого — advisor памяти
приносит в `ChatMemory.add` только сообщения. Плашки достаются сегментам, которые звали
инструменты, модель — каждому ряду прогона, токены — одному последнему. Одной записью, а не тремя:
плашки ищут необогащённые сегменты по `meta == null`, и модель, проставленная раньше, спрятала бы
от них вызовы инструментов.

### ContextItem

Что пользователь приложил к своему сообщению. Record: `{ kind, ref, label, payload }`.

| Поле | Тип | Описание |
|---|---|---|
| `kind` | ContextItemKind | Вид элемента; пока единственный — `ATTACHMENT` |
| `ref` | String | Ссылка в терминах вида (для `ATTACHMENT` — id строки `attachment`) |
| `label` | String | Подпись на момент привязки — чтобы фронт рисовал чип, не ходя за каждым объектом (`@Nullable`) |
| `payload` | Map\<String, Object\> | Детали, специфичные для вида; сейчас всегда пустая |

Отдельной таблицы нет и не нужно: элементы всегда читаются вместе со своим сообщением
и ни разу — сами по себе. Она понадобится, когда появится вид контекста с обратной
выборкой («все комментарии по файлу X»).

**Элемент — ссылка, а не копия.** `ref` резолвится при каждом чтении истории
(`ContextItemService.render`), поэтому переименованное вложение попадает в промпт под
новым именем, а удалённое просто исчезает из него — вместо вечного обещания файла,
которого больше нет. Содержимое в историю не разворачивается: модель читает его
инструментом `getAttachmentContent` тогда, когда оно понадобилось.

**Неизвестный `kind` при чтении отбрасывается** (`ChatMessageMetaToJsonConverter`), а не
роняет разбор меты. Иначе откат приложения после появления нового вида превращался бы в
отказ открыть каждый чат, где такой элемент записан.

### ChatTopicEntity
Таблица: `chat_topic`. Реализует `Persistable<String>` (ID = conversationId).

| Поле | Тип | Описание |
|---|---|---|
| `conversationId` | String | PK, UUID |
| `user` | String | Имя пользователя |
| `userTopic` | String | Название, заданное пользователем вручную (`@Nullable`) |
| `aiTopic` | String | Название, предложенное ИИ через `recordChatInsights` (`@Nullable`) |
| `model` | String | ID выбранной AI-модели (`@Nullable`, null = дефолтная) |
| `mode` | String | ID выбранного режима ассистента (`@Nullable`, null = без режима) |
| `project` | String | ID выбранного проекта — репозитория, в котором работают инструменты (`@Nullable`, null = первый в `kb.projects`) |
| `createdAt` | LocalDateTime | `@CreatedDate` |
| `updatedAt` | LocalDateTime | `@LastModifiedDate` |
| `isNew` | boolean | `@Transient` |

**Два названия вместо флага.** Раньше была одна колонка `topic` плюс булев `is_user`, и авто-имя от ИИ затирало пользовательское. Теперь это разные поля, а `getDisplayTopic()` отдаёт `userTopic`, если он есть, иначе `aiTopic` — ИИ может предлагать тему сколько угодно, ручное название от этого не страдает (миграция `V2026.07.26_00__split_chat_topic`). Режим добавлен миграцией `V2026.07.20_00__add_mode_to_chat_topic`, проект — `V2026.08.18_00__add_project_to_chat_topic`.

### ToolCallIndexEntity
Таблица: `tool_call_index`. Индекс для быстрого поиска tool calls по `callId`.

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `conversationId` | String | FK → chat_topic.conversation_id |
| `callId` | String | Protocol `callId` — уникальный идентификатор вызова инструмента |
| `messageId` | long | FK → chat_message.id (ASSISTANT-сообщение, которое выдало вызов) |
| `responseMessageId` | Long | FK → chat_message.id (TOOL-сообщение с результатом, `@Nullable` если результат ещё не пришёл) |

**Назначение:** позволяет `ToolCallService.findToolCallDetail()` выполнить быстрый lookup по `callId` вместо позиционного поиска в истории сообщений. Заполняется при сохранении сообщений — `ChatHistoryService.append()` зовёт `ToolCallService.index()`.

**Связь:** ключ `(conversationId, callId)` → пара `chat_message` (ASSISTANT-вызов + TOOL-результат, если есть). Индекс синхронизируется с `chat_message` через **ON DELETE CASCADE**.

### ChatPendingSummaryEntity
Таблица: `chat_pending_summary`. Написанные фоновые сводки, ещё не попавшие в историю, — очередь на
чат (`ON DELETE CASCADE`): пока применения нет, разговор продолжается, и следующий раунд сжимает
накопившееся за уже припаркованным. Диапазоны рядов очереди идут подряд и не пересекаются.

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `conversationId` | String | FK → chat_topic.conversation_id |
| `startPosition` / `endPosition` | long | Диапазон позиций, который перестанет быть живым при применении |
| `summaryPosition` | long | Позиция будущего ряда сводки |
| `summaryCreatedAt` | LocalDateTime | Время, которым будут подписаны оба ряда, — время конца раунда |
| `text` | String | Текст сводки как есть, без обёртки для модели |
| `messages` / `summaryChars` | int | Числа будущей плашки |
| `meta` | `ChatMessageMeta` (JSON) | След проектов — на будущий ряд сводки, `usage` раунда — на плашку (`@Nullable`) |
| `createdAt` | LocalDateTime | Когда сводку припарковали |

**Зачем откладывать.** Провайдер кэширует промпт с первого байта, а сжатие подменяет начало истории
— пока кэш горячий, это полная оплата следующего запроса. Ряды ждут повода: паузы в разговоре или
контекста, доросшего до доли окна модели (см. `обзор-чат-системы.md`, «Применение сводки отложено»).
Применяется очередь целиком, по порядку и одной транзакцией: её сводки — куски одной непрерывной
головы разговора, и остановка на середине оставила бы в промпте живой кусок между двумя сжатыми.
Пишет и читает таблицу только `PendingSummaryService`; каждая строка забирается удалением
(`claim`), поэтому двух применений одной сводки не бывает.

### ChatModelProperties
Конфигурационный record (`kb.chat.*` в `application.yaml`).

| Поле | Тип | Описание |
|---|---|---|
| `defaultModel` | ModelOption | Модель по умолчанию |
| `models` | List\<ModelOption\> | Список дополнительных моделей |

`ModelOption` — record: `{ id, label, weak, streamUsage, contextTokens, baseUrl, apiKey }` (полное описание полей — в `конфигурация.md`). Метод `isAllowed(id)` проверяет, есть ли модель в списке разрешённых (defaultModel + models); `contextTokens(id)` отдаёт окно модели или `null`, если оно не названо, — от него считаются автоматические решения о размере истории.

#### Способы задания моделей

Модели задаются в `application.yaml` в секции `kb.chat`:

```yaml
kb:
  chat:
    default-model:
      id: ${AI_MODEL}              # ID модели (переменная окружения)
      label: ${AI_MODEL_LABEL:Default}  # Отображаемое имя
    models:                        # Дополнительные модели (опционально)
      - id: ${KB_CHAT_MODELS_0_ID}
        label: ${KB_CHAT_MODELS_0_LABEL}
```

**Три уровня выбора модели** (приоритет по убыванию):

1. **Поле `model` в теле запроса** — модель, явно переданная в `POST /api/chats/{id}/runs` (или в постановке сообщения в очередь идущего прогона). Валидируется через `isAllowed()`.
2. **Сохранённая модель чата** — поле `model` в `chat_topic`. Задаётся через `PUT /api/models/{conversationId}`. Если модель убрали из конфига, она игнорируется (фильтр `isAllowed`).
3. **Дефолтная модель** — `kb.chat.default-model.id`. Используется когда ни параметр запроса, ни сохранённая модель не заданы.

**Связь со Spring AI:** `spring.ai.openai.chat.options.model` ссылается на `${kb.chat.default-model.id}`, поэтому дефолтная модель из `kb.chat` автоматически используется OpenAI-клиентом.

**Валидация:** `ChatModelProperties.isAllowed(id)` разрешает модель если она совпадает с `defaultModel.id` или есть в списке `models`. При передаче неизвестной модели возвращается `400 Bad Request`.
