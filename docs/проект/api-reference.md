## DocumentController — `/api/documents`

### GET `/api/documents/children`
Lazy-load дочерних узлов с пагинацией. `description` — сниппет ≤150 символов или `null`.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `parentId` | Long? | `null` | ID родителя (`null` — корень) |
| `page` | int | `0` | Номер страницы |
| `size` | int | `10` | Размер страницы |

**Response:** `PagedChildren` (totalElements, totalPages, hasNext, content)

---

### GET `/api/documents/{id}`
Получить один документ по ID с полным `description`. Используется фронтендом при клике на любой узел (tree, children, search results) — все они возвращают сниппет или `null`, а полный текст загружается этим эндпоинтом.

**Response:** `DocumentNode`

**Ошибки:** `404` — документ не найден

---

### GET `/api/documents/{id}/ancestors`
ID предков от корня до узла (не включая сам узел). Используется UI для раскрытия ветки при прямом переходе.

**Response:** `List<Long>` — например `[1, 7, 42]`

---

### GET `/api/documents/{id}/history`
История изменений description документа. Возвращает список снепшотов **без поля `description`** — только метаданные (version, title, type, descriptionVersion, updatedAt). Полный текст конкретной версии загружается отдельно через `GET /api/documents/{id}/history/{version}`.

**Response:** `List<DocumentHistoryShort>`

**Ошибки:** `404` — документ не найден

---

### GET `/api/documents/{id}/history/{version}`
Получить **полную** версию истории (с `description`) по номеру версии. Используется в `HistoryModal` для ленивой подгрузки описания выбранной версии.

**Response:** `DocumentHistory`

**Ошибки:** `404` — документ или версия не найдены

---

### GET `/api/documents/search-by-name`
Поиск документов/папок по фрагменту названия (регистронезависимо). Используется для автокомплита @mention в Markdown-редакторе. Точные совпадения возвращаются первыми, затем частичные — по длине названия.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `name` | String | — | Фрагмент названия (мин. 1 символ) |
| `limit` | int | `10` | Макс. результатов (макс. 20) |

**Response:** `List<DocumentNode>`

---

### POST `/api/documents`
Создать документ или папку.

**Body:** `CreateDocumentRequest`
```json
{
  "title": "string",
  "type": "document | folder",
  "parentId": "long | null",
  "description": "string"
}
```
**Response:** `201 Created` → `Document`

---

### PUT `/api/documents/{id}`
Обновить документ. Сохраняет снапшот в `document_history` перед обновлением. Использует оптимистичную блокировку. При изменении `description` инкрементирует `descriptionVersion` — это делает существующий summary устаревшим (stale), но не удаляет его.

**Body:** `UpdateDocumentRequest`
```json
{
  "title": "string",
  "description": "string"
}
```
**Response:** `Document`

**Ошибки:**
- `403` — попытка переименовать системный документ
- `404` — документ не найден
- `409` — конфликт конкурентного изменения (документ был изменён другим запросом)

---

### DELETE `/api/documents/{id}`
Удалить документ. История удаляется автоматически (`ON DELETE CASCADE`).

**Response:** `204 No Content`

**Ошибки:** `403` — системный документ

---

### PATCH `/api/documents/{id}/move`
Переместить документ/папку в целевого родителя и на конкретную позицию за один атомарный вызов. Заменяет старую пару `moveToParent` + `reorder`: клиент указывает одного соседа вместо всего списка siblings, поэтому частично загруженное дерево на фронтенде не может испортить порядок — точный слот вычисляется на сервере из актуального состояния БД.

**Body:** `MoveRequest`
```json
{ "parentId": 1, "afterId": 7 }     // в папку 1, сразу после узла 7
{ "parentId": 1, "afterId": null }  // в папку 1, первым
{ "parentId": null, "afterId": 42 } // в корень, сразу после 42
```

**Response:** `Document`

**Ошибки:**
- `400` — цикл, или `afterId == id`
- `403` — системный узел
- `404` — узел, целевой родитель или `afterId` не найдены
- `409` — конкурентное изменение
- `422` — цель не папка, или `afterId` принадлежит другому уровню

---

### POST `/api/documents/{id}/summarize`
Сгенерировать (или перегенерировать) AI-summary для документа. Description отправляется в LLM полностью, без усечения. `summarySourceVersion` устанавливается в текущий `descriptionVersion` — это сбрасывает флаг stale до следующего изменения description.

**Response:** `DocumentNode` (с заполненными полями `summary`, `summaryStale=false`, `summarySourceVersion`)

**Ошибки:**
- `404` — документ не найден
- `422` — документ не имеет description (нечего суммаризировать)
- `409` — конфликт конкурентного изменения

---

### GET `/api/documents/search`
Унифицированный поиск. Ищет по `title`, `summary` и `description`. Результаты включают `parentList` — хлебные крошки (предки от корня до родителя).

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `q` | String | — | Поисковый запрос |
| `mode` | String | `keyword` | `keyword` / `semantic` / `hybrid` |
| `threshold` | Double? | `null` | Порог схожести (semantic/hybrid) |
| `limit` | Integer? | `null` | Макс. количество результатов |
| `kwWeight` | Double? | `null` | Вес keyword (только hybrid) |
| `semWeight` | Double? | `null` | Вес semantic (только hybrid) |

**Response:** `List<SearchResult>` — каждый результат содержит `parentList: List<Parent>` с полями `id` и `title`

---

### POST `/api/documents/admin/reindex`
Полный переиндекс всех документов (генерация эмбеддингов заново).

**Response:** `ReindexResponse`
```json
{ "indexed": 42 }
```

---

### POST `/api/documents/admin/export`
Экспорт всех документов. Внутренние ссылки `(/?doc=ID)` перезаписываются в относительные пути — экспортированный Markdown становится самодостаточным.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `meta` | boolean | `true` | `true` — экспорт с `.yaml`-файлами метаданных; `false` — только `.md` |

**Response:** `204 No Content`

---

### GET `/api/documents/download`
Скачивание всего дерева одним `.zip` в раскладке экспорта — распакованный архив можно положить в папку экспорта и импортировать обратно. Серверная папка при этом не нужна: на диске ничего не создаётся, архив собирается прямо в ответ по мере обхода дерева.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `meta` | boolean | `false` | Добавлять ли `.yaml`/`.meta.yaml` в архив |

**Response:** `200 OK`, `application/zip`, `Content-Disposition: attachment; filename="knowledge-base.zip"`

---

### GET `/api/documents/{id}/download`
Скачивание узла: документ — одним `.md`, папка — `.zip`-архивом поддерева в раскладке экспорта. Ответ пишется в поток по мере обхода дерева, поэтому размер поддерева не влияет на память сервера.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `meta` | boolean | `false` | Добавлять ли `.yaml`/`.meta.yaml` в архив (для документа игнорируется) |

**Response:** `200 OK`, `Content-Disposition: attachment`; `text/markdown` или `application/zip`

**Ошибки:** `404` — узел не найден

---

### POST `/api/documents/admin/export/stream`
Тот же экспорт, но с прогрессом: `text/event-stream`, кадр `PROGRESS` на каждый записанный узел и терминальный `DONE` со сводкой `{ "files": N }`.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `meta` | boolean | `true` | Как у `POST /admin/export` |

---

### GET `/api/documents/admin/import/diff`
Сравнение серверной папки экспорта с базой. Ничего не записывает. `text/event-stream`: кадр `ENTRY` на каждый узел по мере обхода, затем `DONE` со сводкой `DiffSummary`.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `parentId` | Long? | `null` | Поддерево, на которое ложится папка экспорта; `null` — корень |

Статусы записи (`SyncEntry.status`): `added` — есть на диске, нет в базе; `modified` — есть в обоих, содержимое расходится; `unchanged` — совпадает; `missing` — есть в базе, но не в папке.

**Ошибки:** `422` — не задан `kb.documents.export-path` или папки нет; `404` — `parentId` не найден

---

### POST `/api/documents/admin/import`
Импорт выбранных записей сравнения. `text/event-stream`: кадр `PROGRESS` на каждый записанный узел, затем `DONE` со сводкой `ImportSummary` (`created`, `updated`, `deleted`, `relinked`, `failed`).

Кадр `PROGRESS` импорта несёт `action` — `created`, `updated`, `deleted`, `relinked` или `failed`; у `failed` в `message` лежит причина отказа (текст исключения, без перевода). Из этих кадров и собирается журнал прогона: сводка говорит, сколько узлов пропущено, кадры — какие именно и почему. Узел, записанный дважды (создан, затем переписан вторым проходом по ссылкам), даёт два кадра.

**Request:**
```json
{ "parentId": 42, "paths": ["intro", "guides/setup"], "deleteMissing": false }
```

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `parentId` | Long? | `null` | Поддерево-приёмник; `null` — корень |
| `paths` | List\<String\>? | `null` | Пути из сравнения; `null`/пустой — всё, что меняется |
| `deleteMissing` | boolean | `false` | Удалять ли отмеченные записи со статусом `missing` |

## ChatController — `/api/chats`

### GET `/api/chats`
Список всех чатов текущего пользователя (только метаданные, без сообщений), отсортированный по `updatedAt` (сначала новые).

**Response:** `List<Chat>` — каждый с полями `model`, `mode` и `project` (выбранные в чате; `null` — дефолтные)

---

### GET `/api/chats/search`
Поиск чатов текущего пользователя по названию и/или содержимому сообщений (лупа над списком чатов). Объединяет оба вида совпадений по чату.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `q` | String | — | Поисковый запрос |
| `limit` | int | `20` | Макс. результатов (макс. 50) |

**Response:** `List<ChatSearchResult>`
```json
{
  "conversationId": "uuid",
  "topic": "string",
  "updatedAt": "2026-06-09T10:00:00",
  "titleMatched": true,
  "messageMatchCount": 3,
  "snippet": "string | null"
}
```

---

### GET `/api/chats/{conversationId}`
Получить чат с сообщениями.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `includeMessages` | boolean | `true` | `false` — только метаданные без сообщений |

**Response:** `Chat` (с полем `messages: List<ChatMessage>` при `includeMessages=true`, `null` при `false`)

**Ошибки:** `404` — не найден, `403` — чужой чат

---

### GET `/api/chats/{conversationId}/messages`
Пагинированная загрузка сообщений чата (без SYSTEM-сообщений и суммаризаций).

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `limit` | int | `20` | Размер страницы (1–100) |
| `beforeCreatedAt` | ISO datetime | — | Курсор: createdAt последнего загруженного сообщения |
| `beforeId` | long | — | Курсор: id последнего загруженного сообщения |

Без курсора — возвращает последние `limit` сообщений. С курсором — сообщения до указанной позиции.

**Response:** `MessagePage`
```json
{
  "messages": [ ... ],
  "hasMore": true,
  "oldestCursor": { "createdAt": "2026-06-09T10:00:00", "id": 42 }
}
```

Среди сообщений встречается строка-плашка «контекст сжат» — след команды `/compact`: без текста, с
полем `compact` (`{ "messages": 42, "summaryChars": 3800, "summaryId": 511 }`). Это единственное
сообщение, у которого поле непусто, — по нему клиент и отличает плашку от обычной реплики; текст её
сводки берётся отдельным `GET /compact`.

### POST `/api/chats/{conversationId}/runs`
Запустить фоновую генерацию ответа. Возвращает `runId` сразу, сам ответ приходит через SSE event channel (`GET /events`).

Сообщение пользователя сохраняется **синхронно, до старта генерации**, поэтому ответ несёт и его `messageId`. Ошибка записи становится ошибкой этого запроса, а не тихо потерянным вопросом.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `model` | String | — | ID модели (опционально) |
| `mode` | String | — | ID режима ассистента (опционально) |
| `project` | String | — | ID проекта (опционально) |
| `clientMsgId` | String | — | ID клиента-инициатора (защита от задвоения пузыря) |
| `retry` | boolean | `false` | Повтор упавшего прогона: тело не передаётся, новое сообщение не создаётся |

**Body:** `StartRunRequest` (JSON). При `retry=true` тело не нужно и игнорируется.
```json
{
  "text": "посмотри отчёт",
  "contextItems": [{ "kind": "ATTACHMENT", "ref": "12" }]
}
```

`contextItems` — что приложено к этому сообщению. Бэк проверяет каждую ссылку (вложение обязано
принадлежать этому чату), сам проставляет подпись с объекта и кладёт результат в `meta` того же
ряда `chat_message`. Подпись с клиента не принимается: в истории должно остаться имя файла, а не
то, что клиент решил про него написать.

**Response:** `200 OK`
```json
{ "runId": "uuid", "messageId": 123 }
```

При `retry=true` в `messageId` возвращается id **уже существующего** вопроса — того самого, который прогон и переигрывает.

**Ошибки:**
- `400 Bad Request` — пустой `text` без `retry=true`; неизвестный `kind`; больше 20 элементов контекста
- `404 Not Found` — вложение из `contextItems` не существует или принадлежит другому чату
- `409 Conflict` — генерация уже идёт в этом чате
- `422 Unprocessable Content` — `retry=true`, но повторять нечего: последнее сообщение чата — не
  неотвеченный вопрос. Повтор допустим ровно в одном состоянии: вопрос сохранён, а модель не выдала
  ни текста, ни вызова инструмента. Как только ответ начался, ход переигрывать нельзя — диалог
  продолжается обычным сообщением пользователя.

---

### POST `/api/chats/{conversationId}/compact`
Сжать контекст чата — бэкенд команды `/compact` в композере. Живой контекст ДО этой команды
(несжатые сообщения плюс уже накопленные сводки) уходит модели **одним запросом, теми же
сообщениями, что и в обычном прогоне**: протокольные `tool_calls` с полными аргументами и
TOOL-ответы с полными результатами внутри. Результат заменяет это окно одной строкой-сводкой —
живого хвоста, в отличие от фоновой суммаризации, не остаётся.

Сама команда сохраняется обычным USER-сообщением и остаётся видна в истории, как любая
реплика (эхо — обычное событие `USER_MESSAGE`, см. ниже), но в окно, которое уходит модели на
сжатие, не входит — вместо неё в конец запроса встаёт инструкция сжатия (системный промпт —
`prompt/compactor.md`). По завершении раунда позиция команды тоже помечается `summarized`, вместе
со сжатым окном: дальше она видна пользователю, но не едет модели. Модель для раунда — та, на
которой работает чат.

Возвращает `runId` сразу: раунд идёт по всему окну и живёт десятки секунд, а исход приезжает
событиями `COMPACT_DONE` / `COMPACT_ERROR` через `GET /events`. Пока он идёт, чат занят так же,
как на генерации (`GET /runs/active` отдаёт этот `runId`), но остановить его нельзя — прогона
за ним нет, и `POST /runs/{runId}/stop` вернёт no-op.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `clientMsgId` | String | — | ID клиента-инициатора — тот же смысл, что у `POST /runs` |

**Body:** `CompactRequest` (JSON) — сообщение целиком.
```json
{ "text": "/compact подробнее про миграции", "instructions": "подробнее про миграции" }
```

`text` — сообщение как оно набрано, сохраняется дословно. `instructions` — хвост команды, уходит
фокусом сжатия: названное получает больше деталей, но остальные разделы сводки всё равно
заполняются полностью.

**Response:** `200 OK`
```json
{ "runId": "uuid", "messageId": 123 }
```

`messageId` — id сохранённой команды, тот же приём, что у `POST /runs`: отправившая вкладка гасит
своё эхо `USER_MESSAGE` по `clientMsgId` и узнаёт id только отсюда.

**Ошибки:**
- `400 Bad Request` — пустой `text`
- `404 Not Found` / `403 Forbidden` — чата нет или он чужой
- `409 Conflict` — чат занят: идёт генерация или другое сжатие. Команда не сохраняется
- `422 Unprocessable Content` — сжимать нечего: живой контекст уже состоит из одной сводки.
  Команда не сохраняется — реплика, которая ничего не сделала, не должна маячить в истории

### GET `/api/chats/{conversationId}/compact`
Детали одного сжатия: числа с его плашки и текст получившейся сводки. Отдельным запросом, а не
полем страницы истории: сводка бывает в десятки килобайт, а открывают её изредка и по одной.

| Параметр | Тип | По умолчанию | Описание |

### GET `/api/chats/projects`
Проекты (репозитории), между которыми можно выбирать, и какой из них дефолтный.

**Response:** `ProjectOptions`
```json
{
  "defaultProject": "kb",
  "projects": [
    { "id": "kb", "label": "Knowledge Base", "available": true },
    { "id": "archive", "label": "Archive", "available": false }
  ]
}
```

`available: false` — проект настроен, но его репозиторий не открылся при старте (не доехал том):
вызовы к нему отвечают `503`, а селектор помечает такой проект «(недоступен)». Из списка он при этом
не исчезает: «проекта нет в списке» уже означает другое — его выключили или убрали из конфигурации,
и чат, который его выбрал, предупреждают отдельно.

`defaultProject` назван явно, а не подразумевается первым элементом: чат хранит `project: null`,
пока пользователь ничего не выбрал, и селектор должен знать, что подсветить. Путь проекта на диск
здесь не отдаётся — он есть только в админском `GET /api/admin/system`.

Включённых записей `kb.projects` может быть сколько угодно (см. [конфигурацию](конфигурация.md)),
но список из одного элемента — нормальное состояние, а не признак ошибки: типовой деплой
обслуживает один репозиторий.

**Проект чата может отсутствовать в этом списке.** `Chat.project` отдаёт то, что записано в чате, а
не то, что сейчас настроено: проект могли выключить (`enabled: false`) или убрать из конфигурации.
Сам чат от этого не ломается — прогон уезжает на дефолтный проект, — но клиенту стоит сказать, что
прежний проект больше недоступен, иначе пользователь решит, что видит его файлы.

---

Отдельного эндпоинта смены проекта нет — выбор становится проектом чата только вместе с
отправленным сообщением (`?project=` на `POST /runs` и `POST /messages`). Так сохранённое у чата
значение всегда означает «на каком проекте шла история», и ровно с ним бэкенд сверяет каждое новое
сообщение: если проект сменился, вопрос получает маркер в `meta` (`project`, `projectSwitchFrom`) —
модель видит предупреждение «всё выше читано в другом репозитории», фронт рисует плашку-разделитель.
Выбор в селекторе до отправки живёт только на фронте. Повтор упавшего прогона (`POST /runs` без
текста) нового вопроса не создаёт — там маркер садится на повторяемый вопрос и считается заново:
`projectSwitchFrom` остаётся прежним (он про историю выше), а возврат в исходный проект маркер
снимает, и событие `USER_MESSAGE` приезжает уже без него.

Проект чата определяет, в каком репозитории работают инструменты модели (`readFile`, `grep`,
`runScript`, `searchCodebase` и правки файлов). Резолв — параметр запроса → сохранённый в чате →
дефолтный; проект, исчезнувший из конфигурации или выключенный, не ломает чат, а молча уступает
дефолтному (см. про `Chat.project` выше) — с тем же маркером смены на первом сообщении после этого.
Тем же сообщением сохранённое значение приводится к дефолтному: маркеру место ровно на одном
вопросе, а не на каждом до конца чата.

### GET `/api/settings/tools`
Каталог инструментов, доступных модели прямо сейчас, для группы «Настройки → Инструменты». Список собран из тех же `ToolCallback`, что отданы `ChatClient` (`ChatToolset` → `ToolCatalogService`), поэтому отражает фактическую конфигурацию: без `kb.projects[].edit-enabled` в нём нет `createFile`/`editFile`, без `kb.script.enabled` — `runScript`, а инструменты внешних MCP-серверов появляются только при `kb.mcp.enabled`.

**Response:** `List<ToolInfo>`, отсортирован по имени
```json
[
  {
    "name": "searchDocuments",
    "description": "Search knowledge base documents by topic/keywords (hybrid: keyword + semantic).",
    "origin": "builtin",
    "params": [
      { "name": "query", "type": "string", "description": "Search query in any language.", "required": true, "values": [] },
      { "name": "mode", "type": "string", "description": "Search mode: hybrid (default), semantic, keyword.", "required": false, "values": [] }
    ]
  }
]
```

`description` — то самое описание из `@Tool`, которое читает модель. `params` разбираются из JSON-схемы инструмента: `type` — `string`/`integer`/`array<string>`/имя определения из `$ref`, `values` — допустимые значения перечислимого аргумента (иначе пусто). `origin` — `builtin` (собственный `@Tool`) или `mcp` (инструмент внешнего сервера); нечитаемая схема стоит инструменту списка аргументов, но не места в каталоге.

### POST `/api/settings/script/run`
Пробный запуск скрипта из «Настройки → Скрипты». Тот же `ScriptRunner`, что у инструмента `runScript`, те же бюджеты и тот же формат ответа — но скрипт пишет человек, а не модель.

**Body:**
```json
{ "script": "return kb.files('**/*.md').length;", "timeoutSeconds": 10 }
```

| Поле | Тип | Описание |
|---|---|---|
| `script` | String | Тело скрипта; выполняется как тело функции — верхнеуровневый `return` разрешён |
| `timeoutSeconds` | int? | Бюджет прогона; `null` — `kb.script.timeout`, больше `kb.script.max-timeout` — молча урезается |

**Response:** `ScriptResult` — `{ project, value, log, stats, error, filesRead, edits }`. Упавший скрипт — это `200 OK` с заполненным `error` (`kind` = `SYNTAX|RUNTIME|TIMEOUT|BUDGET`), а не HTTP-ошибка: разбирать причину и есть смысл стенда. Исключение — `maxResultChars`: превышение не даёт `error`, а обрезает `value` до лимита и добавляет предупреждение в `log`.

Запуск **всегда read-only**: методы записи (`kb.edit`, `kb.create`, `kb.writeBytes`, `kb.createBytes`) в песочницу не привязываются, как бы ни был выставлен `kb.script.edit-enabled`, поэтому `edits` здесь всегда пуст.

**Ошибки:** `409` — `kb.script.enabled=false` (скрипты выключены в деплое), `400` — пустое тело скрипта

## GitController — `/api/git`

Read-only эндпоинты для автодополнения `/file` в композере чата и для файлового браузера (раздел «Файлы») плюс `GET /capabilities` — какие git-элементы управления панель вправе показать. Делегируют в `GitService`, который обеспечивает доступ только к tracked-файлам, защиту от path traversal и ограничения по бинарным/большим файлам.

Каждый эндпоинт принимает необязательный `project` — id проекта из `GET /api/chats/projects`. Без него отдаётся дефолтный проект (первый в `kb.projects`), с неизвестным — `400`: открыть «тот же путь, но в другом репозитории» молча хуже, чем не открыть ничего. Проект настроен, но его репозиторий не открылся (не доехал mount) — `503`: сервер работает, недоступен именно этот проект.

### GET `/api/git/files/search`
Fuzzy-поиск tracked-файлов по имени (subsequence match, регистронезависимо). Результаты ранжированы: лучшее совпадение первым.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `q` | String | — | Часть имени файла, например `mgi` → `MessageInput` |
| `limit` | int | `10` | Макс. результатов |
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `List<GitFileNode>` — `{ path, name, type: "file", size, tracked }`. `tracked: false` — файл виден только через `kb.projects[].allow-globs` проекта (истории в git у него нет); интерфейс помечает такие узлы.

### GET `/api/git/browse`
Открыть путь в файловом браузере **одним** запросом: сервер сам определяет, файл это или каталог, отдаёт содержимое (или листинг) и листинги всех каталогов-предков — чтобы дерево слева раскрылось до узла без запроса на каждый уровень вложенности. До этого эндпоинта переход по ссылке вида `/files/a/b/c/d/E.java` стоил клиенту около десяти последовательных `/tree` плюс запрос содержимого.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `path` | String? | `null` | Путь относительно корня репо; пусто — корень |
| `ancestors` | boolean | `true` | `false` — не отдавать листинги предков (клиент уже держит их в кэше) |
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `GitPathView` — `{ path, type: "file"|"directory"|null, file?, nodes?, tree: [{ path, nodes }], tracked }`. `file` — только для файла, `nodes` (потомки) — только для каталога, `tree` — листинги от корня до родителя пути.

**Ошибки:** `400` — путь содержит `..`, `/`, `-` в начале, `\0`. Несуществующий путь — не ошибка, а `type: null`.

### GET `/api/git/status`
Незакоммиченные изменения рабочего дерева — режим «Изменения» файлового браузера. Отслеживаемые файлы диффятся против `HEAD` (независимо от индекса, то есть семантика `git diff HEAD`), следом идут неотслеживаемые файлы, допущенные `kb.projects[].allow-globs`, под собственным статусом `U`. Скрытое `.gitignore` не показывается.

Патчи по умолчанию выключены и запрашиваются по одному файлу: списку слева хватает счётчиков, а собирать diff всего рабочего дерева ради одного открытого файла — запрос на каждый клик.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `path` | String? | `null` | Сузить ответ до одного файла; переименование находится по обоим именам |
| `patch` | boolean | `false` | Включить текст unified diff |
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `List<GitDiffEntry>` — `{ status, path, oldPath, additions, deletions, patchHeader, patch }`. Статусы: `A`, `M`, `D`, `R`, `C`, `U`. Служебная шапка патча (`diff --git`, `index`, `--- a/…`, `+++ b/…`) приходит отдельным полем `patchHeader`, а `patch` начинается с первого `@@`. У файла без незакоммиченных изменений ответ — пустой список, а не `404`.

**Ошибки:** `400` — путь содержит `..`, `/`, `-` в начале, `\0`

### GET `/api/git/branches`
На какой ветке рабочее дерево, насколько оно разошлось с upstream и какие ветки есть ещё — индикатор ветки в панели «Файлы» и список, из которого выбирают переключение.

Обычное чтение, доступно независимо от `git-commands`: панель говорит, какую ветку показывает, даже когда менять её никому не разрешено. Счётчики читаются по refs на диске — они настолько свежие, насколько свеж последний `fetch`; в сеть этот эндпоинт не ходит.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `GitBranchStatus` — `{ current, detached, unborn, upstream, ahead, behind, branches }`. `current` — короткое имя ветки, а при `detached: true` — сокращённый хэш коммита. `unborn: true` — свежий `git init`: имя у ветки есть, коммитов нет, `branches` пуст. `upstream: null` — ветка ничего не отслеживает, и оба счётчика нулевые и ничего не значат.

### POST `/api/git/fetch`
Обновить remote-refs (`git fetch --prune --no-tags`) — то, что даёт смысл счётчику «позади»: он читается именно по этим refs. Рабочее дерево не трогается: ничего не сливается, файлы не меняются, `pull` остаётся отдельным шагом.

Команда пользователя, а не инструмент модели: разрешается через `kb.projects[].git-commands.enabled` и отклоняется на read-only рабочем дереве. Одновременно по одному репозиторию выполняется одна команда — вторая получает `409`, а не очередь.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `GitCommandResult` — `{ command, output, status }`, где `status` — тот же `GitBranchStatus` уже после команды (клиенту не приходится дорисовывать состояние, которое было до неё), а `output` — собственный вывод git.

**Ошибки:** `400` — неизвестный проект · `403` — команды для проекта не разрешены или дерево read-only · `409` — по репозиторию уже выполняется команда · `422` — git отказал · `503` — репозиторий проекта не открылся. Тело отказа — `{ "message": "…" }` с текстом самого git (`Permission denied (publickey)`): по нему видно, что чинить.

### GET `/api/git/capabilities`
Что интерфейс вправе предлагать пользователю по этому репозиторию: открылся ли он вообще, разрешены ли на нём git-команды пользователя и входит ли в них `push`. Единственный эндпоинт раздела не про содержимое, а про сам проект.

Спрашивается отдельно, а не читается из списка проектов: список клиент кэширует, а этот ответ следует текущему состоянию рабочего дерева — перемонтированный `ro` mount отзывает команды на живом сервере. К инструментам модели отношения не имеет: команды выполняет человек в интерфейсе.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `GitCapabilities` — `{ project, available, commands, push }`. `project` — id того проекта, про который ответ (кто проект не назвал, узнаёт, какой получил). `available: false` — репозиторий не открылся, и остальные поля тоже `false`. `commands` — локальные команды и сетевые чтения (ветки, switch, stash, commit, discard, `merge --abort`, fetch, pull); `push` — публикация в remote, всегда `false` при `commands: false`.

**Ошибки:** `400` — неизвестный id проекта

### GET `/api/git/commits`
История коммитов, свежие первыми. Вкладка «Инфо» файлового браузера запрашивает `limit=1` по пути — кто и когда последним менял файл.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `path` | String? | `null` | Ограничить историю одним файлом/каталогом |
| `limit` | int | `20` | Макс. коммитов (не больше 100) |
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `List<GitCommit>` — `{ hash, shortHash, author, email, date, message }`

### GET `/api/git/commits/search`
Поиск коммита для диалога заполнения плейсхолдеров (тип `commit`). Совпадением считается префикс хэша или подстрока темы коммита — регистр не важен. Тело сообщения не ищется: в строке выдачи видна только тема, и попадание по телу читалось бы как случайный результат.

Индекса ни по хэшу, ни по тексту у git нет, поэтому это линейный обход от HEAD, ограниченный 2000 коммитами.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `q` | String | — | Префикс хэша или подстрока темы; пустой → `[]` |
| `limit` | int | `10` | Макс. коммитов (не больше 100) |
| `project` | String? | `null` | ID проекта; пусто — дефолтный |

**Response:** `List<GitCommit>` — тот же формат, что и у `/api/git/commits`

## PhraseController — `/api/phrases` и `/api/admin/phrases`

### Публичные (чат)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/phrases` | Только `enabled`, `ORDER BY category, position` |
| `PATCH` | `/api/phrases/{id}/favorite?value=true\|false` | Переключить избранное |

### Админские (настройки)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/admin/phrases?q=` | Все фразы (вкл. выключенные); `q` — быстрый поиск по `label` (ILIKE) |
| `POST` | `/api/admin/phrases` | Создать (добавляется в конец своей категории) |
| `PUT` | `/api/admin/phrases/{id}` | Изменить (смена категории → переезд в конец новой) |
| `DELETE` | `/api/admin/phrases/{id}` | Удалить |
| `PATCH` | `/api/admin/phrases/{id}/favorite?value=` | То же, что публичный тоггл |
| `PATCH` | `/api/admin/phrases/{id}/enabled?value=` | Переключить только флаг `enabled` |
| `PATCH` | `/api/admin/phrases/{id}/move` | Переупорядочить; тело `{ "position": <слот соседа> }` |

**Ошибки:**
- `404` — неизвестный `id` (NoSuchElementException)
- `400` — пустое `category`/`label`/`text` после трима (IllegalArgumentException)
- `DELETE` → `204 No Content`

## SystemInfoController — `/api/admin/system`

Read-only вид конфигурации сервера для Admin-панели. Содержит информацию о профиле, БД, репозитории и параметрах поиска. **Внимание:** секреты (пароли, API-ключи) никогда не возвращаются.

### GET `/api/admin/system`
Получить полную информацию о конфигурации сервера.

**Response:** `ServerInfo` со следующими полями:

| Поле | Тип | Описание |
|---|---|---|

| `javaVersion` | String | Версия JDK (например, `25`) |
| `springBootVersion` | String | Версия Spring Boot |
| `springAiVersion` | String | Версия Spring AI |
| `datasourceUrl` | String | URL БД (логины/пароли удаляются) |
| `datasourceType` | String | Тип БД (например, `PostgreSQL 17` или `H2`) |
| `gitProjectPath` | String | Путь к Git-репозиторию проекта |
| `documentsExportPath` | String | Путь для экспорта документов |
| `embeddingModel` | String | Модель эмбеддингов |
| `embeddingCacheEnabled` | boolean | Кэширование эмбеддингов включено |
| `semanticSearchEnabled` | boolean | Семантический поиск включён |

**Ошибки:**

## Примечания

### Версии и обновления

Все версии, указанные в API Reference, соответствуют текущей версии приложения (см. [Архитектура](архитектура.md), раздел 2 — Технологический стек).

### Authentication

Все эндпоинты требуют HTTP Basic-аутентификацию с пользователем/паролем из `kb.security.*` (см. [Конфигурация](конфигурация.md)).

### Content-Type

Все запросы и ответы используют `application/json`, кроме эндпоинтов, которые явно указывают другой тип (например, `text/plain` для содержимого файлов).
