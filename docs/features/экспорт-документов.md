# Экспорт и импорт документов

Обмен базы знаний с файловой системой в обе стороны: выгрузка дерева в Markdown + опционально YAML-метаданные и обратная загрузка из той же папки — через сравнение и выбор того, что применять. Плюс скачивание отдельного узла из интерфейса: документ как `.md`, папка как `.zip`.

> **Связанные документы:** [API Reference](../проект/api-reference.md) · [Конфигурация](../проект/конфигурация.md) · [Документы](../проект/модели-данных/документы.md) · [Администрирование](администрирование-руководство-пользователя.md)

## Формат экспорта

Экспорт создаёт следующую структуру в директории, указанной в `kb.documents.export-path`:

```
export-dir/
├── .index.md              # упорядоченный список всех корневых элементов
├── vvedenie.md             # документ → .md файл (только description, без заголовка)
├── vvedenie.yaml           # метаданные документа (только при meta=true)
├── arkhitektura.md
├── arkhitektura.yaml
├── modeli-dannykh/         # папка (имя: lower-case, спецсимволы → дефисы)
│   ├── .index.md           # упорядоченный список детей папки
│   ├── .content.md         # описание папки (всегда создаётся, может быть пустым)
│   ├── .meta.yaml          # метаданные папки (только при meta=true)
│   ├── dokumenty.md
│   ├── dokumenty.yaml
│   ├── chat.md
│   └── ...
└── features/
    ├── .index.md
    ├── .content.md
    └── ...
```

### Типы файлов

| Файл | Назначение |
|---|---|
| `название.md` | Тело документа — только description, без заголовка (заголовок в метаданных) |
| `название.yaml` | Метаданные документа: id, title, type, parentId, position, updatedAt (только при `meta=true`) |
| `.index.md` | Упорядоченный список детей папки в Markdown; папки ссылаются на `.content.md`, документы — на `.md` |
| `.content.md` | Описание папки (создаётся всегда, даже для пустых папок) |
| `.meta.yaml` | Метаданные папки (только при `meta=true`) |

### Правила именования

- Заголовки документов приводятся к нижнему регистру, спецсимволы и пробелы заменяются на дефисы: `safeName()` → `modeli-dannykh`, `vvedenie`
- Кириллица сохраняется как есть (транслитерация не применяется)
- Если два соседа дают одно и то же имя, второму добавляется суффикс: `doc.md` → `doc-1.md`. Решение принимается один раз, в первом проходе, поэтому карта ссылок и файлы на диске не расходятся
- При `replace=false` то же правило дополнительно обходит файлы, оставшиеся от прошлой выгрузки; при `replace=true` они перезаписываются
- Служебные файлы папок используют префикс `.` (скрытые)

**Заголовок и порядок живут только в `.index.md`.** Имя файла нормализовано и теряет регистр и пунктуацию, поэтому обратная загрузка берёт человеческое название и позицию именно оттуда.

## Перезапись ссылок

Все внутренние ссылки вида `[Название](/?doc=ID)` в содержимом документов автоматически заменяются на относительные пути файловой системы:

```
[Архитектура](../проект/архитектура.md)  →  [Архитектура](arkhitektura.md)
[Модели данных](../проект/модели-данных/.content.md) →  [Модели данных](modeli-dannykh/.content.md)
```

Ссылки на папки резолвятся в `.content.md`. Если целевой документ не найден в дереве — ссылка остаётся без изменений. Это делает экспортированные документы полностью автономными — ссылки работают при просмотре в любом Markdown-редакторе или на GitHub.

Импорт делает обратное преобразование: относительная ссылка, ведущая на известный файл экспорта, снова становится `(/?doc=ID)`.

Односторонним остаётся только одно преобразование: ссылки на файлы репозитория `[Git.java](/files?path=...)` при экспорте превращаются в обычный текст `Git.java (backend/.../Git.java)` — снаружи приложения обслуживать `/files` некому. Из текста ссылка не восстанавливается, поэтому импорт такого документа (если его правда меняли на диске) её потеряет.

## Как это устроено внутри

**Ничего не читается целиком.** Обход дерева (`DocumentTreeReader`) идёт по одному уровню за запрос и берёт из БД только структуру — id, заголовок, тип, позицию, — без `description`. Тело документа подтягивается отдельным запросом ровно в тот момент, когда пишется его файл, и тут же забывается. Пиковая память экспорта — один документ, а не база знаний.

**Проходов два, и это неустранимо.** Документ может ссылаться на соседа, до которого обход ещё не дошёл, поэтому сначала строится карта `id → путь файла` (только пути, без содержимого), и лишь потом пишутся файлы. Второй проход не пересчитывает имена, а берёт их из карты первого: при `replace=false` именование зависит от того, что уже лежит на диске, а диск к тому моменту уже меняется.

**Скачивание узла ничего не буферизует.** `GET /api/documents/{id}/download` для папки отдаёт zip, который собирается прямо в ответ: узел отрендерен → положен в архив → забыт. Размер поддерева на память сервера не влияет.

## Импорт: сравнение, потом выбор

Импорт — это две операции, а не одна.

**Сравнение** (`GET /admin/import/diff`) читает папку и базу параллельно, уровень за уровнем, и на каждый узел выдаёт запись со статусом:

| Статус | Что значит | Что сделает импорт |
|---|---|---|
| `added` | Есть на диске, в базе нет | Создаст узел |
| `modified` | Есть в обоих, содержимое или заголовок расходятся | Перезапишет описание (и заголовок) |
| `unchanged` | Совпадает | Ничего |
| `missing` | Есть в базе, в папке нет | Удалит — но только если явно попросить |

Сравнение ничего не пишет: это ответ на вопрос «что изменится, если импортировать».

**Применение** (`POST /admin/import`) получает список выбранных путей и делает только их. Именно это разделение делает повторный импорт безопасным: без него каждый прогон создавал бы дерево заново.

### Сопоставление по пути

Запись на диске и узел в базе — это одно и то же, когда совпадают их пути экспорта (цепочка `safeName` через `/`). Метаданные из `.yaml` не читаются: папка, выгруженная без `meta`, импортируется точно так же, как выгруженная с ним.

Плата за это — переименование узла в приложении выглядит как удаление плюс добавление. Сравнение показывает это честно, а не пытается угадать.

### Что считается изменением

Сторона базы рендерится тем же кодом, которым пишет экспорт, и сравнивается с байтами на диске. То есть документ совпадает ровно тогда, когда свежий экспорт дал бы лежащий там файл — сразу после выгрузки сравнение показывает «изменений нет». Переводы строк и обрамляющие пустые строки нормализуются.

### Сколько записей на узел

Один проход создаёт и обновляет узлы текстом как есть, второй возвращается **только к тем**, в чьём теле действительно были относительные ссылки, — перечитывает файл с диска и переписывает ссылки в `/?doc=ID`. У подавляющего большинства документов ссылок нет, и они пишутся один раз. В сводке такие «вторые записи» видны как `relinked`.

Каждый узел — своя транзакция: заголовок, который не удалось применить (системный узел), стоит одного узла, а не всего прогона; такие узлы попадают в `failed`, и импорт идёт дальше.

### Ограничения

- Новая папка, которую **не** отметили, забирает с собой всё своё поддерево — детей не к чему прицепить. Интерфейс отмечает предков автоматически; при работе через API отмечайте их сами.
- Смена типа узла (папка ↔ документ) на месте не применяется: такая запись попадает в `failed`.
- Порядок новых узлов внутри уровня — в конец, в порядке `.index.md`. При полном импорте в пустое дерево это в точности порядок из индекса.
- Загрузки архива из браузера нет: импорт идёт из серверной папки `kb.documents.export-path`.

## Прогресс операций

Экспорт, сравнение и импорт устроены на бэке одинаково: они принимают `Consumer<SyncEvent>` и отдают сводку. `SyncJobRunner` превращает это в `text/event-stream`.

| Кадр | Когда | Полезная нагрузка |
|---|---|---|
| `ENTRY` | Решён очередной узел сравнения | `entry` — запись `SyncEntry` |
| `PROGRESS` | Записан очередной узел | `path` — путь узла |
| `DONE` | Терминальный | `summary` — `DiffSummary` / `ImportSummary` / `{ files }` |
| `ERROR` | Терминальный | `message` — причина, пригодная для показа |

Задача выполняется на отдельном виртуальном потоке (`documentSyncExecutor`) — возврат `SseEmitter` освобождает поток сервлета. Если браузер отключился, следующая отправка не проходит и задача снимается, а не домалывает дерево, на которое уже никто не смотрит.

## API

Полное описание параметров и тел — в [API Reference](../проект/api-reference.md).

| Эндпоинт | Назначение |
|---|---|
| `POST /api/documents/admin/export` | Экспорт в серверную папку, `204` без тела |
| `POST /api/documents/admin/export/stream` | То же с прогрессом (SSE) |
| `GET /api/documents/{id}/download` | Скачать узел: `.md` или `.zip` поддерева |
| `GET /api/documents/admin/import/diff` | Сравнить папку с базой (SSE), ничего не пишет |
| `POST /api/documents/admin/import` | Импортировать выбранное (SSE) |
| `POST /api/documents/admin/reindex` | Полная переиндексация семантического поиска |

## Интерфейс

**Администрирование → Массовые операции** (`BulkOperations.jsx`):

- **Экспорт всех документов** — кнопка «Выгрузить», чекбокс «С метаданными (.yaml)», под ней во время работы — счётчик и путь текущего узла (`ExportOperation.jsx`)
- **Сравнить папку с базой** и **Импортировать отмеченное** (`ImportOperation.jsx`) — сравнение выводит список различий (`SyncDiffList.jsx`) с галочками; совпадающие записи скрыты по умолчанию, потому что сразу после экспорта их сто процентов
- **Путь выгрузки** — рядом показан текущий `kb.documents.export-path`: без него «не удалось выгрузить» неотличимо от незаданного `DOCUMENTS_EXPORT_PATH`

Логика галочек (`syncSelection.js`): отметка ребёнка автоматически отмечает новых предков, снятие папки снимает её потомков.

**База знаний → шапка узла** — кнопка скачивания рядом с переименованием и удалением. Это обычная ссылка `<a download>`, а не `fetch`: браузер стримит ответ в файл, содержимое не проходит через память вкладки.

## Конфигурация

В `application.yaml`:

```yaml
kb:
  documents:
    export-path: ${KB_DOCUMENTS_EXPORT_PATH:./exported-docs}
    replace: true   # перезаписывать существующие файлы (false → суффиксы -1, -2...)
```

| Параметр | Переменная окружения | Описание |
|---|---|---|
| `kb.documents.export-path` | `KB_DOCUMENTS_EXPORT_PATH` | Путь к директории для экспорта и источник импорта |
| `kb.documents.replace` | — | Перезаписывать ли существующие файлы при совпадении имён |

## Примечания

- Вложения в экспорт и импорт не включаются
- История изменений (`document_history`) не экспортируется, но импорт её пополняет: запись описания идёт обычным путём `DocumentService.update`, со снимком и постановкой задачи на эмбеддинг
- Формат оптимизирован для чтения человеком и хранения в Git
