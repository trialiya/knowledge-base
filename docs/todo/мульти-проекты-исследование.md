# Несколько проектов (репозиториев) — проработка

Статус: **чек-лист «до второго проекта» закрыт целиком** — guard снят,
несколько включённых проектов обслуживаются, деплой на них рассчитан (§10).
Из фазы 2 сделаны чипы и ссылки с проектом, проект в аргументах tools и маркер
смены проекта; остальное — исследование. Задача была: приложение обслуживало
ровно один репозиторий, нужно несколько — с выбором проекта в каждом чате,
возможностью сменить его по ходу диалога, корректной работой инструментов,
ссылок на файлы и панели «Файлы».

Документ отвечает на три вопроса: **что именно сегодня привязано к одному
проекту**, **какие есть пути реализации у каждого узла** и **в каком порядке
это делать**, чтобы каждый шаг был отдельным PR.

---

## 1. Инвентаризация: где живёт «единственный проект»

### 1.1 Бэкенд

| Точка | Что делает | Чем мешает |
|---|---|---|
| `GitProperties` (`kb.git.project-path`, `edit-enabled`) | одна строка пути, один флаг записи | одна пара на весь процесс |
| `GitService` | singleton; в полях `repoPath`, `repoRealPath`, `repository`, `git`; в конструкторе открывает JGit и **падает**, если `.git` нет | один экземпляр = один репозиторий; падение на старте недопустимо, когда проектов много |
| `GitFunction`, `GitEditFunction` | tools модели, держат `GitService` полем | ссылаются на конкретный репозиторий |
| `ScriptRunner`, `ScriptSession`, `KbScriptApi`, `KbEditScriptApi` | `GitService` полем; `runScript` ходит в файлы через него | то же |
| `ScriptEditPolicy` | `kb.git.edit-enabled` + `kb.script.edit-enabled` + writable-дерево | политика записи глобальная, а у проектов она разная (один ro-mount, другой rw) |
| `GitController` (`/api/git/**`) | `browse`/`tree`/`content`/`search`/`commits` без параметра проекта | весь фронт (панель файлов, чипы, превью) адресует файлы одним путём |
| `SearchAgentService` | получает `GitFunction`/`ScriptFunction` при сборке бина | сабагент обязан искать в том же проекте, что и родительский прогон |
| `SystemInfoController`, `SettingsController` | показывают один `project-path` | админка/настройки должны показывать список |
| `DocumentLinkRewriter` | regex `[(текст)](/files?path=PATH[#Lx-Ly])` | формат ссылки не несёт проекта |
| `prompt/sys.md` | «Files, commits → Git repo» — репозиторий один и безымянный | модель не знает, что проектов несколько и какой сейчас активен |

### 1.2 Фронтенд

| Точка | Что делает |
|---|---|
| `filesPanel/useFileTree` + `fileTreeStore` | модульный кэш каталогов, ключ — только `path` |
| `urlScheme.filesPath` / `/files/<path>` | адрес файла не содержит проекта |
| `common/docLinkParsing.parseFileLink` | разбирает `/files?path=…` и `/files/<path>` |
| `chatPanel/fileChips` | токены `⟦file:PATH⟧`, `⟦ref:PATH⟧`, `⟦commit:HASH:SUBJECT⟧` — без проекта |
| `common/useFilePreview` + `usePreviewCache` | кэш превью по пути |
| `api/gitApi` | все вызовы `/api/git/*` без проекта |
| `App.jsx` `refreshToken` | «в репозитории что-то поменялось» — сигнал общий на всё |

### 1.3 Деплой

Первый проект монтируется в фиксированный `/project` (`ENV PROJECT_PATH=/project`,
`${PROJECT_PATH_MOUNT}:/project:ro`), остальные — в `/projects/<id>`, по одному
тому на проект.

`git grep` идёт subprocess'ом из корня репозитория, а рабочее дерево принадлежит
хостовому пользователю — без исключения `safe.directory` git отвечает «dubious
ownership». Проверено на живом git 2.43: без исключения — отказ; с точным путём в
`--system` — работает, в том числе из подкаталогов; **глобов нет** — ни
`/projects/*`, ни любой другой шаблон, кроме `*` («доверять всему»), не
принимаются. Отсюда раскладка: путь первого проекта фиксирован образом и
прописан в `Dockerfile`, пути остальных известны только в рантайме — их
перебирает `docker/start.sh` (`/projects/*` с `.git` внутри) и добавляет
исключения в `--global` (`HOME=/app`), заново на каждый старт.

### 1.4 Что к проекту НЕ привязано (и это решение, а не данность)

База знаний (`document`, `attachment`, эмбеддинги, поиск) живёт в БД и общая для
всего сервера; `kb.documents.export-path` — одна папка. Вложения чата привязаны
к чату. Модели и режимы — глобальный конфиг. Пока считаем это правильным:
проект = репозиторий кода, БЗ — общая (см. §8, там же цена обратного решения).

## 2. Готовый шаблон: выбор модели в чате

Проект почти один в один повторяет уже реализованный «выбор модели», и это
главный аргумент за такую форму фичи — новых механизмов не нужно:

| Модель (есть) | Проект (нужно) |
|---|---|
| `kb.chat.models[]` + `default-model` в конфиге | `kb.projects[]` + `default-project` |
| `chat_topic.model` (nullable = дефолт) | `chat_topic.project` |
| `GET /api/chats/models` | `GET /api/chats/projects` |
| `PUT /api/chats/{id}/model` | `PUT /api/chats/{id}/project` |
| `?model=` на `POST /runs`, `resolveModel()` («запрос → сохранённое → null») | `?project=`, `resolveProject()` |
| `ChatModelProperties.isAllowed()` | `ProjectProperties.isAllowed()` |
| `ModelSelector` + `useModelConfig` + `ListboxSelect` | `ProjectSelector` + `useProjectConfig` |
| `Chat.model` в DTO, вкладка «Инфо» | `Chat.project` там же |

Отличие ровно одно, но существенное: **модель не меняет смысл истории, а проект
меняет** (§6).

## 3. Где описывать проекты: конфиг, БД или гибрид

**A. Только конфиг** (`kb.projects[]`, по образцу `kb.chat.models`):

```yaml
kb:
  projects:
    - id: kb
      label: Knowledge Base
      path: /projects/kb
      edit-enabled: false     # перекрывает kb.git.edit-enabled
    - id: billing
      label: Биллинг
      path: /projects/billing
```

Плюсы: путь на диск задаёт админ, а не пользователь (в БД-варианте `POST` с
`path: /etc` — это уже вопрос доверия к аутентифицированному пользователю); нет
миграций; ровно тот же паттерн, что у моделей; список проектов известен на
старте, значит реестр репозиториев строится один раз. Минусы: добавление
проекта = рестарт.

**B. Проекты в БД** + CRUD в админке. Плюсы: динамика. Минусы: миграции ×2
(Postgres + H2) плюс `sample-data.sql`/`SampleDataFixtureTest`; валидация путей
становится задачей рантайма; реестр JGit-репозиториев нужно уметь перестраивать
на лету; в контейнере новый путь всё равно не появится без монтирования — то
есть динамика половинчатая.

**C. Гибрид**: конфиг задаёт корневые каталоги (`kb.project-roots`), сервер
находит в них git-репозитории сам и показывает как проекты. Удобно для
«папка с десятком репозиториев», но добавляет сканирование ФС и делает `id`
производным от имени каталога (переименовали — поехали ссылки в истории).

**Рекомендация: A**, с `ProjectProperties`, устроенным как `ChatModelProperties`
(`isAllowed`, дефолтный проект, `List<ProjectOption>`). Переход на B позже
дешёвый: `ProjectRegistry` уже будет прослойкой, менять придётся только
источник списка. Совместимость: если `kb.projects` пуст, единственным проектом
становится `kb.git.project-path` с `id=default` — старые деплои не замечают
изменения.

## 4. Бэкенд: как проект доезжает до кода

### 4.1 `GitService` — три пути

**(a) Реестр экземпляров.** `GitService` остаётся как есть, но перестаёт быть
`@Service`-синглтоном: `GitRegistry` держит `Map<projectId, GitService>` и
`forProject(id)`. Потребители получают реестр вместо сервиса.
*Плюсы:* внутренности `GitService` (1905 строк, `requireInsideRepo`, кэш
tracked-путей, `git grep` в cwd репозитория) не трогаются вообще; изоляция
проектов гарантирована конструкцией. *Минусы:* правка сигнатур у всех
потребителей; `@PreDestroy` закрытия репозиториев переезжает в реестр.

**(b) Stateless-сервис**: каждый метод принимает `ProjectRef`.
*Минусы:* переписывание почти всего файла и всех вызовов — огромный шумный
дифф, в котором легко потерять правило «только tracked-файлы».

**(c) Текущий проект в `ThreadLocal` / scoped-бин.** *Минусы:* прогоны идут на
виртуальных потоках и через Reactor (`ChatRunService`), контекст туда не
распространяется автоматически — тот же класс багов, из-за которого
пользователя уже приходится протаскивать в `buildContext` руками.

**Рекомендация: (a).**

Дополнительно в реестре: **ленивое открытие** репозитория (проект, который в
этом запуске никто не открыл, не занимает дескрипторы) и **деградация вместо
падения** — сегодня недоступный путь валит контекст на старте; при нескольких
проектах один отвалившийся mount не должен ронять сервер: проект помечается
недоступным, tools возвращают внятную ошибку, UI показывает его выключенным.

### 4.2 Как проект попадает в tools

В `ToolContext` уже есть готовый паттерн ключей: `CONVERSATION_ID`, `USER_NAME`,
`ToolInvocationCollector.KEY`, `RunCancellation.KEY` (`ChatUtils.buildContext`).
Проект добавляется туда же — `PROJECT_ID`, и `GitFunction`/`GitEditFunction`/
`ScriptFunction` берут `GitRegistry.forProject(...)`.

Почему так, а не «набор tools на проект»: `ChatClientRegistry` уже ветвится по
моделям с собственным эндпоинтом; второе измерение дало бы произведение
клиентов, а `defaultTools(...)` фиксируется при сборке `ChatClient`. Контекст
же вычисляется на каждый прогон — там проекту и место.

Что придётся учесть:

- `GitFunction` сегодня не принимает `ToolContext` ни в одном методе — параметр
  добавляется во все ~7 tools. `ToolContext` не попадает в JSON-схему
  инструмента, так что **модель лишнего аргумента не увидит**;
  `ToolArgumentGapsTest` следит только за «обычными» параметрами.
- `ScriptRunner.run(...)` получает `projectId` (и `ScriptEditPolicy` становится
  per-project: у одного проекта дерево writable, у другого нет).
- `SearchAgentService` уже принимает `parentContext` — проект наследуется
  оттуда, отдельного канала не нужно.

**Сделано: проект как аргумент tool'а.** Необязательный `project` у
`getFileContent`, `grepContent` и `runScript` перекрывает проект прогона на один
вызов — ради кросс-проектных вопросов («сравни, как это сделано в A и в B»).
Пропущенный или пустой аргумент означает проект чата, поэтому обычный вызов не
изменился.

Риск был назван заранее — модель начнёт путать проекты и молча читать не тот, —
и снят обязательным эхом: `GitFileContent.project`, `GitGrepMatch.project`,
`ScriptResult.project`. Ответ всегда говорит, какой репозиторий отвечал, и
`sys.md` требует брать id для ссылки из ответа, а не из активного проекта. Аргумент
резолвится там же, где раньше резолвился только контекст (`GitFunction#git`,
`ScriptFunction#runScript`), так что изоляция путей осталась делом `GitRegistry`.

Правки (`createFile`, `editFile`) аргумента не получили: писать в репозиторий,
который пользователь в этом чате не выбирал, — не тот риск, который окупается
удобством. Из того же правила следует неочевидное: `runScript` писать умеет, и
поэтому прогон с названным чужим проектом принудительно read-only (`forceReadOnly`
— тот же механизм, которым обходится сабагент поиска). Иначе аргумент стал бы
ровно тем обходом выбора пользователя, ради запрета которого правкам его и не
дали; `ScriptEditPolicy` проверяет права уже названного проекта и такой лазейки
сам не закрыл бы.

**Починено:** `ToolInvocationCollector#hasSeenFile` сравнивал только путь, а он
теперь может быть прочитан в другом репозитории — чтение `src/App.java` в
проекте B засчитывалось бы как «файл видели» для правки `src/App.java` в
проекте A (`editFile`, `kb.edit`). Теперь `hasSeenFile` принимает канонический
`project` правки и для инструментов, умеющих читать чужой проект
(`getFileContent`, `grepContent`, `runScript`), сверяет его с тем же
обязательным эхом ответа, а не с сырым аргументом вызова — эхо уже несёт
канонизированный id, а аргумент мог быть не указан или назвать дефолтный
проект явно, и оба случая должны читаться как «свой». Для остальных
инструментов (`getFileOutline`, `editFile`, поиск по документам и т. д.)
сверка не нужна: они не умеют читать чужой проект вовсе.

Метка проекта на сообщениях (в UI, не в guard'е) — отдельная работа, ей это не
затронуто.

Сабагент поиска получает те же `ToolCallback`, поэтому аргумент виден и ему.
Сам он проектов не знает — `search-agent.md` о них не говорит и `{project_context}`
туда не подставляется, — так что по своей воле он аргумент не заполнит; а если
имя проекта приедет в тексте задачи, кросс-проектный поиск как раз и получится.
Выдуманный id падает на `ProjectCatalog#require` с перечислением настроенных,
то есть громко, а не молчаливым чтением чужого репозитория.

### 4.3 Системный промпт

Системное сообщение собирается на каждый прогон (`spec.system(sp -> sp.param(...))`
в `ChatController`/`ChatRunService`), в память не пишется. Значит новый
плейсхолдер `{project_context}` — имя проекта, корень, доступна ли запись,
одно-два предложения описания из конфига — **сам по себе доедет до следующего
ответа** после смены проекта, миграций не требует. Это и есть «как сказать
модели, какой проект сейчас».

## 5. Хранение выбора и API

- Миграция `chat_topic.project` — **четыре правки** по правилу репозитория:
  `db/migration`, `db/migration-h2`, `db/sample-data.sql`, `SampleDataFixtureTest`.
- `resolveProject(conversationId, requested)` — копия `resolveModel`: параметр
  запроса → сохранённое в чате → `null` (дефолтный проект). `null` в колонке
  означает «дефолт», как у модели: убрали проект из конфига — чат не ломается,
  фильтр `isAllowed` отбрасывает неизвестное значение.
- Эндпоинты: `GET /api/chats/projects`, `PUT /api/chats/{id}/project`,
  `?project=` на `POST /{id}/runs` и `POST /{id}/messages`.
- `/api/git/**` получает `project` параметром (или префиксом
  `/api/git/{projectId}/...` — см. §7).
- `SettingsController`/`SystemInfoController` отдают список проектов вместо
  одного пути (пути на диск — только в админке, как сейчас).

## 6. Смена проекта по ходу чата — главный содержательный вопрос

Смена модели ничего не портит: история остаётся правдой. Смена проекта делает
**часть истории ложной** — прочитанные файлы, пути, результаты `grep`,
`runScript` и `searchCodebase` относятся к другому репозиторию, но лежат в
контексте как обычные tool-ответы. Модель по умолчанию сочтёт их актуальными.

Варианты, от самого строгого к самому гибкому:

1. **Запрет смены после первого сообщения.** Селектор блокируется, как сейчас
   блокируется выбор модели во время стриминга; сменить проект = создать чат.
   Дёшево, предсказуемо, но пользователь просил именно возможность сменить.
2. **Форк чата.** Смена создаёт новый чат с тем же названием и без истории
   (или с summary истории). Честно, но плодит чаты.
3. **Маркер в истории.** В историю пишется сообщение-разделитель («Проект
   переключён: *Биллинг* → *KB*. Всё выше относится к прежнему проекту; пути и
   содержимое файлов оттуда здесь недействительны — перечитай нужное заново»).
   Технически это обычная строка `chat_message` со служебным флагом в `meta` —
   ровно тот приём, которым уже помечена «крошка» tool-вызовов
   (`ChatMessageMeta.toolCalls` + `isToolCalls`), поэтому фронт умеет не
   показывать такую строку как обычный текст, а нарисовать плашкой.
4. **Метка проекта на каждом сообщении** (`chat_message.meta.project`). Даёт UI
   возможность показать происхождение блока, а `SummarizeService` — не смешивать
   проекты в одном summary (и это уже не косметика: `prompt/summarizer.md`
   сжимает историю, и без метки проект в сжатом виде исчезнет).

**Рекомендация: 3 + 4**, плюс 1 как опция деплоя для строгих инсталляций.
Маркер обязан переживать сжатие — в `summarizer.md` добавляется правило «строки
о смене проекта сохраняй дословно».

**Сделано — вариант 3, но маркер не отдельной строкой, а в `meta` самого
вопроса** (`ChatMessageMeta.project` + `projectSwitchFrom`), тем же приёмом, что
вложения (`contextItems`): смена проекта — свойство сообщения, которое её
совершило, и отдельная строка истории ей не нужна. Решает бэкенд: выбор
становится проектом чата только с отправленным сообщением (`?project=` на
прогоне), эндпоинт `PUT /{id}/project` упразднён — поэтому `chat_topic.project`
всегда означает «на каком проекте шла история», и сравнение с ним и есть
детекция смены (`ChatController#projectSwitch`; сравнение по каноническим id,
проект, выбывший из конфигурации, сравнивается как есть). Первому сообщению
чата маркер не ставится — над пустой историей предупреждать не о чем.

Модель видит маркер как `<project-switched from to>`-блок, дописанный перед
вопросом при чтении истории (`ChatMemoryService#promptRow`) — в БД, как и опись
вложений, он не попадает; summarizer читает те же `PromptRow`, правило
«воспроизводи дословно и не смешивай стороны» добавлено в `summarizer.md`, а
summary-строка несёт в `meta.project` проект, на котором закончился сжатый
кусок. Фронт рисует плашку-разделитель перед вопросом (`MessageList`,
`.project-switch-divider`); живьём она доезжает эхом `USER_MESSAGE`
(оптимистичный пузырь смену не знает — её решает бэкенд).

Повтор упавшего прогона нового вопроса не создаёт, а проект при нём выбирают
заново — маркер садится на повторяемый вопрос (`ChatMemoryService#markProjectSwitch`),
причём `from` у уже помеченного вопроса не переписывается: он говорит, к какому
репозиторию относится история ВЫШЕ, а от повторов она не меняется.

Отдельно: активный прогон. Смену во время генерации фронт блокирует
(селектор), а на бэке отдельный запрет не нужен: без `PUT` сменить проект чата
можно только новым сообщением, а второй прогон на чат и так не запускается
(`activeByConversation`).

## 7. Ссылки на файлы и панель «Файлы»

Здесь больше всего мест и главный источник тихих ошибок: путь `backend/pom.xml`
существует в двух проектах, и ссылка без проекта откроет не тот файл.

**Адрес в UI.** По правилу «путь несёт открытый ресурс, query — состояние
экрана» проект — часть идентичности: `/files/<projectId>/<path…>`. Старый
`/files/<path>` и `?path=` остаются и канонизируются в дефолтный проект — фронт
уже обязан поддерживать старые формы ссылок (`readUrl`), так что механизм есть.

**Формат ссылки в markdown**, который пишет модель (по `sys.md`) и переписывает
`DocumentLinkRewriter` — сейчас `[текст](/files?path=PATH#L1-L10)`. Наименее
травматичное расширение — `&project=ID`: старые ссылки в уже сохранённых
документах и сообщениях остаются валидными и означают дефолтный проект.
Правятся: regex в `DocumentLinkRewriter`, `parseFileLink` в `docLinkParsing`,
инструкция в `sys.md`, «плоское» разворачивание ссылки при экспорте (там в
скобках стоит путь — добавится имя проекта).

**Чипы композера** (`⟦file:PATH⟧`, `⟦ref:PATH⟧`, `⟦commit:HASH:SUBJECT⟧`).
Два пути:
- *квалифицировать токен* — требует парсера обеих форм, зато чип перестаёт
  зависеть от того, что выбрано в чате сейчас;
- *резолвить по проекту чата в момент отправки* — формат не меняется, но при
  смене проекта черновик с чипами становится мусором.

**Сделано: квалификация** — `⟦file@PROJECT:PATH⟧`, `⟦ref@PROJECT:PATH⟧`,
`⟦commit@PROJECT:HASH:SUBJECT⟧`. Разделитель `@`, а не второй сегмент через
двоеточие (`⟦file:PROJECT:PATH⟧`, как предполагалось изначально): двоеточие в пути
законно, и `⟦file:docs:notes.md⟧` было бы не отличить от проекта `docs`, а после
имени вида стоит либо `@`, либо `:` — разбор однозначен при любом пути. Токен без
проекта остаётся валидным и означает репозиторий чата: так писала прежняя версия
формата, и такие токены лежат в сохранённых черновиках (`chatDrafts`). Смена
проекта в чате вписывает в них прежний проект, пока он ещё известен, — тот же
приём, что у бэкенда с сохранёнными ссылками (`FileLinkProjectBackfillService`).

**Кэши на фронте.** `fileTreeStore` (каталоги + раскрытые узлы) и
`usePreviewCache` (превью файлов) ключуются по пути — ключ становится
`projectId + path`. Без этого дерево одного проекта покажется в другом; это
самый вероятный баг всей фичи, потому что кэш модульный и переживает уход в
другой раздел.

**Сама панель.** Выбор проекта — в шапке левой панели раздела «Файлы».
Синхронизировать его с проектом активного чата жёстко не стоит (панель — не
чат), но переход по ссылке из чата обязан открывать файл **в проекте этой
ссылки**, переключая панель. `refreshToken` («файл изменён инструментом») должен
нести проект, иначе правка в одном проекте сбросит кэш другого.

## 8. База знаний, поиск, экспорт

Минимальный вариант (рекомендуемый на первых фазах): **документы остаются
общими**. Один и тот же документ описывает несколько репозиториев чаще, чем
кажется, а привязка — это колонка `document.project`, фильтр в дереве, в
keyword- и semantic-поиске, в `searchDocs` скрипта, отдельный
`export-path` на проект и миграции ×2. Отдельная фаза, и начинать с неё не надо.

Промежуточный шаг, если общая БЗ начнёт мешать: не привязка, а **приоритет** —
в промпте указать, к какому проекту относится текущий чат, и разрешить модели
самой выбирать релевантные документы (она и так решает, что читать).

## 9. Безопасность и эксплуатация

- **Изоляция путей.** `requireInsideRepo` работает внутри одного `GitService` и
  сравнивает с `repoRealPath` — при реестре это автоматически даёт изоляцию
  между проектами. Отдельно валидируется сам `projectId`: только из списка,
  никаких путей из запроса (это и есть главный довод за конфиг, §3).
- **Права на запись — per project.** `edit-enabled` в записи проекта плюс
  проверка writable-дерева (сегодня — `ChatConfig#gitEditFunction`, которая
  просто не создаёт бин). При нескольких проектах «есть ли у модели правки»
  перестаёт быть свойством деплоя и становится свойством прогона: набор tools
  один, а отказ должен приходить из tool'а с внятным текстом. Это заметная
  смена модели поведения — её нужно проговорить в `sys.md`.
- `kb.script.allow-globs`/`deny-globs` — тоже кандидаты на per-project.
- **Ресурсы.** JGit `Repository` держит открытый индекс и дескрипторы; `git
  grep` — subprocess с cwd проекта. На десятках проектов нужен ленивый открытие
  + закрытие давно не используемых.
- **Недоступный проект** (mount отвалился) — не падение старта, а состояние.

## 10. Порядок работ

**Фаза 0 — рефакторинг без фичи. Сделано.** `kb.projects` в конфигурации (ровно
одна запись, вторая роняет старт — `ProjectCatalog`), `GitRegistry` с
экземпляром `GitService` на проект, ключ `projectId` в `ToolContext`
(`ProjectContext`), `GitFunction`/`GitEditFunction`/`ScriptRunner`/
`ScriptEditPolicy` резолвят проект по вызову, «проект не назван» = первый в
списке. `kb.git.project-path` остался как прежняя форма записи и подставляется
значением по умолчанию, так что деплой не меняется. API, фронтенд и промпты не
тронуты — проект пока никто не выбирает, поэтому всё едет на дефолтном.

**Фаза 1 — проект как выбор чата.**

*Бэкенд и API — сделано.* `chat_topic.project` (миграция ×2), `resolveProject`
рядом с `resolveModel`, `GET /api/chats/projects` + `PUT /{id}/project` +
`?project=` на `runs`/`messages`, `project` в DTO `Chat`, необязательный
`project` на всех `/api/git/**`. Выбранный проект едет в `ToolContext`
(`RunOptions.project` → `ProjectContext.KEY`), поэтому инструменты прогона и
сабагент поиска читают именно его репозиторий. Резолв — как у модели: параметр
запроса → сохранённое в чате → дефолт; проект, убранный из конфига, чат не
ломает.

*Промпт и ссылки — сделано.* `{project_context}` в `sys.md` (`ProjectPromptService`)
называет модели активный проект и готовый кусок ссылки; формат ссылки на файл
стал `[текст](/files?path=PATH&project=ID#Lx-Ly)` — в `sys.md`, в трёх `mode-*.md`
и в описании `getFileContent`. `DocumentLinkRewriter` понимает обе формы, а при
экспорте проект схлопывается вместе с диапазоном строк. Уже сохранённые ссылки
(история чатов, документы и их версии) размечены run-once бэкафиллом
`FileLinkProjectBackfillService` — иначе смысл старой ссылки поехал бы в тот день,
когда первым в списке станет другой репозиторий. Заодно `kb.projects[].enabled`:
выключенный проект не обслуживается, а чат сохраняет его id — по расхождению со
списком фронт и покажет «проект больше недоступен».

*Фронт — сделано.* `ProjectSelector` под полем ввода рядом с моделью и режимом
(выбор запоминается за чатом и в localStorage, блокируется на время генерации);
плашка «проект недоступен», когда сохранённый у чата проект исчез из конфигурации.
Панель «Файлы» получила свой селектор репозитория и адрес `/files/<path>?project=`
— проект в query, а не сегментом: сегментом его не отличить от каталога в корне
репозитория, а ждать список проектов, чтобы прочитать адрес, значит не уметь
прочитать его синхронно. Все вызовы `/api/git/**` несут проект, а модульные кэши
(`fileTreeStore`, превью файлов, содержимое чипов) разложены по проектам — это и
был самый вероятный баг фичи. Ссылка из чата открывает файл в проекте ЭТОЙ ссылки
и переключает панель.

Чипы композера несут проект (§7), поэтому смена проекта не портит черновик: чип
остаётся о своём репозитории, а при отправке содержимое читается из него и в
сообщении подписано именем проекта — иначе модель прочтёт путь как свой. Чипы
документов проект не несут: база знаний общая.

*Чек-лист до второго проекта.* Адреса, чипы, кэши и tools проект уже несут;
держит ограничение «один включённый проект» (guard в `ProjectCatalog`) вот что:

1. ~~Маркер смены проекта в истории~~ — **сделано** (§6: `meta` вопроса, детекция
   на приёме сообщения, `PUT /{id}/project` упразднён, предупреждение модели в
   `promptRow`, правило в `summarizer.md`, плашка на фронте).
2. ~~Метка проекта на сообщениях + summary~~ — **сделано в объёме, нужном
   guard'ам и сжатию**: `meta.project` стоит на вопросе-переключателе и на
   summary-строке (проект, на котором закончился сжатый кусок). Метка на
   *каждом* сообщении (происхождение блока в UI, §6 вариант 4 целиком) — не
   делалась и вторыми проектом не блокирует.
3. ~~Снять guard~~ — **сделано**: `ProjectCatalog` обслуживает все включённые
   записи, первая остаётся ответом на «проект не назван». Тест guard'а заменён
   на «несколько проектов обслуживаются, первый — дефолтный».
4. ~~Деплой~~ — **сделано**: в `application.yaml` лежит слот второго проекта
   (`PROJECT2_*`, выключен), в обоих compose — закомментированный mount
   `/projects/<id>`, в `example.env` — переменные, в `docs/проект/конфигурация.md`
   — инструкция «как включить». Исключения `safe.directory` для непервых проектов
   ставит `docker/start.sh` на старте: путей их git не знает заранее, а глобов
   `safe.directory` не понимает (проверено на git 2.43 — работает либо точный
   путь, либо `*`).
5. ~~Деградация недоступного проекта~~ — **сделано**: `GitRegistry` ловит отказ
   на открытии репозитория и оставляет проект настроенным, но неработающим
   (`ERROR` в лог, отказ по имени проекта в `forProject`, `editsAllowed` — false).
   Сервер при этом стартует. Исключение — первый проект: его получает всякий, кто
   проект не назвал, поэтому его отказ по-прежнему роняет старт.

6. ~~Признак недоступного проекта в UI~~ — **сделано**: `GET /api/chats/projects`
   отдаёт `available`, селекторы (панель «Файлы» и композер чата) помечают такой
   проект «(недоступен)». Заодно селектор репозитория в «Файлах» переехал на
   место заголовка панели — панель показывает один репозиторий, его имя и есть
   её заголовок.

**Фаза 2 — качество.** Квалификация чипов композера и ссылок в markdown —
*сделано* (§7); проект в аргументах tools с эхом в ответе — *сделано* (§4.2);
маркер смены проекта и project в meta — *сделано* (§6). Осталось: per-project
script-политики (`allow-globs`/`deny-globs`); метка проекта на каждом сообщении,
если UI она понадобится.

**Фаза 3 — динамика.** Проекты в БД + админка; при необходимости — привязка
документов БЗ и per-project экспорт.

Документация, которую придётся править вместе с кодом: `docs/проект/конфигурация.md`
(`kb.projects`, монтирования), `api-reference.md`, `архитектура.md`,
`обзор-чат-системы.md`, `docs/features/файлы-руководство-пользователя.md` и
`чат-руководство-пользователя.md`.
