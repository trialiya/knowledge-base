# Git-команды для пользователя (pull/switch/push/…) — анализ

Статус: **исследование, кода нет**. Задача: дать *пользователю* (не модели)
возможность выполнять git-команды над проектом — сначала из панели «Файлы»,
затем из чата, с уведомлением модели о выполненных командах (по образцу
маркера смены проекта). Возможность включается явно в конфигурации проекта.

Документ отвечает на четыре вопроса: **какие команды нужны и в каких
«ярусах» риска они живут**, **на какие готовые узлы кодовой базы это
ложится**, **какие ограничения и конфликты надо продумать заранее** и
**в каком порядке делать**.

---

## 1. Обзор команд: что нужно и что не нужно

Команды делятся на три яруса — у каждого свой уровень риска и свои
предусловия. Ярус, а не отдельная команда, — единица включения и UI-паттерна
(что подтверждать, что показывать, что стримить).

### Ярус A — чтение (риска нет, часть уже есть)

| Команда | Что даёт | Сегодня |
|---|---|---|
| `status` | грязное ли дерево, ahead/behind | есть: `getUncommittedChanges` + вкладка «Changes» |
| `log` | история | есть: `/api/git/commits` |
| `branch` (список), current branch | что вообще есть и где мы | **нет** — нужен для UI switch'а |
| `fetch` | обновить remote-refs, узнать behind | **нет**; сетевой, но дерево не трогает |
| `remote -v` (инфо) | куда идёт push/pull | нет; достаточно показать в UI |

### Ярус B — локальные изменения (обратимо, но конфликтогенно)

| Команда | Зачем пользователю | Главный риск |
|---|---|---|
| `switch <branch>` | переключить проект на ветку | незакоммиченные изменения (см. §4) |
| `switch -c <name>` | новая ветка перед работой | почти безрисково |
| `add` + `commit` | зафиксировать правки (свои и модельные — `GitWriter` уже стейджит) | нечего коммитить; автор коммита (§5.4) |
| `stash push` / `stash pop` | увести/вернуть изменения вокруг pull/switch | конфликт на pop |
| `restore` (discard файла) | откатить файл к HEAD | **необратимая потеря правок** — отдельное подтверждение |
| `merge --abort` | выйти из неудачного merge после pull | нужен, иначе pull-конфликт — тупик для пользователя |

### Ярус C — сетевые мутации (нужны креды, влияют на remote)

| Команда | Риск |
|---|---|
| `pull` (= fetch + merge) | конфликты, грязное дерево, креды |
| `push` | отклонение non-fast-forward; публикация наружу |

### Сознательно не даём

`rebase` (интерактивность, переписывание истории), `reset --hard` на ветку
(есть точечный discard), `push --force*`, `clean -fd`, произвольные аргументы
и вообще «строка команды»: поверхность — **фиксированный набор глаголов** с
типизированными параметрами, не shell. Это важно и для README, который
обещает «no command execution»: фича должна быть описана как
user-initiated fixed-verb операции, а не как доступ к консоли.

## 2. На что это ложится в кодовой базе

Инфраструктура почти вся есть:

- **`GitService`** (`service/file/git/`) — открытый JGit `Repository`/`Git`
  на проект; `GitRegistry` — один инстанс на проект и единственный ответчик
  на «можно ли писать» (`editsAllowed` = конфиг × `Files.isWritable`).
- **`GitWriter`** — образец «отдельный класс на мутации рядом с большим
  read-сервисом». Новый `GitCommands` (или `GitWorkflow`) — такой же сосед.
- **`GitService.exec()`** — готовый ProcessBuilder-паттерн (сейчас только
  `git grep`); пригодится, если решим шеллаутить pull/push (§5.2).
- **Флаги проекта** — `ProjectProperties.ProjectOption`: `editEnabled`,
  `untrackedEditEnabled` уже задают паттерн «выключено по умолчанию,
  валидируется в `ProjectCatalog`, комбинируется с физикой в `GitRegistry`».
- **Панель файлов** — `FilesToolbar.jsx` (группа кнопок), `ConfirmModal`,
  `useNotice`; сигнал инвалидации — `filesRefreshTick` в `App.jsx`,
  его бампаем после успешных pull/switch/stash/commit.
- **Стриминг долгих операций** — SSE-протокол `useJobStream` +
  `SyncJobRunner`/`SyncEvent` (админка) — готовый шаблон для вывода pull/push.
- **Маркер смены проекта** — точный образец для «пользователь выполнил
  git-команду» в чате: `ChatMessageMeta` (+ `MetaJson` в конвертере!) →
  нотис собирается на чтении в `ChatHistoryService.promptRow()` →
  правило «preserve verbatim» в `prompt/summarizer.md` → баннер в
  `MessageList.jsx`.

## 3. Конфигурация и гейтинг

Новый флаг на проект, по умолчанию выключен:

```yaml
kb:
  projects:
    - id: kb
      path: /projects/kb
      git-commands-enabled: true   # ярусы A(fetch)+B
      git-push-enabled: true       # ярус C push — отдельный флаг
```

Почему два флага, а не один: push — единственная операция, которая
*публикует* содержимое наружу; включить «pull и порядок в рабочем дереве»
без права публикации — реальный сценарий. `git-push-enabled` только сужает
`git-commands-enabled` (паттерн `untrackedEditEnabled`).

Гейт — в `GitRegistry`, зеркально `editsAllowed`:

```
gitCommandsAllowed(id) = flag && repoOpened && Files.isWritable(root)
```

`Files.isWritable` обязателен: дефолтный проект монтируется `:ro` (§10
мульти-проектного исследования) — на нём pull физически невозможен, и UI
должен честно не показывать кнопки, что бы ни говорил конфиг. Плюс
`safe.directory` уже должен покрывать пути (grep шеллаутится) — для
pull/push это тем более обязательно.

Наружу флаг отдаётся не через `ProjectView` «в лоб» (он сознательно узкий),
а либо одним булевым полем `gitCommands`/`gitPush` в `ProjectView`
(минимально), либо `GET /api/git/capabilities?project=` — второе лучше,
т.к. ответ зависит от живого состояния дерева (ro-remount) и не должен
кэшироваться вместе со списком проектов.

## 4. Главные ограничения: грязное дерево и конфликты

Центральная проблема задачи. Состояния, в которые попадает репозиторий:

**4.1 `pull` при незакоммиченных изменениях.** Git отказывает, если merge
затронет изменённые файлы («would be overwritten»). Правильное поведение —
не чинить самим, а *предсказать и предложить*: перед pull дергаем status;
если дерево грязное — модалка с выбором: «stash → pull → pop» /
«commit → pull» / отмена. Молчаливый auto-stash делать нельзя: pop сам
может конфликтовать, и пользователь должен знать, что его правки уезжали
в stash.

**4.2 Конфликты merge после pull.** Даже с чистым деревом pull может
закончиться конфликтом. Репозиторий остаётся в состоянии `MERGING` — и это
состояние видят *все*: вкладка «Changes» уже показывает конфликтующие файлы
(`status.getConflicting()` учтён в `getUncommittedChanges`), модельные
инструменты читают дерево с маркерами `<<<<<<<`. Обязательный минимум:
- баннер «repository in merge state» в панели файлов, пока
  `repository.getRepositoryState() != SAFE`;
- кнопка `merge --abort` — гарантированный выход;
- разрешение конфликта руками (через правки файлов + commit) — уже
  возможно существующими средствами.

**4.3 `switch` при незакоммиченных изменениях.** Git разрешает switch,
если изменения не пересекаются с diff'ом веток — и тогда изменения «едут»
на новую ветку (само по себе легально, но неожиданно). Если пересекаются —
отказ. Поведение как в 4.1: предсказали, предложили stash/commit/отмену.
Никогда не `switch --force`/`--discard-changes`.

**4.4 Незакоммиченные правки — общие с моделью.** `GitWriter` стейджит всё,
что правит модель. Пользовательский `stash`/`commit`/`discard` оперирует и
этими правками тоже. Это скорее фича (пользователь коммитит работу модели),
но: (а) discard теряет работу модели безвозвратно — подтверждение обязано
показывать список файлов; (б) если git-команда выполняется, пока идёт run
модели, дерево меняется у неё под ногами. Минимальная защита — мьютекс на
проект: одна мутирующая git-операция за раз, и отказ (или очередь), если
активен run с включёнными edit-инструментами по этому проекту.

**4.5 `push`-отказы.** Non-fast-forward после чужого пуша — показать
«remote ahead, сделайте pull», не предлагать force. Detached HEAD
(теоретически возможен после ручных манипуляций на хосте) — push и commit
блокируются с внятным сообщением; в UI показываем текущий HEAD.

**4.6 Кэши и индексы.** После pull/switch/stash: бамп `filesRefreshTick`
(деревья, changes, diff, preview перечитаются); кэш `fileTreeStore` и
`usePreviewCache` инвалидируются им же. Векторный индекс НЕ затрагивается —
он про базу знаний, не про файлы репозитория. `OutlineService` — проверить,
кэширует ли по содержимому (hash) или по пути.

**4.7 Креды для fetch/pull/push.** Самое неприятное операционное
ограничение. Репозитории — примонтированные хостовые деревья; их remote'ы
могут требовать ssh-агента или credential helper'а хоста, которых в
контейнере нет. Решения по нарастающей: (1) документировать «remote должен
быть доступен из контейнера» (deploy-ключ, https c токеном в URL/insteadOf);
(2) шеллаут в системный `git`, который сам подхватит helper'ы, если они
настроены в образе; (3) поле для PAT в конфиге — только если очень нужно, и
тогда токен не должен светиться ни в логах, ни в argv (`GIT_ASKPASS`/env).
Начать с (1)+(2).

## 5. Решения, которые надо принять

**5.1 Один эндпоинт или по эндпоинту на глагол.** По глаголу
(`POST /api/git/pull`, `/switch`, `/stash`, …): типизированные тела, разные
предусловия и разные ответы; «универсальный executor» провоцирует
командную строку. Мутирующие роуты — в отдельный `GitCommandController`,
чтобы `GitController` остался read-only, как обещает его javadoc.

**5.2 JGit или шеллаут.** JGit покрывает всё нужное (Pull/Push/Checkout/
Stash/MergeCommand), даёт типизированные результаты (`MergeResult` со
списком конфликтов вместо парсинга stdout) и не тянет argv-риски. Минусы —
креды (нужен `CredentialsProvider`/ssh-транспорт) и отличия в
merge-поведении от нативного git. Шеллаут проще с кредами (система сама),
но требует парсить вывод и следить за argv (`-`-префиксы у веток — уже есть
паттерн отказа в `requireSafePath`). **Рекомендация: JGit для локальных
операций (switch/stash/commit/status/branch — ярусы A и B), решение по
fetch/pull/push отложить до проверки кредов в реальном деплое; вероятен
шеллаут по образцу `exec()`.** Валидация имён веток — `Repository.isValidRefName`.

**5.3 Синхронно или SSE.** Локальные операции — синхронный JSON (быстрые).
fetch/pull/push — потенциально долгие и «разговорчивые»: SSE по протоколу
`useJobStream` (ENTRY/PROGRESS/DONE/ERROR), прогресс из
`ProgressMonitor'а` JGit или stdout'а git.

**5.4 Автор коммита.** Пользователь один (basic auth), у git-identity в
контейнере может не быть. Задать явно: `user.name`/`user.email` из
конфигурации (`kb.git.author.*` или на проект), иначе коммит упадёт или
подпишется мусором.

**5.5 Результат в чат (фаза 2).** Копия механики project switch:
- в `ChatMessageMeta` — поле `gitEvents` (список: команда, проект, итог —
  «pulled 3 commits, fast-forward», «switched to feature/x»), два правка-
  места: сам класс и `MetaJson` в `ChatMessageMetaToJsonConverter`;
- нотис `<git-command …>` собирается на чтении в `promptRow()`, в контент
  сообщения не пишется; правило «preserve verbatim» — в `summarizer.md`;
- баннер в `MessageList.jsx` (i18n `chat.json`, en+ru);
- выполнение из чата — либо кнопки в панели чата, либо slash-команды в
  `run/chatCommands.js` (`/pull` по образцу `/compact`, у которого уже есть
  прецедент событийной тройки `COMPACT_STARTED/DONE/ERROR` в
  `ChatEventType`).

Важно: команды из чата выполняет **бэкенд по прямому действию пользователя**,
модель tools для pull/push не получает — набор инструментов модели не
меняется вовсе, меняется только то, что она *узнаёт* о случившемся.

## 6. Порядок работ (каждый шаг — отдельный PR)

1. **Конфиг + гейт + capabilities.** Флаги в `ProjectOption`/`Project`,
   `gitCommandsAllowed`/`requireGitCommands` в `GitRegistry`,
   `GET /api/git/capabilities`. Документация: `конфигурация.md`.
2. **Ярус A.** `branches`/`current`/`fetch` (+ ahead/behind в статусе).
   UI: индикатор ветки и behind-счётчик в `FilesToolbar`.
3. **Ярус B.** switch / create-branch / stash / commit / discard /
   merge-abort, `GitCommands` рядом с `GitWriter`, предпроверки грязного
   дерева, модалки, баннер merge-state, бамп `filesRefreshTick`.
   Руководство пользователя в `docs/features/`.
4. **Ярус C.** pull/push через SSE, решение по кредам на реальном деплое.
5. **Чат-фаза.** `gitEvents` в meta, нотис в `promptRow`, summarizer,
   баннер, slash-команды.

Открытые вопросы перед стартом: (а) подтвердить схему кредов на боевом
деплое (решает §5.2 для яруса C); (б) нужен ли мьютекс «git-операция ↔
активный run с edit» уже в ярусе B (склоняюсь — да, он дешёвый);
(в) хотим ли выбор remote/ветки у push или всегда `origin`/upstream
текущей (для первой версии — всегда текущая).
