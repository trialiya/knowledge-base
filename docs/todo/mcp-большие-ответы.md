# Большие ответы внешних MCP — план

Статус: стадии A и B (шаг 1) реализованы, шаг 2 — проработка. Два шага: **(1)** лимит на то, что
ответ MCP-инструмента приносит в контекст модели, с полной копией на бэкенде;
**(2)** вызов MCP-инструментов из `runScript`, чтобы фильтровал детерминированный
код, а модель видела только выжимку.

## 1. Как сейчас

Цепочка вызова MCP-инструмента моделью:

```
ChatRunService → ChatToolset.all() → McpToolRegistry.callbacks()
  → RecordingToolCallback( SyncMcpToolCallback | UnavailableToolCallback )
```

- `McpToolRegistry#published` оборачивает инструмент подключения в
  `RecordingToolCallback` (и в `UnavailableToolCallback`, пока сервер лежит).
  Ни одна обёртка строку результата не трогает.
- `SyncMcpToolCallback#call` (Spring AI 2.0.1) возвращает
  `jsonHelper.toJson(response.content())` — JSON-массив блоков контента
  `[{"type":"text","text":"…"}]`. Полезная нагрузка обычно лежит строкой JSON
  внутри `text`, то есть закодирована дважды. `structuredContent` теряется.
  Картинки (`{"type":"image","data":"<base64>"}`) уходят модели целиком.
- `isError` и исключения клиента превращаются в `ToolExecutionException` с
  `response.content()` в сообщении — тоже без ограничения размера.
- Итог: ответ в 200 КБ целиком ложится в контекст, переживает компакцию только
  как кусок истории и стоит токенов на каждом следующем шаге прогона.

Для встроенных инструментов эта проблема уже решена — для скриптов:

| Что | Где |
| --- | --- |
| Модель видит значение, обрезанное до `kb.script.limits.max-result-chars` (20 000) | `ScriptResultKeeper` |
| Полное значение лежит под `rN` в `chat_script_result` (до `kb.script.results.max-chars`, последние `keep-per-chat`) | `ChatScriptResults` (`ScriptResultStore`) |
| Следующий скрипт читает его через `kb.result('rN')` | `KbScriptApi#result`, `ScriptResultReader` |
| `saveScriptResult` сохраняет его во вложение, не пропуская через модель | `ScriptResultFunction` |

Оба шага ниже опираются на эту полку, а не строят вторую.

## 2. Общая основа: нормализация ответа MCP

Новый класс `tools/McpContent` (утилита без состояния). Нужен обоим шагам,
поэтому делается первым.

`McpContent.normalize(String contentJson) → Normalized(Object value, String json, int omittedBinaryBytes)`:

1. Разобрать JSON-массив блоков, который вернул `SyncMcpToolCallback`/`Async…`.
2. Блоки `image`/`audio`/blob-ресурсы заменить заглушкой
   `{"type":"image","mimeType":"image/png","omitted":"340 KB"}`: base64 в
   контексте модели бесполезен и почти всегда больше всего остального.
3. Развернуть:
   - один `text`-блок, текст которого парсится как JSON → это JSON-значение;
   - один `text`-блок → строка;
   - иначе → массив блоков как есть (после п. 2).
4. Не разобралось (сервер вернул не то, что обещал протокол) → исходная строка.

Одно и то же значение и показывает начало модели (шаг 1), и лежит под `rN`
(шаг 1), и возвращается из `mcp.call` (шаг 2). Поэтому
`kb.result('r7')` и повторный `mcp.call(...)` скрипт видит одинаково.

Маленький ответ (≤ лимита) **не** нормализуется для модели — уходит байт в байт
как сейчас. Меньше неожиданностей и никаких изменений для небольших серверов.

## 3. Шаг 1 — лимит и полная копия

### 3.1. Обёртка

Новый `tools/McpResultLimitCallback implements ToolCallback` — по образцу
`UnavailableToolCallback`: `getToolDefinition()`/`getToolMetadata()` делегируются
(список инструментов и кэш префикса промпта не меняются), меняется только `call`.

`McpToolRegistry#published` становится:

```
UP   → Recording( Limit( tool ) )
DOWN → Recording( Unavailable( tool ) )
```

`RecordingToolCallback` остаётся снаружи: плашка и `resultText` в БД показывают
ровно то, что видела модель, — инвариант из `docs/todo/tool-результаты-отображение.md`
не ломается.

`call(input, toolContext)`:

1. `raw = delegate.call(input, toolContext)`.
2. `raw.length() <= limit(connection)` → вернуть `raw` как есть.
3. Иначе `n = McpContent.normalize(raw)`; если `ToolContext` несёт
   `conversationId` (`ChatUtils.conversationId`) — `store.keep(conversationId,
   "mcp:" + toolName, null, n.json())`. Метод `keep` уже никогда не бросает и сам
   отвечает «не сохранено, слишком большое / выключено».
4. Вернуть модели конверт вместо сырого ответа:

```json
{
  "truncated": true,
  "totalChars": 184213,
  "resultId": "r7",
  "shape": {"type": "object", "keys": {"issues": "array[250] of {key,summary,status,…}", "total": "number"}},
  "head": "{\"issues\":[{\"key\":\"KB-1\",…",
  "hint": "Ответ обрезан до 20000 символов. Полный ответ сохранён как r7: разбери его скриптом (kb.result('r7')) или сохрани файлом (saveScriptResult r7). Чтобы не тянуть лишнее, сузь запрос к инструменту."
}
```

- `head` — начало `n.json()` (нормализованного, без base64), не сырого ответа:
  в лимит попадает полезный текст, а не экранирование.
- `shape` — обход на 2 уровня: ключи, типы, длины массивов, ключи первого
  элемента. Стоит пару сотен символов и сразу говорит модели, какой скрипт
  писать. Обход ограничен по числу ключей.
- `resultId: null` и другой `hint`, когда копия не сохранена: нет чата
  (вызов вне сохранённого диалога), `kb.script.results.enabled=false` или
  ответ больше `max-chars`. Причина берётся из `Kept.note()`.
- Подсказки про `kb.result` и `saveScriptResult` — только когда эти инструменты
  в сборке есть (`kb.script.enabled`); иначе одна фраза «сузь запрос».

`isError` / `ToolExecutionException`: сообщение обрезается тем же лимитом
(без сохранения) — иначе один ошибочный ответ сервера обходит всю защиту.

### 3.2. Хранилище

Та же `chat_script_result`, та же нумерация `rN` в чате. Колонка `script`
получает `mcp:<имя инструмента>`, `project` — `NULL` (колонка уже nullable).
Миграции нет. `kb.results()` в листинге показывает `mcp:jira_search` — для
модели это информативно.

Почему не своя таблица: `kb.result`, `saveScriptResult`, ротация по
`keep-per-chat`, лимит `max-chars` и удаление вместе с чатом уже работают.
Вторая полка означала бы вторую нумерацию (`m7` vs `r7`), и модель путалась бы.
Если позже понадобится различать источники в UI — колонка `source` отдельной
миграцией (четыре правки по правилам репо).

Что меняется в коде вокруг: `StoredScriptResult#script` и javadoc
`ScriptResultStore#keep` — «имя скрипта, или `mcp:<tool>` для ответа
MCP-инструмента»; комментарий миграции не трогаем (история), описание таблицы в
`docs/проект/модели-данных/чат.md` — обновить.

`ScriptResultStore` — интерфейс из пакета `service/chat/script`, а обёртка
живёт в `tools/`, который сейчас не импортирует ничего из `service`. Это
направление не открываем: обёртка получает узкий интерфейс
`tools/ToolResultShelf` (`keep(conversationId, label, json) → Kept`), а
`ChatConfig` реализует его поверх `ScriptResultStore`.

### 3.3. Конфигурация

В `McpProperties` (`kb.mcp.*`), по образцу `bearer-tokens`:

```yaml
kb:
  mcp:
    max-result-chars: ${KB_MCP_MAX_RESULT_CHARS:20000}   # ≤0 — без лимита (поведение до изменения)
    result-limits:                                       # подключение → свой лимит
      confluence: 60000
```

Лимит в символах, как у скриптов: токены зависят от модели, а символы видны в
логе и в настройках. Проверка при старте: `max-result-chars` больше
`kb.script.results.max-chars` — WARN (копия не поместится, и id не будет никогда).

Бин: `McpToolRegistry` получает `ScriptResultStore` (`ObjectProvider`, может
отсутствовать) и лимиты. Сейчас `published` — `static`; станет методом экземпляра.

### 3.4. Что видит пользователь

- Плашка вызова показывает конверт. В `ToolCallDetailModal` для
  `truncated: true` — бейдж «обрезано, полный ответ r7» (i18n `en`/`ru`).
  Отдельный рендерер не нужен: конверт — обычный JSON.
- Панель «Настройки → MCP» (`SettingsController`) показывает действующий лимит
  подключения рядом со статусом.

### 3.5. Тесты

- `McpContentTest`: один text-JSON, один text, несколько блоков, image → заглушка,
  мусор вместо массива.
- `McpResultLimitCallbackTest`: ответ под лимитом проходит байт в байт; над
  лимитом — конверт, значение сохранено в fake-`ScriptResultStore` (как в
  sandbox-тестах); без `conversationId`; store вернул `Kept.not(note)`; лимит

- `McpToolRegistryTest`: порядок обёрток для UP/DOWN.
- Интеграционно (`*IT`, H2/PG): `kb.result('rN')` в скрипте читает то, что
  сохранила обёртка.

## 4. Шаг 2 — MCP из скрипта

### 4.1. API для скрипта

Отдельный глобальный объект `mcp`, а не методы на `kb`:

```js
mcp.tools()                     // [{name, connection, description, available}] — только то, что этому прогону можно
mcp.call("jira_search")         // без аргументов
mcp.call("jira_search", {jql})  // → нормализованное значение (§2)
```

Почему не `kb.mcpCall`. Правило песочницы — «недоступный метод отсутствует, а
не отказывает», а при `HostAccess.EXPLICIT` набор методов задаётся классом
привязанного объекта. Методы на `kb` дали бы четыре класса (чтение/запись ×
с MCP/без), а `KbEditScriptApi` уже `final`. Отдельный объект привязывается
только тогда, когда прогону MCP разрешён. Иначе `mcp` просто не определён, и
модель получает `ReferenceError`, а не метод, который отказывает.

`mcp` — гостевая обёртка (как `kb-helpers.js` в `ScriptRunner`) над хост-объектом
`McpScriptApi` с двумя экспортированными методами `String tools()` и
`String call(String name, String argsJson)`. Аргументы сериализует
`JSON.stringify` гостя, ответ разбирает его `JSON.parse`. Хосту не нужно
конвертировать `Value` и строить прокси, у гостя — обычные JS-объекты, а
необязательный второй аргумент обёртка решает сама, без перегрузок по арности.

Пример, ради которого всё делается:

```js
const r = mcp.call("jira_search", { jql: "project = KB AND status = Open", maxResults: 500 });
return r.issues.map(i => ({ key: i.key, title: i.fields.summary, assignee: i.fields.assignee?.displayName }));
```

Сырые 400 КБ остаются в песочнице. Модель видит возвращённое значение — под
обычным `max-result-chars`, с `resultId` и `resultLimit`, как любой скрипт.

Имя — то же, под которым модель видит инструмент в своём списке (после
`STABLE_NAMES` и снятия дублей в реестре). Неизвестное или запрещённое имя →
ошибка со списком разрешённых имён.

### 4.2. Откуда берутся инструменты

`McpToolRegistry` публикует второй вид в том же снимке: `scriptTools()` —
`ScriptTool(name, connection, description, callback)`. В `callback` — сырой
инструмент для `UP` и `Unavailable(tool)` для `DOWN`, **без** `Limit` (скрипту
нужен весь ответ) и **без** `Recording` (вызов из скрипта — не отдельная плашка,
он попадает в журнал прогона, §4.6). Дубли имён снимаются так же, как в
`callbacks()`. Соединение каждого инструмента известно только реестру, а оно
нужно для проверки `script-access`.

Вызов идёт через `ToolCallback`, а не напрямую через `McpSyncClient`. Тогда
префиксы имён, `McpToolFilter`, «сервер лежит» и sync/async-клиенты работают
одинаково для модели и для скрипта. Ответ — та же JSON-строка блоков, её
разбирает `McpContent.normalize`.

### 4.3. Где живёт код

- `config/model/ScriptMcpProperties` — `kb.script.mcp.*`.
- `McpProperties.scriptAccess` — `kb.mcp.script-access.<соединение>.{tools, scheduled}`.
- `service/chat/script/ScriptMcpScope` — вид прогона: `NONE` (по умолчанию),
  `CHAT`, `SCHEDULED`. Новый компонент `ScriptRequest` с `withMcp(scope)`.
  Явное поле, а не вывод из `forceReadOnly`: `runScript` по чужому проекту тоже
  `forceReadOnly` (писать можно только в проект чата), но к MCP это отношения
  не имеет.
- `service/chat/script/ScriptMcp` — бин-шлюз уровня приложения: по запросу и
  прогону открывает `McpScriptApi` или отвечает «MCP этому прогону нет».
  `ScriptRunner` получает его шестым аргументом конструктора. Пятиаргументный
  конструктор остаётся (с `ScriptMcp.none()`), чтобы не трогать тесты песочницы.
- `service/chat/script/McpScriptApi` — хост-объект одного прогона: разрешённые
  инструменты, бюджеты, таймаут, нормализация, журнал.

Кто какой `ScriptMcpScope` ставит:

| Вызывающий | Вид |
| --- | --- |
| `ScriptFunction` — копия главного чата | `CHAT` (и для чужого проекта тоже) |
| `ScriptFunction.readOnly` — копия сабагента | `NONE` |
| `SavedScriptFunction`, `ChatScriptRun` (`/script`) | `CHAT` |
| `ScheduledScriptService` | `SCHEDULED` |
| `ScriptTestController` (стенд) | `NONE` |
| источник — вложение (`ScriptRunSource.Kind.ATTACHMENT`) | `ScriptRunner` понижает до `NONE`: код прислал тот, кто загрузил файл |

### 4.4. Права и бюджеты

Права и бюджеты разведены по двум местам. Какие инструменты скрипт вообще может
вызвать — свойство **сервера**, поэтому оно лежит в конфиге MCP рядом с его
токенами и заголовками (`McpProperties`). Сколько вызовов и байт тратит прогон —
свойство **песочницы**, это `kb.script.mcp.*`.

```yaml
kb:
  mcp:
    script-access:                    # имя соединения → что из него можно звать из скрипта
      jira:
        tools: [jira_search, jira_get_*]   # glob-и имён; соединения нет в списке — из скриптов не зовётся ничего
        scheduled: true                    # и из плановых скриптов тоже; по умолчанию false
      confluence:
        tools: ["*"]
  script:
    mcp:
      enabled: ${KB_SCRIPT_MCP_ENABLED:false}   # общий выключатель; без него script-access не читается
      max-calls: 20                             # вызовов MCP за прогон
      max-bytes: 16MB                           # суммарный размер ответов за прогон
```

Почему явный список инструментов, а не «всё, кроме пишущих»: признак
`readOnlyHint` сервер выставляет сам себе, и проверить его нельзя. Пишущий
инструмент, по ошибке помеченный как читающий, в цикле скрипта наделает дел
быстрее, чем модель успеет это заметить. Список в конфиге — решение
администратора, который этот сервер подключил. По умолчанию (соединения нет в
`script-access`) из скриптов не зовётся ничего — даже при
`kb.script.mcp.enabled=true`.

`kb.mcp.script-access` — отдельный компонент `McpProperties`, по образцу
`headers`. `ScriptMcpProperties` (`kb.script.mcp.*`) — отдельным классом, как
`ScriptResultProperties`: `ScriptProperties.Limits` в тестах собирается
позиционно, новый компонент тронул бы десятки мест.

Кому доступно:

| Прогон | `mcp` |
| --- | --- |
| `runScript` / `runSavedScript` / `/script` в чате | инструменты из `script-access.<соединение>.tools`, если `kb.script.mcp.enabled` |
| Плановый скрипт (`ScheduledScriptService`) | только инструменты соединений с `scheduled: true` — за ним никто не смотрит |
| Сабагент поиска, стенд в настройках (`forceReadOnly`) | нет: прогон «только чтение» по построению, а что инструмент только читает, конфиг не гарантирует |

`mcp.tools()` перечисляет только то, что этому прогону можно вызвать.
Инструмент вне списка отвечает ошибкой, которая называет ключ конфига: модель
не может это исправить, а пользователь должен понять, куда смотреть.

Бюджеты:

- `max-calls` — свой счётчик, не общий `maxCalls` (тот рассчитан на 2000 дешёвых
  локальных чтений). Каждый вызов списывается: **без** мемоизации через
  `ScriptSession#call` — у MCP-инструмента бывают побочные эффекты, и повтор
  должен повторять.
- `max-bytes` — сумма длин нормализованных ответов; превышение — обычный
  `ScriptLimitExceededException` с советом сузить запрос.

### 4.5. Таймаут и остановка

Watchdog закрывает GraalJS-контекст по дедлайну или по «Стоп», но вызов хоста,
застрявший в `callTool`, этим не прерывается: прогон переживёт свой таймаут на
`spring.ai.mcp.client.request-timeout`. Поэтому `McpScriptApi`:

- получает дедлайн и `RunCancellation` прогона от `ScriptRunner`;
- перед вызовом проверяет, что до дедлайна осталось время;
- выполняет `callback.call` на виртуальном потоке и ждёт его частями до
  дедлайна, проверяя «Стоп» между ними. По таймауту или остановке перестаёт
  ждать и бросает ошибку. Запрос к серверу может дойти и после этого — так и
  написано в журнале прогона.

### 4.6. Журнал и видимость

- Каждый вызов — строка в журнале прогона (`log`):
  `mcp.call('jira_search'): 184 KB in 1.2 s`, ошибка — с её текстом. Отдельный
  список вызовов в `ScriptResult` не заводим: журнал уже показывается и модели,
  и в деталях вызова.
- `ScriptStats` получает `mcpCalls` (перегрузка конструктора на пять полей
  оставляет 15 мест создания как есть; в JSON поле только когда не 0).
  Мета плашки — `mcpCalls`, плашка в стадии D показывает «MCP: 3».
- Серверный лог — строка INFO на вызов.
- Ошибка инструмента («сервер недоступен», `ToolExecutionException`, запрет,
  бюджет) бросается в скрипт исключением с исходным текстом. Что JS ловит его
  через `try/catch`, закрепляет sandbox-тест. Если не ловит, обёртка `mcp`
  возвращает `{error}`, и это описывается в справочнике.

### 4.7. Справочник для модели

Справочник скриптов собирается `ScriptGuideService` из `prompt/script-run*.md`
один раз при старте. Новый фрагмент `prompt/script-run-mcp.md` добавляется во
все четыре рендеринга чата, когда `kb.script.mcp.enabled`, `kb.mcp.enabled` и
`kb.mcp.script-access` не пуст. Сабагенту — никогда. Список инструментов в
справочник не пишется: он меняется вместе с серверами и рвал бы кэш промпта —
для этого есть `mcp.tools()`. Пример для слабой модели — в навыке
`script-writing`, а не в справочнике. Что во фрагменте:

- когда звать инструмент напрямую, а когда из скрипта: ожидаешь большой ответ,
  нужна фильтрация, агрегация или несколько вызовов подряд → скрипт;
- `mcp.tools()` / `mcp.call()` и форма возвращаемого значения;
- бюджеты и что делать при ошибке;
- связка с шагом 1: увидел `truncated: true, resultId: r7` → `kb.result('r7')`,
  повторно звать сервер не нужно.

Описание `runScript` в аннотации не меняется — правило самого `ScriptFunction`.

### 4.8. Тесты

Sandbox-тесты `ScriptRunner` с fake-`ToolCallback`:

- `mcp.call` возвращает нормализованное значение, а результат скрипта
  обрезается и сохраняется как обычно;
- `max-calls` / `max-bytes`; повтор не кэшируется;
- методов нет при `enabled=false` и `forceReadOnly`; соединение вне
  `script-access` и инструмент вне его `tools` — отказ с именем ключа; плановый
  прогон видит только соединения с `scheduled: true`;
- инструмент недоступен → понятная ошибка; зависший инструмент → прогон
  укладывается в таймаут; «Стоп» во время вызова;
- `ScriptGuideServiceTest`: фрагмент есть ровно тогда, когда есть gateway.

## 5. Порядок работы

По правилу «стадии с ревью между ними»:

| Стадия | Содержание | Статус |
| --- | --- | --- |
| A | `McpContent` + тесты | готово |
| B | Шаг 1: обёртка, конфиг, проводка в реестре, лимит в панели, доки | готово |
| C | Шаг 2, ядро: `ScriptMcpProperties`, `script-access`, `ScriptMcpScope`, `scriptTools()`, `ScriptMcp` + `McpScriptApi`, бюджеты, таймаут, sandbox-тесты | в работе |
| D | Шаг 2, обвязка: справочник, `mcpCalls` в плашке, доки, i18n, `UPDATING.md` не нужен (по умолчанию выключено) | — |
| E | Полное ревью (`/code-review`) и `./run/test.sh pre-pr` | — |

Что показало ревью стадии B для C:

- В деталях вызова уже есть переключатель «что видела модель / целиком»
  (`tool_call_full_result`), поэтому отдельный бейдж «обрезано» в модалке не
  понадобился.
- `tools` не импортирует ничего из `service`, поэтому полка — узкий
  `ToolResultShelf`. Для C это значит: `McpScriptApi` живёт в
  `service/chat/script` и зависит от `tools` (`McpToolRegistry`, `McpContent`),
  обратной зависимости нет.

## 7. Решения

1. **Лимит по умолчанию** — 20 000 символов, как у скриптов. Соединению с
   длинными полезными ответами задаётся свой через `kb.mcp.result-limits`.
2. **`kb.script.mcp.enabled`** — по умолчанию `false`.
3. **Пишущие MCP-инструменты из скрипта** — решает конфиг MCP:
   `kb.mcp.script-access.<соединение>.tools` перечисляет, что можно звать из
   скриптов; по умолчанию ничего. `readOnlyHint` сервера не учитывается.
4. **Плановые скрипты** — только инструменты соединений с
   `kb.mcp.script-access.<соединение>.scheduled: true`.
