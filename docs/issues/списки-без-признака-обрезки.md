# Списки с пределом без признака обрезки

#475 завёл `GitCommitSearchResult { commits, truncated }` с доводом: «список без
признака обрезки не отличает „нет“ от „не дошли“». #477 назвал предел обхода в
описании инструмента. Почти все остальные инструменты с пределом молчат.

## 1. `searchCommitLog` выбрасывает уже посчитанный `truncated`

`GitService.searchCommitLog` (`service/file/git/GitService.java:437-443`) берёт
`CommitSearch.search(...).commits()`. `getCommitLog(query)` для модели не узнаёт
ни что `maxCount` сработал, ни что обход упёрся в 20 000. Описание инструмента
говорит о пределе статически, но на конкретный вызов ответа нет. Прямое
противоречие с мотивацией #475 в соседнем методе.

Что сделать: отдавать модели `truncated` (отдельным полем ответа или через
`ToolResult`), как это делает `/api/git/commits/grep`. То же для
`/api/git/commits/search` (`controller/GitController.java:235`, пикер фраз) —
там тоже `.commits()`.

## 2. Предел есть, флага нет, описание молчит

| Инструмент | Предел | Где |

| `getCommitLog` без query | 100 | `GitService.java:349`; просьба о 200 молча даёт 100 |
| `searchFiles` | 50, литерал без константы | `GitService.java:598`; описание инструмента предел не называет |
| `grepContent` | 200 блоков + 20 000 строк вывода | `GitGrepRunner.java:95-96, :40`; обрыв по `MAX_OUTPUT_LINES` невидим |
| `grepDocuments` | 200 | `DocumentService.java:61, :676` |

| `searchAttachments` | 20, newest first | `AttachmentRepository.java:50, :63` |

Без предела вовсе: `getChatAttachments`, `getDocumentAttachments`,
`getTreeSkeleton`, `getFileTree`, `getUncommittedChanges`, `kb.files`.

## 3. `GitGrepResult.truncated` неточен

`GitGrepResult.group` ставит `truncated = matches.size() >= limit`: `true` и
когда совпадений ровно `limit` (в #475 это специально сделано точным для
коммитов), и не ставится, когда прогон оборвал потолок `MAX_OUTPUT_LINES`.

## 4. `searchDocuments` в режиме keyword игнорирует аргументы

`DocumentFunction.searchDocuments` (`functions/DocumentFunction.java:123`)
принимает `limit` и `threshold`, но `case "keyword" -> documentService.search(query)`
их не передаёт. `DocumentRepository.java:137-141` — жёсткий
`LIMIT 20 ORDER BY updated_at DESC`: модель получает 20 самых свежих совпадений,
а не самые релевантные. Гибридный режим строит keyword-половину из того же
списка (`DocumentService.java:~808-812`).

`kb.search.keyword.limit: 20` в `application.yaml:512` не читается нигде —
мёртвый ключ конфигурации. Либо подключить его к запросу и к аргументу `limit`,
либо убрать из `application.yaml` и `конфигурация.md`.

## 5. Пределы без цены

Из #477: «предел в 2000 был выбран на глаз», и в комментарии теперь написано, во
что обходится 20 000. Измеренная цена есть только у `CommitSearch.SCAN`. Просто
названы, без довода: `Diffs.MAX_DIFF_LINES = 500` (`Diffs.java:19`),
`FileViews.HEAD_LINES = 200` / `TAIL_LINES = 50`, `RepoFiles.MAX_FILE_SIZE = 512 КБ`,
`GitCommands.MAX_OUTPUT_CHARS = 4000`, `ResultLimit.OBJECT_DEPTH = 2`,
`ScriptProperties.DEFAULT_MAX_CALLS = 2000`. Не задача «измерить всё», а правило
для следующего, кто их тронет: цифра без комментария о цене — повод замерить.
