# Поиск коммитов: что осталось вокруг #467, #475, #477, #488, #492

#475 вынес `CommitSearch` из `GitService` и завёл `GitCommitSearchResult`
с `truncated`, #477 поднял предел обхода до 20 000 и измерил его цену, #488
довёл признак до `ToolResult` у `getCommitLog`, #492 — до пикера плейсхолдера и
сделал признак точным. Ниже — что вокруг этого осталось в трёх экземплярах.

## Бэкенд

- **Три обхода истории.** `GitService.getCommitLog` (`:330-351`) и
  `getOutgoingCommits` (`:366-398`) идут через `git.log()`, `CommitSearch.search`
  (`CommitSearch.java:81-122`) строит `RevWalk` сам — с доводом в комментарии,
  что `LogCommand` отдаёт свой `RevWalk` как `Iterable` и закрыть его нечем.
  Довод верен и для первых двух: их обход тоже не закрывается. Один
  `CommitWalk` (откуда, фильтр пути, диапазон, предел) под всеми тремя; тогда
  `getCommitLog` без запроса — это `CommitSearch` с пустым запросом, и
  листинг получает `truncated` даром (сегодня просьба о 200 молча даёт 100 —
  последний пункт из `списки-без-признака-обрезки.md`, который #488 не закрыл).
- **Потолок 100 — в четырёх местах.** `CommitSearch.MAX_RESULTS`
  (`:45`), литерал в `GitService.getCommitLog` (`:332`) и его Javadoc (`:323`,
  `:404`), `GitService.MAX_OUTGOING` (`:113`), описание инструмента
  `GitFunction.java:171` («1–100»). Одна константа, на которую ссылаются
  Javadoc и описание.
- **Пустой запрос проверяется трижды.** `CommitSearch.search` (`:84`),
  `GitController.searchCommits` и `grepCommits` (`:236-238`, `:255-257` — те же
  пять строк дважды), `GitFunction.getCommitLog` (`:211`). Контроллеру хватит
  проверки в `CommitSearch`; у инструмента пустой запрос значит «листинг», это
  остаётся.
- **Пары `X` / `XAt` и перегрузки по числу аргументов.**
  `getCommitLog` ×2, `getBlame` / `getBlameAt`, `getFileContent` /
  `getFileContentAt`, `getFileOutline` / `getFileOutlineAt`,
  `getUncommittedChanges` ×4 (`GitService.java:316, :447, :610-615, :646-696,
  :713-725, :1211-1264`). `GitController.getCommits` (`:180`) ветвится по
  `at == null`, чтобы выбрать перегрузку, хотя четырёхаргументная принимает
  `null`. Один метод с `@Nullable rev` на пару — минус десяток публичных
  методов в файле на 484 строках.
- **Где совпало — ищет фронт.** `CommitSearch` отвечает «коммит подошёл», а
  строки описания с запросом находит `searchPanel/commitHits.js` тем же
  сравнением; ради этого `/commits/grep` везёт 50 полных описаний. Категории
  «Документы» и «Файлы» получают строки совпадений с бэкенда (`DocumentGrep`,
  `git grep`). `GitCommitMatch { commit, lines }` из `CommitSearch` выровняет
  коммиты с ними, уберёт двойное сравнение и `hashMatch`-эвристику.

## Фронтенд

- **Три способа выбрать коммит, три интерфейса.** Пикер плейсхолдера
  (`PlaceholderSearchField` + `useSearchDropdown`, `searchCommits`), категория
  «Коммиты» (`useSearchResults` + `commitHits`, `grepCommits`) и
  `common/git/RevisionPicker.jsx`, где хеш только вводят руками: Javadoc у
  `gitApi.getRefs` обещает «хеши ищут через `searchCommits`», а пикер ревизии
  этого не делает. `useSearchDropdown` с `searchCommits` ложится туда без
  новой механики — тот же дропдаун, что у плейсхолдера.
- **Три формулировки «показано не всё».** Пикер различает три случая
  (`phraseFill.partial` / `partialHistory` / `nothingFoundPartial`,
  `PlaceholderSearchField.jsx:161-199`, по `spec.limit`), страница поиска —
  одну (`ResultList.jsx:99`, `truncated.${scope}`), чат — одну
  (`GrepMatchesView`). Различие «лимит полон — уточните» / «история не
  досмотрена» одинаково полезно всем трём; одна функция
  `truncationNote(count, limit, truncated)` с ключами в `common`.
- **`useSearchResults.useAnswer`** (`:28-60`) — четвёртый экземпляр хука
  «ключ запроса + ответ со своим ключом», см. `blame.md` про `useFileBlame` и
  `useFileContent`.
