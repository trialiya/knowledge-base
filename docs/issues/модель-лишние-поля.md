# Модели уходят лишние поля

#453 и #454 поставили `@JsonInclude(NON_NULL)` на nullable-поля git-DTO,
документов и вложений и завели `DocumentSkeletonNode` вместо полного
`DocumentNode` с заглушками. #480 добавил `ModelView` (`forModel()`), чтобы
инструмент отдавал модели урезанный ответ, а окну деталей — полный. Сделано
точечно, остались места с тем же недугом.

Сериализует ответы `CompactToolResultConverter` поверх
`DefaultToolCallResultConverter`; глобального `default-property-inclusion` в
конфиге нет, работают только аннотации на полях. Все DTO ниже уходят и
sub-agent'у поиска (`kb.search.subagent.allowed-tools`).

## 1. `findDocumentsByName` отдаёт полный `DocumentNode`

`DocumentFunction.findDocumentsByName` (`functions/DocumentFunction.java:239`)
возвращает `List<DocumentNode>` из `DocumentService.toStubNode`: у каждой записи
`children: []`, `createdAt`, `updatedAt`, `summaryStale`, `hasChildren`, `version`,
а `description` — это 150-символьный сниппет под чужим именем. Ровно то, что
#454 убрал у `getTreeSkeleton`.

Что сделать: вернуть `DocumentSkeletonNode` (или его вариант со сниппетом).
Проверить, что «Обзор» в чате (`recordList.js`) по-прежнему принимает список.

## 2. Nullable-поля без `NON_NULL`

| DTO | Поле | Когда `null` |
| --- | --- | --- |
| `model/script/ScriptResult.java:134` `ForModel` | `error` | каждый успешный прогон шлёт `"error": null` |
| там же | `ScriptError.line` | ошибка без строки |
| `model/git/dto/GitFileContent.java` | `commit` | каждое чтение рабочего дерева |
| там же | `content` | бинарный файл |
| там же | `language`, `fromLine`, `toLine` | неизвестный язык, чтение целиком |
| `model/git/dto/GitFileNode.java` | `size` | каждый каталог в `getFileTree` |
| `model/git/dto/GitFileOutline.java` | `language` | |
| `model/git/dto/GitEditResult.java` | `diff` | `createFile` (`GitWriter.java:115`) |
| `model/doc/dto/DocumentShort.java` | `summarySourceVersion`, `parentId` | ответ всех 8 инструментов записи |
| `model/doc/dto/DocumentSkeletonNode.java:15-23` | `parentId` | корневые узлы |
| `model/search/SearchAgentResult.java:30-37` | `report` | |

Оговорка из #454: `parentId` печатается и при `null`, потому что «Обзор»
узнаёт иерархию по `'parentId' in r` (`treeResult.js`). Для
`DocumentSkeletonNode` и `DocumentShort` это надо учесть — либо оставить, либо
поправить `treeResult.js`.

## 3. Поля, которые `NON_NULL` не спрячет

Пустые списки и `false` — не `null`:

- `ScriptResult.ForModel`: `log`, `filesRead`, `edits` уходят как `[]`.
- `SearchResult.parentList` помечен `NON_NULL`, но никогда не `null`:
  `DocumentService.attachParents` подставляет `List.of()` для корней. Нужен
  `NON_EMPTY`.
- `DocumentView.children` у листового документа — `[]`; у каждого ребёнка
  `parentId` равен id самого документа, плюс `version` и `system`.
- `GitFileContent.binary=false`, `tracked=true`; `GitFileNode.tracked=true`;
  `GitGrepMatch.tracked=true` без `includeUntracked`; `searchFiles` всегда
  `type: FILE` (`GitService.java:636-637`).
- `GitFileNode.name` всегда равен последнему сегменту `path`.
- `GitCommit.email` рядом с `author` на каждом коммите.
- `GitFileOutline.parser` (`tree-sitter` / `regex` / `markdown`) — диагностика
  для UI.
- `DocumentNode`, `DocumentView`, `DocumentShort`, `Attachment`: `createdAt`,
  `updatedAt`, `summaryStale`, `ownerType` (дублирует `documentId`/`conversationId`).

## 4. Кандидаты на `ModelView`

- **`GitEditResult.diff`** при `editFile` — unified diff до 500 строк, который
  модель только что сама написала, возвращается ей целиком. UI его использует
  (`getResultMeta`), так что это второй `ModelView` после `ScriptResult`. То же
  через `ScriptResult.ForModel.edits`: `forModel()` диффы не трогает.
- `getFileContent` с диапазоном строк не ограничен ничем: `FileViews.of`
  режет `[from, to]` без предела размера, `fromLine=1, toLine=999999` на
  большом файле вернёт его целиком. Чтение целиком ограничено 512 КБ
  (`RepoFiles.MAX_FILE_SIZE`), дальше head+tail 200+50 строк; Javadoc
  `GitFunction.java:54-55` всё ещё говорит «без содержимого».
- `getCommitDiff` / `getUncommittedChanges` с `includePatch`: 500 строк на файл
  (`Diffs.MAX_DIFF_LINES`), но число файлов и число хешей через запятую не
  ограничены.
- `grepContent` и `grepDocuments`: нет предела длины строки, совпадение в
  минифицированном файле уходит целиком.
- `getOriginalMessages`: описание обещает «Max 10 messages per call»
  (`MessageLookupFunction.java:29`), код не проверяет; текст сообщений не
  ограничен.
- `getTreeSkeleton` — `repo.findAll()` без предела; `getAttachmentContentByFileName`
  — список без предела по числу, каждый элемент до 15 000 символов.
